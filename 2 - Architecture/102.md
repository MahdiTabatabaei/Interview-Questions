**معماری پیازی** (Onion Architecture) روشی برای طراحی نرم‌افزار است که می‌گوید:

**مرکز سیستم باید شامل منطق اصلی و قوانین کسب‌وکار باشد، و همه‌چیزهای دیگر باید به این مرکز وابسته باشند، نه برعکس.**

مثل یک پیاز، این معماری از چند **لایه** تشکیل شده که دور هسته قرار گرفته‌اند.

---

## چرا اسمش پیاز است؟

چون لایه‌های آن مثل پیاز روی هم قرار می‌گیرند و **هرچه به مرکز نزدیک‌تر می‌شویم، بخش‌های مهم‌تر و پایدارتر سیستم قرار دارند**.

---

## لایه‌های اصلی

### 1) لایه Domain (هسته پیاز)

این **مغز سیستم** است و شامل:

- قوانین و منطق اصلی کسب‌وکار
- موجودیت‌ها (Entities)
- سرویس‌های دامنه

ویژگی مهم:

**هیچ وابستگی به لایه‌های بیرونی ندارد.**

---

### 2) لایه Application

این لایه می‌گوید «با دامنه چه کار انجام بدهیم».

شامل:

- use caseها
- سرویس‌های اپلیکیشن

این لایه هم **به لایه‌های بیرونی وابسته نیست**.

---

### 3) لایه Infrastructure (زیرساخت)

این لایه ابزارها و جزئیات فنی را فراهم می‌کند:

- دیتابیس
- ارسال ایمیل
- لاگ‌گیری
- APIها

این لایه **به لایه‌های داخل وابسته است، اما لایه‌های داخل به این وابسته نیستند**.

---

### 4) لایه Presentation (UI/API)

نزدیک‌ترین لایه به کاربر:

- رابط کاربری
- کنترلرهای API

این لایه هم باید فقط به داخل وابسته باشد، نه برعکس.

---

## هدف اصلی Onion Architecture

هدف این معماری این است که:

- **منطق اصلی سیستم از تغییرات تکنولوژی آسیب نبیند.**
- تغییر دیتابیس، UI یا فریمورک بدون ایجاد مشکل در منطق اصلی انجام شود.
- سیستم قابل تست و توسعه‌پذیر باشد.

---

## یک مثال خیلی ساده

فرض کن یک اپلیکیشن فروشگاه داری.

- اگر تصمیم بگیری دیتابیس را از MySQL به MongoDB تغییر بدهی

یا

- از Web API به gRPC مهاجرت کنی

**نباید لازم باشد کد قسمت‌های مهم مثل قوانین سفارش، پرداخت و سبد خرید را تغییر بدهی.**

تمام این تغییرات فقط باید در لایه‌های بیرونی رخ بدهند.

---

## خلاصه کوتاه و راحت

- هسته = منطق اصلی کسب‌وکار
- لایه‌های بیرونی = تکنولوژی‌ها و ابزارها
- وابستگی همیشه از بیرون به داخل است
- تغییر ابزارها نباید منطق سیستم را خراب کند
