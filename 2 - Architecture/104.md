در معماری **میکروسرویس‌ها** دو مفهوم مهم وجود دارد: **Autonomy** و **Authority**. این دو کمک می‌کنند سرویس‌ها واقعاً مستقل و قابل مقیاس باشند.

---

# 1) مفهوم Autonomy (خودمختاری)

درواقع **Autonomy یعنی هر میکروسرویس بتواند مستقل از بقیه سرویس‌ها کار کند.**

ویژگی‌های سرویس خودمختار:

- توسعه مستقل
- استقرار (Deploy) مستقل
- پایگاه داده مستقل
- منطق کسب‌وکار مستقل
- حداقل وابستگی به سرویس‌های دیگر

مثال:

فرض کن سیستم فروشگاه داری با این سرویس‌ها:

- User Service
- Order Service
- Payment Service

اگر **Order Service** بخواهد deploy شود، نباید لازم باشد **User Service** یا **Payment Service** هم deploy شوند.

همچنین Order Service باید بتواند بدون وابستگی زیاد به دیتابیس یا منطق بقیه سرویس‌ها کار کند.

هدف Autonomy:

- کاهش coupling
- افزایش سرعت توسعه
- deploy مستقل سرویس‌ها

---

# 2) مفهوم Authority (مالکیت داده و منطق)

درواقع **Authority یعنی هر سرویس مالک قطعی داده و منطق دامنه خودش باشد.**

یعنی فقط یک سرویس **حق تغییر یا مدیریت داده‌های مربوط به خودش را دارد**.

مثال:

در یک سیستم فروشگاه:

User Service

مالک داده‌های کاربر است.

Order Service

مالک سفارش‌ها است.

Payment Service

مالک پرداخت‌ها است.

بنابراین:

- سرویس Order Service **نباید مستقیم به دیتابیس User Service دسترسی داشته باشد**.
- اگر Order Service اطلاعات کاربر را بخواهد باید از طریق **API یا event** از User Service بگیرد.

---

# مثال ساده ترکیب Autonomy و Authority

فرض کن Order Service می‌خواهد سفارش ثبت کند.

کارهایی که انجام می‌دهد:

1. بررسی کاربر → درخواست به User Service
2. ذخیره سفارش → در دیتابیس خودش
3. درخواست پرداخت → Payment Service

اما:

- سرویس Order Service **مالک سفارش‌ها است (Authority)**
- و می‌تواند **مستقل deploy و توسعه شود (Autonomy)**

---

# تفاوت کوتاه این دو مفهوم

Autonomy

تمرکز روی **استقلال عملیاتی سرویس**

Authority

تمرکز روی **مالکیت داده و منطق دامنه**

---

# یک قانون مهم در میکروسرویس‌ها

قانون معروف:

**“You build it, you run it, you own it.”**

یعنی تیمی که یک سرویس را می‌سازد:

- مالک آن سرویس است
- مسئول داده‌های آن است
- مسئول اجرای آن است

این دقیقاً ترکیب **Autonomy + Authority** است.
