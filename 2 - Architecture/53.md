مفهوم ACID (در دیتابیس‌های سنتی)

- Atomic
- Consistent
- Isolated
- Durable

مفهوم BASE (در سیستم‌های توزیع‌شده)

- Basically Available
- Soft state
- Eventually consistent

ACID = دقت

BASE = سرعت و مقیاس‌پذیری

----

مفاهیم **ACID** و **BASE** دو «طرز فکر» متفاوت برای کار با داده در سیستم‌ها هستند؛ مخصوصاً وقتی به **سیستم‌های توزیع‌شده** می‌رسیم، تضادشان خیلی پررنگ می‌شود و مستقیم به **CAP** و **Eventual Consistency** ربط پیدا می‌کند.

بیاییم مرحله‌ای و فشرده ببینیم:

---

## 1. تعریف ACID چیست؟

درواقع **ACID** مجموعه‌ای از ویژگی‌هاست که معمولاً در **دیتابیس‌های سنتی (Relational / SQL)** و تراکنش‌های کلاسیک استفاده می‌شود:

1. **A – Atomicity (اتمی بودن)**  
   یا همهٔ کارهای یک تراکنش انجام می‌شود، یا هیچ‌کدام.  
   - مثال: انتقال پول بین دو حساب: یا هر دو عملیات (برداشت + واریز) انجام شود یا هیچ‌کدام.

2. **C – Consistency (سازگاری قوی)**  
   بعد از تراکنش، دیتابیس همچنان قوانین و محدودیت‌ها (Constraints) را رعایت می‌کند.  
   - مثلاً موجودی منفی نشود، کلیدهای خارجی معتبر باشند و…

3. **I – Isolation (جداسازی)**  
   تراکنش‌ها طوری عمل می‌کنند که انگار **به‌صورت تک‌به‌تک و پشت‌سرهم** اجرا شده‌اند؛ نه هم‌زمان.  
   - یعنی اجرای هم‌زمان تراکنش‌ها، نتیجه‌ای معادل اجرای ترتیبی بدهد.

4. **D – Durability (ماندگاری)**  
   وقتی تراکنش Commit شد، حتی بعد از کرش سرور/برق رفتن، نتیجهٔ آن از بین نمی‌رود.

🔹 نتیجه:  
مکانیزم **ACID** برای **ثبات قوی، تراکنش‌های مهم مالی، بانک‌ها، سیستم‌های مالی و…** عالی است.  
اما در **مقیاس خیلی بزرگ و توزیع‌شده، هزینه‌بر و کند می‌شود** (به‌خاطر هماهنگی زیاد بین نودها).

---

## 2. تعریف BASE چیست؟

درواقع **BASE** یک استاندارد رسمی مثل ACID نیست؛ بیشتر یک **فلسفه/رویکرد** در دنیای **سیستم‌های توزیع‌شده و NoSQL** است.  

معمولاً در مقابل ACID مطرح می‌شود.

عبارت BASE مخفف است از:

1. **B – Basically Available (در اصل در دسترس)**  
   سیستم همیشه سعی می‌کند **جواب بدهد**؛ حتی اگر داده کاملاً دقیق نباشد.

2. **S – Soft state (حالت نرم/غیرقطعی)**  
   حالت سیستم ممکن است موقتاً ناپایدار باشد و بدون ورودی جدید هم تغییر کند  
   (مثلاً با sync شدن replicaها، state عوض شود).

3. **E – Eventual consistency (سازگاری نهایی)**  
   داده در همهٔ نودها **در لحظه یکی نیست**،  
   اما اگر مدتی صبر کنیم و بروزرسانی جدیدی نیاید، **در نهایت هماهنگ می‌شود**.

🔹 نتیجه:  
قابلیت BASE به‌جای سازگاری قوی، **Availability بالا + مقیاس‌پذیری + تحمل خطا** را ترجیح می‌دهد.  
این دقیقاً همان مدلی است که در بسیاری از دیتابیس‌های **NoSQL** و معماری‌های **Microservice / Event-Driven** می‌بینیم.

---

## 3. تفاوت ACID vs BASE در یک نگاه

### قیاس جدول‌وار

| ویژگی | ACID | BASE |
|-------|------|------|
| تمرکز اصلی | **Correctness (درستی قوی)** | **Availability + Scalability** |
| مدل سازگاری | Strong Consistency | Eventual Consistency / Weak Consistency |
| نوع سیستم | RDBMS سنتی (SQL) | NoSQL، سیستم‌های توزیع‌شده بزرگ |
| مناسب برای | بانک‌ها، مالی، تراکنش‌های دقیق، یک دیتابیس مرکزی | سیستم‌های با ترافیک زیاد، جغرافیای گسترده، شبکه‌های اجتماعی، لاگ، کَش |
| رفتار در CAP | بیشتر متمایل به **CP** یا **CA** (در محیط تک‌نودی) | بیشتر متمایل به **AP** |
| هزینه | Latency و Coordination بالا | امکان Latency کمتر، مقیاس‌پذیری بیشتر |
| خطای موقت داده | قابل قبول نیست | موقتاً قابل قبول است |

## 4. ارتباط ACID / BASE با CAP و Eventual Consistency

### دو مفهوم ACID و CAP

- سیستم‌هایی که **ACID کامل** را حفظ می‌کنند، معمولاً در دنیای توزیع‌شده:
  - ویژگی **Consistency** را جدی می‌گیرند
  - در صورت Partition، ممکن است **Availability را قربانی کنند** (مدل CP)
  - مثلاً: تراکنش توزیع‌شده (Two-phase commit) → اگر یکی از نودها unreachable باشد، تراکنش معلق می‌ماند یا fail می‌شود.

### و BASE و CAP

- سیستم‌های **BASE**:
  - قابلیت Availability را ترجیح می‌دهند
  - در صورت Partition، اجازه می‌دهند داده موقتاً **Inconsistent** شود
  - ولی با Eventual Consistency، **بعداً sync می‌شوند**
  - این‌ها همان سیستم‌های **AP** هستن.

## 5. مثال‌های ملموس برای درک تفاوت

### مثال ۱ – سیستم بانکی (ACID)

سناریو: انتقال ۱۰۰ هزار تومان بین دو حساب:

- یا هر دو عملیات (برداشت از A، واریز به B) انجام شود
- یا هیچ‌کدام انجام نشود  
- اگر یکی از دیتابیس‌ها Down شود، ترجیح می‌دهد تراکنش را Fail کند تا پول گم/دوبله نشود.  
- **قیمت:** ممکن است سیستم لحظه‌ای برای بعضی درخواست‌ها پاسخ ندهد → ولی داده همیشه درست است.

### مثال ۲ – شبکهٔ اجتماعی / Like (BASE)

سناریو: کاربر روی دکمه Like کلیک می‌کند:

- ممکن است تعداد Like در موبایل خودش زودتر آپدیت شود، در دسکتاپ با تأخیر.
- دیتابیس‌ها در دیتاسنترهای مختلف، لایک را چند ثانیه دیرتر ببینند.
- **اما در نهایت** همه‌جا یک عدد یکسان نمایش داده خواهد شد.
- اگر یکی از replicaها down شود، همچنان سیستم اجازه لایک‌کردن می‌دهد، بعداً sync می‌کند.
- **قیمت:** لحظه‌ای ممکن است عدد لایک دقیق نباشد، ولی تجربه کاربری خوب و High Availability داریم.

## 6. در سیستم‌های Microservice / Event-Driven (مثل استک خودت)

در معماری‌ای شبیه آنچه گفتی (**Kubernetes + ASP.NET Core + RabbitMQ + Elasticsearch**)، خیلی وقت‌ها:

- **هر سرویس دیتابیس خودش را دارد** (Database per Service)
- بین سرویس‌ها **Distributed Transaction ACID** نداریم (چون پیچیده، کند و شکننده است)
- به‌جای آن از:
  - **Outbox Pattern**
  - **Inbox Pattern**
  - **Idempotency**
  - **Eventual Consistency**
  استفاده می‌کنیم.

این یعنی در سطح **هر سرویس** معمولاً:
- داخل دیتابیس خودش از **ACID محلی** استفاده می‌کند  
  (مثلاً یک تراکنش در SQL Server یا Postgres).

اما در سطح **کل سیستم**:
- رفتار کلی شبیه **BASE + Eventual Consistency** است:
  - سرویس A یک Event منتشر می‌کند
  - سرویس B با تأخیر آن را می‌گیرد و دیتای خودش را آپدیت می‌کند
  - در این فاصله، سیستم موقتاً **inconsistent** است، ولی در نهایت **همگام می‌شود**.

به زبان ساده:

> داخل هر سرویس: ACID  
> بین سرویس‌ها: BASE + Eventual Consistency

این ترکیب، الگوی رایج معماری Microservice مدرن است.

## 7. چطور تصمیم بگیری ACID یا BASE؟

معمولاً این سؤالات را می‌پرسیم:

1. **آیا کمی ناسازگاری موقت قابل قبول است؟**
   - اگر نه → تمایل به ACID و Strong Consistency
   - اگر بله → می‌توانیم BASE و Eventual Consistency را بپذیریم

2. **در دسترس بودن (Availability) چقدر مهم است؟**
   - مثلاً برای یک فروشگاه بزرگ جهانی، Down بودن سیستم ضرر سنگین دارد → BASE جذاب‌تر می‌شود.

3. **مقیاس چقدر بزرگ است (ترافیک، جغرافیا، تعداد نودها)؟**

   - در مقیاس خیلی بزرگ، ACID سراسری تقریباً غیرعملی و پرهزینه است.

4. ویؤگی های**Domain چقدر حساس است؟**

   - مالی/بانکی/حسابداری → معمولاً ACID قوی‌تر  
   - لاگ‌ها، آمار، Recommendation، فید اخبار، لایک → BASE

---

## 8. خلاصهٔ نهایی

- **ACID**:  
  - فلسفهٔ: «داده‌ام باید همیشه درست و سازگار باشد؛ حتی اگر به قیمت کندی یا عدم دسترسی موقت.»
  - مناسب: بانک، مالی، تراکنش‌های حساس، دیتابیس مرکزی.

- **BASE**:  
  - فلسفهٔ: «سیستم باید همیشه زنده و پاسخگو باشد؛ اگر داده کمی دیرتر هماهنگ شد، اشکال ندارد.»  
  - در عمل: **Basically Available, Soft state, Eventual consistency**
  - مناسب: سیستم‌های توزیع‌شده بزرگ، NoSQL، سرویس‌های اینترنت مقیاس بالا، event-driven systems.

- در معماری Microservice مدرن:  
  - **درون هر سرویس**: ACID محلی  
  - **بین سرویس‌ها**: BASE + Eventual Consistency با کمک RabbitMQ، Outbox، Inbox، Idempotency
