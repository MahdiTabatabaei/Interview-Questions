Outbox:

- در سرویس فرستنده
- تضمین ارسال Event

Inbox:

- در سرویس گیرنده
- تضمین مصرف Event فقط یک بار (Idempotency)

---


این دو الگو هر دو برای **قابل‌اعتماد کردن پیام‌رسانی در سیستم‌های توزیع‌شده** استفاده می‌شوند، اما هر کدام سمت متفاوتی از جریان پیام را حل می‌کنند:

- الگوی **Outbox**: مشکل **ارسال مطمئن پیام از سرویس فرستنده**
- الگوی **Inbox**: مشکل **مصرف مطمئن و idempotent پیام در سرویس گیرنده**

---

# 1) تعریف Outbox Pattern چیست؟

فرض کن در سرویس سفارش می‌خواهی:

1. سفارش را در دیتابیس ذخیره کنی
2. بعد یک event مثل `OrderCreated` به RabbitMQ بفرستی

مشکل اینجاست:

- اگر DB ذخیره شود ولی publish به RabbitMQ fail شود → داده ثبت شده ولی event ارسال نشده
- اگر اول publish شود ولی DB fail شود → event منتشر شده ولی داده واقعی وجود ندارد

## راه‌حل Outbox

به جای اینکه مستقیم event را به broker بفرستی:

- داخل **همان transaction دیتابیس**:
  - داده اصلی را ذخیره می‌کنی
  - و event را هم در یک جدول `OutboxMessages` ذخیره می‌کنی

بعد یک background worker آن eventها را از Outbox می‌خواند و به RabbitMQ publish می‌کند.

### نتیجه
اگر transaction موفق شود، هم داده اصلی هست هم event آماده ارسال است.  
پس event گم نمی‌شود.

---

## مثال ساده

### جدول‌ها

- `Orders`
- `OutboxMessages`

### در یک transaction:

```text
Insert into Orders(...)
Insert into OutboxMessages(EventType='OrderCreated', Payload='...')
Commit
```

بعد worker:

```text
خواندن پیام‌های ارسال‌نشده از Outbox
→ publish به RabbitMQ
→ mark as sent
```

---

# 2) Inbox Pattern چیست؟

حالا برویم سمت consumer.

فرض کن سرویس پرداخت event `OrderCreated` را از RabbitMQ می‌گیرد.  
ابزار RabbitMQ ممکن است در شرایطی پیام را دوباره تحویل دهد:

- consumer ack نداده
- connection قطع شده
- retry انجام شده
- publisher duplicate فرستاده

پس یک event ممکن است **بیش از یک بار** به consumer برسد.

اگر consumer بدون کنترل، هر بار این پیام را پردازش کند، ممکن است:

- دوبار پرداخت ثبت شود
- دوبار ایمیل ارسال شود
- دوبار رکورد ساخته شود

## راه‌حل Inbox

سرویس گیرنده قبل از پردازش، یک جدول مثل `InboxMessages` دارد.  
هر پیام با `MessageId` یا `EventId` چک می‌شود:

- اگر قبلاً پردازش شده → دوباره انجامش نده
- اگر جدید است → پردازش کن و در Inbox ثبت کن

### نتیجه
مصرف پیام **idempotent** می‌شود.

---

# 3) تفاوت اصلی در یک جمله

- الگوی **Outbox** می‌گوید:  
  > «چطور مطمئن شوم event از سرویس من گم نمی‌شود و eventually publish می‌شود؟»

- الگوی **Inbox** می‌گوید:  
  > «چطور مطمئن شوم اگر یک پیام چند بار به من رسید، فقط یک بار اثر بگذارد؟»

---

# 4) مقایسه مستقیم

| مورد | Outbox Pattern | Inbox Pattern |
|------|----------------|---------------|
| محل استفاده | سمت Producer | سمت Consumer |
| مشکل اصلی | از دست رفتن event هنگام publish | پردازش تکراری پیام |
| ایده اصلی | ذخیره event در DB قبل از publish | ثبت پیام دریافتی قبل/حین پردازش |
| هدف | Reliable message publishing | Idempotent message consumption |
| ابزار رایج | Outbox table + background publisher | Inbox table + deduplication check |
| وابستگی به broker | مستقل از broker | مستقل از broker |
| نتیجه | پیام eventually ارسال می‌شود | پیام تکراری دوبار اثر نمی‌گذارد |

# 5) مثال واقعی در معماری میکروسرویس

## سناریو
- `OrderService` سفارش ثبت می‌کند
- `PaymentService` باید event را مصرف کند

---

## بدون Outbox / Inbox

### مشکل 1:
وقتی `OrderService` سفارش را ذخیره می‌کند ولی قبل از publish کرش می‌کند  
در این وضعیت → `PaymentService` هیچ‌وقت خبردار نمی‌شود

### مشکل 2:
وقتی `PaymentService` event را می‌گیرد، پرداخت را ثبت می‌کند، اما قبل از ack کرش می‌کند  
در این وضعیت → RabbitMQ دوباره همان event را می‌فرستد  
→ ممکن است دوباره پرداخت ثبت شود

---

## با Outbox + Inbox

### در OrderService

- سفارش در DB ذخیره می‌شود
- وقدار `OrderCreated` در Outbox ذخیره می‌شود
- سپس worker بعداً آن را publish می‌کند

### در PaymentService

- قبل از اعمال اثر، `MessageId` در Inbox بررسی می‌شود
- اگر قبلاً processed شده بود → نادیده گرفته می‌شود
- اگر جدید بود → پردازش + ثبت در Inbox

# 6) آیا Outbox جلوی Duplicate را هم می‌گیرد؟

نه کامل.

الگوی Outbox تضمین می‌کند پیام **گم نشود**،  
اما در بعضی شرایط ممکن است پیام **بیش از یک بار** publish شود.

مثلاً:

- ابتدا worker پیام را publish کرده
- ولی قبل از اینکه status آن را `Sent` کند کرش کرده
- بعد از restart دوباره همان پیام را publish می‌کند

پس Outbox معمولاً **at-least-once delivery** می‌دهد، نه exactly-once.

برای همین Inbox مهم می‌شود.

---

# 7) آیا Inbox بدون Outbox کافی است؟

بستگی به مشکل طراحی دارد.

- اگر نگرانی‌ بیزینس این است که producer event را از دست ندهد → **Outbox لازم است**
- اگر نگرانی‌ بیزینس duplicate processing در consumer است → **Inbox لازم است**
- در سیستم‌های جدی معمولاً **هر دو** با هم استفاده می‌شوند

- Business data + Outbox message در یک transaction

## Broker

- RabbitMQ / Kafka / Service Bus

## سمت Consumer
- Check inbox
- اگر جدید بود:
  - business logic
  - save inbox record
  - ack

# 9) شبه‌کد ساده

## Outbox

```csharp
using var tx = db.Database.BeginTransaction();

db.Orders.Add(order);

db.OutboxMessages.Add(new OutboxMessage
{
    Id = eventId,
    Type = "OrderCreated",
    Payload = json,
    OccurredOn = DateTime.UtcNow
});

db.SaveChanges();
tx.Commit();
```

publisher worker:

```csharp
var messages = db.OutboxMessages.Where(x => !x.Sent).ToList();

foreach (var msg in messages)
{
    PublishToRabbitMq(msg);
    msg.Sent = true;
}

db.SaveChanges();
```

---

## Inbox

```csharp
var exists = db.InboxMessages.Any(x => x.MessageId == message.Id);

if (exists)
{
    // قبلاً پردازش شده
    return;
}

// business logic
ProcessMessage(message);

db.InboxMessages.Add(new InboxMessage
{
    MessageId = message.Id,
    ProcessedAt = DateTime.UtcNow
});

db.SaveChanges();
```

# 10) خلاصه خیلی ساده

اگر بخواهم خیلی ملموس بگویم:

- **Outbox** =  
  «پیامی که باید بفرستم را اول در دفتر خروجی خودم ثبت می‌کنم تا گم نشود.»

- **Inbox** =  
  «پیامی که دریافت می‌کنم را در دفتر ورودی‌ام چک می‌کنم که قبلاً یک بار انجامش نداده باشم.»

---

# نتیجه نهایی

## Outbox Pattern
برای **ارسال مطمئن event/message** از سمت producer است.

## Inbox Pattern
برای **جلوگیری از پردازش تکراری** در سمت consumer است.

## در عمل
در معماری‌های مبتنی بر RabbitMQ / Kafka / Microservices معمولاً:

>الگوی  **Outbox + Inbox با هم** استفاده می‌شوند  
> چون اولی مشکل **loss** را حل می‌کند و دومی مشکل **duplicate** را.
