Anemic Model:

- فقط getter/setter
- بدون رفتار
- قوانین کسب‌وکار بیرون از مدل

Domain Model:

- دارای رفتار
- قوانین داخل خود مدل
- غنی و واقعی‌تر

مثال Anemic (بد):
```csharp

public class Order { public int Qty { get; set; } }

```
مثال Domain Model (خوب):
```csharp

public class Order
{
    private int _qty;
    public void Increase(int value)
    {
        if(value <= 0) throw new Exception();
        _qty += value;
    }
}

```

----

 فرق Domain Model و Anemic Model رو با یک تصویر ذهنی واضح . بیایم با مثال «ثبت سفارش» در یک فروشگاه آنلاین، دو مدل را کنار هم مقایسه کنیم.

تصویر ذهنی خیلی کوتاه:

- درDomain Model: مغز و قلب در خود دامنه هستند؛ موجودیت‌ها رفتار دارند و قوانین را اجرا می‌کنند.
- در Anemic Model: موجودیت‌ها فقط ظرف داده‌اند؛ مغز خارج از دامنه در سرویس‌هاست؛ قوانین پراکنده و ضعیف.

مثال مشترک: سناریوی “ثبت سفارش”

قانون‌های دامنه:
- سفارش فقط زمانی قابل تأیید است که حداقل یک آیتم داشته باشد.
- مجموع قیمت باید با تخفیف معتبر محاسبه شود.
- موجودی باید رزرو شود قبل از تأیید نهایی.

1) طراحی Domain Model (غنی)
ویژگی‌ها:
- موجودیت‌ها و Value Objectها رفتار دارند.
- قوانین درون دامنه متمرکز و قابل کشف هستند.
- تغییر قوانین معمولاً در دامنه انجام می‌شود نه در لایه‌های بیرونی.

کد نمونه (خلاصه):

```csharp
// Domain
public class Order
{
    private readonly List<OrderItem> _items = new();
    public IReadOnlyCollection<OrderItem> Items => _items.AsReadOnly();
    public Money Total { get; private set; } = Money.Zero;
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;

    public void AddItem(ProductId productId, int quantity, Money unitPrice)
    {
        if (quantity <= 0) throw new DomainException("Quantity must be positive.");
        _items.Add(new OrderItem(productId, quantity, unitPrice));
        RecalculateTotal();
    }

    public void ApplyDiscount(DiscountPolicy policy)
    {
        Total = policy.Apply(Total);
    }

    public void Confirm(IInventoryService inventory)
    {
        if (!_items.Any())
            throw new DomainException("Order must have at least one item.");

        inventory.Reserve(_items.Select(i => (i.ProductId, i.Quantity)));
        Status = OrderStatus.Confirmed;
    }

    private void RecalculateTotal()
    {
        Total = _items.Aggregate(Money.Zero, (sum, i) => sum + i.Subtotal);
    }
}

public record OrderItem(ProductId ProductId, int Quantity, Money UnitPrice)
{
    public Money Subtotal => UnitPrice * Quantity;
}
```

تصویر ذهنی:

- سفارش یا Order مثل یک موجود زنده است: خودش می‌فهمد چه موقع معتبر است، خودش جمع می‌زند، خودش تخفیف را اعمال می‌کند، و خودش با انبار تعامل رزرو می‌کند (از طریق یک پورت/سرویس دامنه).
- قوانین نزدیک به داده‌ها هستند؛ خواندن کد دامنه، قوانین را آشکار می‌کند.

مزایا:
- انسجام بالا، قوانین متمرکز، تست‌پذیری خوب، جلوگیری از منطق تکراری.
- کاهش “دانش پنهان” در سرویس‌های پراکنده.

معایب:
- طراحی اولیه سخت‌تر، نیاز به درک درست دامنه و Ubiquitous Language.


2) طارحی Anemic Model (فقیر)

ویژگی‌ها:
- موجودیت‌ها فقط getter/setter دارند؛ رفتار ندارند.
- قوانین در Application Service یا حتی Controllerها پخش می‌شوند.
- دامنه “بی‌مغز” است؛ سرویس‌ها تصمیم می‌گیرند.

کد نمونه (خلاصه):

```csharp
// Domain (Anemic)
public class Order
{
    public List<OrderItem> Items { get; set; } = new();
    public decimal Total { get; set; }
    public string Status { get; set; } = "Draft";
}

public class OrderItem
{
    public Guid ProductId { get; set; }
    public int Quantity { get; set; }
    public decimal UnitPrice { get; set; }
}

// Application Service
public class OrderService
{
    private readonly IInventoryService _inventory;

    public OrderService(IInventoryService inventory)
    {
        _inventory = inventory;
    }

    public void AddItem(Order order, Guid productId, int qty, decimal price)
    {
        if (qty <= 0) throw new Exception("Quantity must be positive.");
        order.Items.Add(new OrderItem { ProductId = productId, Quantity = qty, UnitPrice = price });
        order.Total = order.Items.Sum(i => i.UnitPrice * i.Quantity);
    }

    public void ApplyDiscount(Order order, decimal percent)
    {
        if (percent is < 0 or > 100) throw new Exception("Invalid discount.");
        order.Total = order.Total * (1 - percent / 100m);
    }

    public void Confirm(Order order)
    {
        if (!order.Items.Any()) throw new Exception("Order must have items.");
        _inventory.Reserve(order.Items.Select(i => (i.ProductId, i.Quantity)));
        order.Status = "Confirmed";
    }
}
```

تصویر ذهنی:
- سفارش یا Order یک ظرف داده است؛ هیچ قانونی در خودش ندارد.
- درواقع  Application Service نقش “مغز” را بازی می‌کند و همه‌چیز را کنترل می‌کند.

مزایا:
- شروع کار ساده‌تر، سرعت توسعه ابتدایی بیشتر.
- مناسب وقتی دامنه بسیار ساده یا کوتاه‌عمر است.

معایب:
- قوانین پراکنده و سخت‌تر برای نگهداری.
- احتمال نقض قوانین چون هر سرویس می‌تواند داده‌ها را دستکاری کند.
- تست‌ها شکننده‌تر، تغییرات پرهزینه‌تر.


مقایسه شهودی

- طارحی Domain Model: مثل تیمی که قواعد بازی را داخل زمین و توسط بازیکنان اجرا می‌کند (بازیکن‌ها بلدند چه کنند).
- طراحی Anemic Model: مثل تیمی که بازیکنان فقط می‌دوند و مربی از کنار زمین هر حرکت را فریاد می‌زند؛ اگر مربی نباشد، تیم فلج می‌شود.

کی انتخاب کنیم؟

- اگر دامنه پیچیده، دارای قوانین متداخل، طول عمر زیاد، و نیاز به تکامل دارد → Domain Model.
- اگر دامنه ساده/CRUD محور، کوتاه‌عمر، یا ماژول کم‌اهمیت است → Anemic می‌تواند کفایت کند، ولی مراقب پراکندگی قوانین باش.

نشانه‌های خطر Anemic

- موجودیت‌ها فقط properties و بدون متدهای رفتاری.
- قوانین اعتبارسنجی و محاسبات در Controller یا Serviceها.
- تغییر در یک قانون نیازمند ادیت چندین کلاس خارج از دامنه.
- تکرار منطق در چند جای مختلف.
