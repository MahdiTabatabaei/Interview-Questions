درواقع **Zero Trust Architecture (ZTA)** یک مدل امنیتی است که بر این اصل بنا شده:

> **هیچ کاربر، سرویس یا دستگاهی به صورت پیش‌فرض قابل اعتماد نیست — حتی اگر داخل شبکه باشد.**

در مدل‌های قدیمی امنیت شبکه فرض این بود که:

```
Inside Network = Trusted
Outside Network = Untrusted
```

یعنی اگر کسی داخل شبکه سازمان بود تقریباً به همه چیز دسترسی داشت.

اما در Zero Trust این فرض کاملاً حذف می‌شود.

---

# ایده اصلی Zero Trust

در Zero Trust همیشه این فرض وجود دارد:

```
Never Trust
Always Verify
```

یعنی:

- هر درخواست باید **احراز هویت شود**
- هر درخواست باید **اجازه دسترسی بررسی شود**
- هر درخواست باید **بررسی امنیتی شود**

حتی اگر از داخل همان دیتاسنتر آمده باشد.

---

# مثال ساده

فرض کن در یک سیستم Microservices این سرویس‌ها وجود دارند:

```
API Gateway
OrderService
PaymentService
InventoryService
```

در مدل سنتی اگر OrderService داخل شبکه بود می‌توانست مستقیم PaymentService را صدا بزند.

اما در Zero Trust حتی این ارتباط هم باید بررسی شود.

مثلاً:

```
OrderService → PaymentService
```

قبل از اجرا باید بررسی شود:

- آیا OrderService احراز هویت شده؟
- آیا اجازه دسترسی دارد؟
- آیا درخواست معتبر است؟

---

# اصول اصلی Zero Trust

چند اصل مهم در این معماری وجود دارد.

### 1️⃣ Verify Explicitly

هر درخواست باید بررسی شود بر اساس:

- هویت کاربر
- هویت سرویس
- دستگاه
- موقعیت
- سطح دسترسی

مثال:

```
User Token
Service Identity
Device Trust
```

---

### 2️⃣ Least Privilege Access

هر سرویس یا کاربر فقط **کمترین دسترسی لازم** را دارد.

مثلاً:

```
OrderService
   ✔ create payment
   ❌ delete payment
```

---

### 3️⃣ Assume Breach

فرض می‌شود که ممکن است سیستم compromise شده باشد.

پس:

- مانیتورینگ مداوم
- محدود کردن دسترسی
- و segment کردن شبکه

استفاده می‌شود.

---

# Zero Trust در Microservices

در معماری Microservices این موضوع خیلی مهم می‌شود چون:

```
ده‌ها یا صدها سرویس
ارتباط دائم بین سرویس‌ها
```

بنابراین Zero Trust معمولاً شامل این موارد است:

### Service Authentication

سرویس‌ها باید هویت داشته باشند.

مثلاً با:

```
mTLS
JWT
Service Identity
```

---

### Service Authorization

هر سرویس نمی‌تواند هر سرویس دیگری را صدا بزند.

مثلاً:

```
OrderService → PaymentService ✅
InventoryService → PaymentService ❌
```

---

### Encryption Everywhere

همه ارتباطات رمزنگاری می‌شوند:

```
TLS
mTLS
```

---

# مثال عملی در سیستم Microservices

بدون Zero Trust:

```
OrderService → PaymentService
```

هیچ بررسی خاصی نیست.

---

با Zero Trust:

```
OrderService
   │
   │ mTLS + Service Identity
   │
PaymentService
   │
   └── Policy Check
```

در این حالت PaymentService بررسی می‌کند:

- آیا این سرویس مجاز است؟
- آیا certificate معتبر است؟

---

# ابزارهای رایج برای Zero Trust

در سیستم‌های مدرن این ابزارها استفاده می‌شوند:

**Identity**

- OAuth2
- OpenID Connect
- Keycloak
- Auth0

**Service Authentication**

- mTLS
- SPIFFE / SPIRE

**Service Mesh**

- Istio
- Linkerd

**Policy Enforcement**

- OPA (Open Policy Agent)

---

# مثال واقعی در Kubernetes

در Kubernetes معمولاً Zero Trust با **Service Mesh** پیاده می‌شود.

```
Service A
   │
   │ mTLS
   ▼
Service B
```

و Istio یا Linkerd این کارها را انجام می‌دهند:

- احراز هویت سرویس‌ها
- بررسی authorization policy
- و encryption

---

# تفاوت با مدل امنیتی قدیمی

مدل قدیمی:

```
Firewall
     │
Trusted Network
     │
Everything trusted
```

Zero Trust:

```
User/Service
      │
Authentication
      │
Authorization
      │
Policy Check
      │
Service
```

هر درخواست بررسی می‌شود.

---

# جمع‌بندی

مفهوم Zero Trust Architecture یک مدل امنیتی است که می‌گوید:

- هیچ چیز به صورت پیش‌فرض trusted نیست
- هر درخواست باید احراز هویت شود
- هر درخواست باید authorization شود
- دسترسی‌ها باید حداقل باشند

در سیستم‌های مدرن مخصوصاً:

- Cloud
- Microservices
- Kubernetes

درواقع Zero Trust تبدیل به **استاندارد امنیتی اصلی** شده است.
