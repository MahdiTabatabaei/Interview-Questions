پیام‌هایی که **چند بار Fail می‌شوند** به یک صف مخصوص منتقل می‌شوند.

موارد Fail:

- deserialization error
- validation error
- business rule violation

ایجاد DLQ جلوگیری می‌کند از:

- وضعیت block شدن Queue اصلی
- و retry بی‌نهایت

### مثال C# (MassTransit)
```csharp

cfg.ReceiveEndpoint("orders", e =>
{
    e.BindDeadLetterQueue();
});

```

---

نکته مفهوم **DLQ فقط مخصوص RabbitMQ نیست**.

## تعریف ساده

درواقع **Dead Letter Queue (DLQ)** یعنی صفی برای پیام‌هایی که **نتوانسته‌اند به‌درستی پردازش شوند**.

مثلاً وقتی:
- چند بار مصرف شدند ولی fail شدند
- پیام expire شدند
- یا reject شدند
- و یا queue پر شده و policy اجازه نگهداری نداده

این پیام‌ها به‌جای گم‌شدن، به یک صف دیگر فرستاده می‌شوند تا بعداً بررسی شوند.

---

# آیا فقط در RabbitMQ وجود دارد؟

خیر. این مفهوم در خیلی از Message Brokerها هست، فقط اسم یا پیاده‌سازی‌اش فرق می‌کند:

- **RabbitMQ** → Dead Letter Exchange / Dead Letter Queue
- **Azure Service Bus** → Dead-letter subqueue
- **AWS SQS** → DLQ
- **Kafka** → معمولاً با الگوی application-level topic پیاده می‌شود
- **ActiveMQ** → DLQ دارد

پس:
> مفهوم **DLQ یک concept معماری/پیام‌رسانی است، نه ویژگی انحصاری RabbitMQ.**

---

# در RabbitMQ آیا خودکار ساخته می‌شود؟

معمولاً **نه، خودکار به آن شکلی که “همه‌چیز آماده باشد” ساخته نمی‌شود**.  
معمولاً **برنامه‌نویس / DevOps باید آن را تعریف کند**.

در RabbitMQ معمولاً این چیزها را باید مشخص کنی:

1. یک **Exchange** برای dead letter
2. یک **Queue** به‌عنوان DLQ
3. روی صف اصلی تنظیم کنی که اگر پیام dead-letter شد، به کدام exchange برود

یعنی باید configuration داشته باشی.

---

# در RabbitMQ پیام چطور به DLQ می‌رود؟

در RabbitMQ پیام در چند حالت می‌تواند dead-letter شود. مهم‌ترین‌ها:

## 1) پیام reject یا nack شود و requeue=false باشد

اگر consumer بگوید:

- این پیام را نمی‌خواهم
- دوباره هم به صف اصلی برنگردد

ابزار RabbitMQ آن را dead-letter می‌کند.

---

## 2) زمان TTL پیام تمام شود

اگر برای پیام یا صف زمان انقضا تعریف شده باشد و زمانش بگذرد،  
پیام به DLQ می‌رود.

---

## 3) ظرفیت Queue length limit رد شود

اگر ظرفیت صف محدود باشد و پیام‌ها جا نشوند،  
پیام ممکن است dead-letter شود.

---

## 4) سناریو Quorum queue delivery-limit

در بعضی سناریوها اگر تعداد دفعات تحویل از حدی بگذرد، dead-letter می‌شود.

---

# روند کلی با مثال ذهنی

فرض کن این را داریم:

- صف اصلی: `order.created.queue`
- صف DLQ: `order.created.dlq`
- و Exchange اصلی: `order.exchange`
- و Dead letter exchange: `order.dlx`

## جریان:

1. پیام وارد `order.created.queue` می‌شود
2. مصرف کننده consumer آن را مصرف می‌کند
3. پردازش fail می‌شود
4. مصرف کننده consumer پیام را `nack` می‌کند با `requeue=false`
5. ابزار RabbitMQ پیام را به `order.dlx` می‌فرستد
6. و `order.dlx` پیام را route می‌کند به `order.created.dlq`

---

# مثال پیکربندی RabbitMQ

## تعریف DLX و DLQ

مثال با مفهوم AMQP:

- Exchange اصلی: `order.exchange`
- Queue اصلی: `order.created.queue`
- DLX: `order.dlx`
- DLQ: `order.created.dlq`

### صف اصلی باید این argument را داشته باشد:

```text
x-dead-letter-exchange = order.dlx
x-dead-letter-routing-key = order.created.dead
```

یعنی هر پیامی که dead-letter شد، برود به این exchange و routing key.

---

## مثال ساختار منطقی

```text
Producer
   ↓
order.exchange
   ↓
order.created.queue
   ↓
Consumer fail + nack(requeue=false)
   ↓
order.dlx
   ↓
order.created.dlq
```

---

# مثال C# ذهنی/نمونه

اگر با .NET و RabbitMQ.Client کار کنی، ایده‌اش شبیه این است:

```csharp
var factory = new ConnectionFactory() { HostName = "localhost" };
using var connection = factory.CreateConnection();
using var channel = connection.CreateModel();

// DLX
channel.ExchangeDeclare("order.dlx", ExchangeType.Direct, durable: true);

// DLQ
channel.QueueDeclare("order.created.dlq", durable: true, exclusive: false, autoDelete: false);
channel.QueueBind("order.created.dlq", "order.dlx", "order.created.dead");

// Main Exchange
channel.ExchangeDeclare("order.exchange", ExchangeType.Direct, durable: true);

// Main Queue with DLX config
var args = new Dictionary<string, object>
{
    { "x-dead-letter-exchange", "order.dlx" },
    { "x-dead-letter-routing-key", "order.created.dead" }
};

channel.QueueDeclare(
    queue: "order.created.queue",
    durable: true,
    exclusive: false,
    autoDelete: false,
    arguments: args
);

channel.QueueBind("order.created.queue", "order.exchange", "order.created");
```

---

# مثال مصرف‌کننده که پیام را به DLQ می‌فرستد

```csharp
var consumer = new EventingBasicConsumer(channel);

consumer.Received += (model, ea) =>
{
    try
    {
        var body = ea.Body.ToArray();
        var message = Encoding.UTF8.GetString(body);

        // شبیه‌سازی خطا
        throw new Exception("پردازش ناموفق بود");
        
        // اگر موفق بود:
        // channel.BasicAck(ea.DeliveryTag, multiple: false);
    }
    catch
    {
        // پیام را reject می‌کنیم و نمی‌گذاریم به صف اصلی برگردد
        channel.BasicNack(ea.DeliveryTag, multiple: false, requeue: false);
    }
};

channel.BasicConsume(queue: "order.created.queue", autoAck: false, consumer: consumer);
```

### چه می‌شود؟
چون:
```csharp
requeue: false
```

و چون صف اصلی `x-dead-letter-exchange` دارد،  
ابزار RabbitMQ پیام را می‌برد به `order.created.dlq`.

---

# آیا همیشه باید مستقیم به DLQ برود؟

نه، معمولاً قبل از DLQ چند الگو داریم:

## حالت رایج بهتر:

- بار اول fail → retry
- بار دوم fail → retry
- بار سوم fail → DLQ

یعنی DLQ معمولاً برای خطاهای نهایی است، نه هر خطای موقت.

این retry می‌تواند:
- در خود consumer باشد
- با delayed retry queue باشد
- با policy انجام شود

---

# فرق Retry Queue با DLQ

این‌ها را قاطی نکن:

## Retry Queue
برای تلاش مجدد

## DLQ
برای پیام‌هایی که دیگر پردازش عادی‌شان شکست خورده و باید جدا بررسی شوند

---

# آیا DLQ یعنی پیام خراب است؟

نه لزوماً.  
ممکن است مشکل از این‌ها باشد:

- باگ در consumer
- وابستگی ها dependency down
- داشتن payload نامعتبر
- بخطر version mismatch
- رخداد timeout
- وجود business rule conflict

پس DLQ جایی برای:

- تحلیل
- مشاهده alert
- باز پردازش reprocess
- لاگ audit

است.

---

# در عمل بعد از رفتن به DLQ چه می‌کنیم؟

معمولاً یکی از این کارها:

- لاگ و مانیتور می‌کنیم
- پیام alert می‌فرستیم
- مقدار payload را بررسی می‌کنیم
- ابزار re-drive / replay می‌سازیم
- بعد از fix شدن مشکل دوباره publish می‌کنیم

---

# خلاصه پاسخ سوالت

## 1) آیا DLQ فقط در RabbitMQ هست؟

**نه**، یک مفهوم عمومی در messaging systems است.

## 2) آیا خودکار ساخته می‌شود؟

**معمولاً نه**، در RabbitMQ باید توسط برنامه‌نویس یا DevOps تعریف و config شود.

## 3) پیام چطور به DLQ می‌رود؟

معمولاً وقتی:
- وضعیت پیام `reject/nack` شود و `requeue=false`
- زمان TTL تمام شود
- صف overflow شود
- و delivery limit رد شود

ابزار RabbitMQ آن را به **Dead Letter Exchange** می‌فرستد و از آنجا به **DLQ** route می‌کند.

----


در دو حالت میتوان ساختار DLQ را تعیین کرد ، ولی **رایج‌ترین و بهتر در بیشتر پروژه‌ها** اینه که **برنامه‌نویس / تیم سرویس** آن را به‌صورت **declaration/config در خود اپلیکیشن** تعریف کند؛
و **تیم زیرساخت** فقط RabbitMQ را بالا بیاورد، مانیتور کند، policyهای کلی بدهد، و دسترسی‌ها را تنظیم کند.

## خلاصه کوتاه
ساختار DLQ را می‌شود از دو جا مشخص کرد:

1. **در کد یا config اپلیکیشن**
   - هنگام ساخت queue/exchange
   - با آرگومان‌هایی مثل:
     - `x-dead-letter-exchange`
     - `x-dead-letter-routing-key`

2. **در خود RabbitMQ**
   - با **Policy**
   - یا گاهی با تعریف دستی queue/exchange در پنل management / IaC

---

# تفاوت این دو رویکرد

## 1) تعریف DLQ در کد اپلیکیشن

مثلاً برنامه‌نویس وقتی صف اصلی را declare می‌کند، می‌گوید:

- اگر پیام reject شد
- یا TTL تمام شد
- یا شرایط dead-letter پیش آمد

بفرستش به فلان exchange/queue

### مزیت‌ها

- کنار کد سرویس است و واضح‌تر است
- قابل version-controlled است
- روی هر environment راحت reproducible است
- برای میکروسرویس‌ها خیلی متداول است

### عیب
- اگر تیم زیرساخت بخواهد بدون تغییر کد policy را عوض کند، کمتر منعطف است
- میزان coupling بین اپ و [[Topology]] بیشتر می‌شود

---

## 2) تعریف DLQ در خود RabbitMQ با Policy

ابزار RabbitMQ اجازه می‌دهد روی queueها policy بگذاری، مثلاً:

- هر queue با الگوی خاص
- و dead-letter به فلان exchange شود

### مزیت‌ها
- بدون تغییر کد می‌توان رفتار را عوض کرد
- برای عملیات production و governance خوب است
- تیم platform/ops کنترل بیشتری دارد

### عیب
- ساختار topology از داخل کد معلوم نیست
- دیباگ سخت‌تر می‌شود اگر devها به policyها دسترسی نداشته باشند
- ممکن است بین dev/staging/prod تفاوت ناخواسته پیش بیاید

---

# پس مسئولش کیه؟
## از نظر فنی:

**هر کسی که topology را مدیریت می‌کند** می‌تواند DLQ را تعریف کند.

## از نظر عملی در پروژه‌ها:
### معمولاً یکی از این مدل‌هاست:

#### مدل A — تیم سرویس تعریف می‌کند

خیلی رایج در میکروسرویس‌ها  
اپلیکیشن خودش:
- مقدار exchange
- تعریف queue
- نوع binding
- و DLQ
را declare می‌کند.

#### مدل B — تیم زیرساخت/پلتفرم تعریف می‌کند

بیشتر در سازمان‌های بزرگ  
ابزار RabbitMQ topology با:
- policy
- helm chart
- terraform
- definitions.json
- management setup

مدیریت می‌شود.

#### مدل C — مدل ترکیبی

رایج‌ترین مدل حرفه‌ای:
- **اپلیکیشن** queue/exchangeهای خودش را می‌شناسد
- **زیرساخت** policyهای سراسری مثل TTL، limits، HA، monitoring را مدیریت می‌کند

---

# مثال از تعریف در کد
در declare صف اصلی، این آرگومان‌ها داده می‌شود:

```csharp
var args = new Dictionary<string, object>
{
    ["x-dead-letter-exchange"] = "orders.dlx",
    ["x-dead-letter-routing-key"] = "orders.failed"

channel.QueueDeclare(
    queue: "orders.main",
    durable: true,

    autoDelete: false,

```

و بعد queue مربوط به DLQ هم bind می‌شود.

# مثال از دید مفهومی در RabbitMQ Policy

مثلاً تیم ops می‌گوید:

- هر queue که اسمش `orders.*` است
- مقدار dead-letter exchange آن بشود `orders.dlx`

این دیگر لازم نیست داخل کد باشد.
