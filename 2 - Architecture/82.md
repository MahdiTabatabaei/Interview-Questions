مفهوم  **API Rate Limiting** یعنی محدود کردن تعداد درخواست‌هایی که یک کلاینت می‌تواند در یک بازه زمانی به API بفرستد. هدف آن:

- جلوگیری از **DoS / Abuse**
- کنترل **مصرف منابع**
- حفظ **پایداری سیستم**

مثال ساده:

```
100 request / minute per user
```

اگر بیشتر شود:

```
HTTP 429 Too Many Requests
```

---

# روش‌های اصلی پیاده‌سازی Rate Limiting

چند الگوریتم استاندارد برای این کار وجود دارد.

## 1. Fixed Window

در این روش یک بازه زمانی ثابت تعریف می‌شود.

مثال:

```
100 request per minute
```

پیاده‌سازی:

```
minute 1 → counter = 100
minute 2 → reset
```

مثال:

```
12:00:00 - 12:00:59
```

اگر کاربر 100 درخواست بفرستد، درخواست 101 رد می‌شود.

مزیت:
- ساده

مشکل:
- **Burst problem**

مثال:

```
99 request at 12:00:59
99 request at 12:01:01
```

تقریباً 200 درخواست در 2 ثانیه.

---

## 2. Sliding Window

در این روش به جای بازه ثابت، یک پنجره متحرک استفاده می‌شود.

مثال:

```
100 request per 60 seconds
```

سیستم همیشه **60 ثانیه آخر** را بررسی می‌کند.

مزیت:

- دقیق‌تر
- میزان burst کمتر

عیب:

- محاسبات بیشتر

---

## 3. Token Bucket

یکی از رایج‌ترین الگوریتم‌ها.

ایده:

یک bucket داریم که توکن‌ها داخل آن ریخته می‌شود.

```
bucket capacity = 100
refill rate = 10 token/sec
```

هر درخواست:

```
consume 1 token
```

اگر توکن نبود:

```
request rejected
```

مزیت:

- اجازه burst کوتاه
- کنترل نرخ

---

## 4. Leaky Bucket

ایده شبیه یک سطل سوراخ‌دار است.

درخواست‌ها وارد صف می‌شوند:

```
Incoming requests → Queue → Process at fixed rate
```

مثال:

```
10 request/sec
```

مزیت:

- ترافیک صاف (smooth)

---

# محل پیاده‌سازی Rate Limiting

درواقع Rate Limiting می‌تواند در چند لایه انجام شود.

## 1. API Gateway (رایج‌ترین)

مثال:

```
Client
   ↓
API Gateway (Rate Limit)
   ↓
Microservices
```

ابزارها:

- Kong
- NGINX
- Envoy
- AWS API Gateway
- Azure API Management

---

## 2. داخل خود API

مثلاً در ASP.NET Core.

نمونه:

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.AddFixedWindowLimiter("api", opt =>
    {
        opt.PermitLimit = 100;
        opt.Window = TimeSpan.FromMinutes(1);
    });
});
```

---

## 3. Distributed Rate Limiting

در Microservices چون چند instance داریم:

```
API Instance 1
API Instance 2
API Instance 3
```

در این حالت counter باید **مشترک** باشد.

بنابراین از:

```
Redis
Memcached
Distributed Cache
```

استفاده می‌شود.

معماری:

```
Client
   ↓
API
   ↓
Redis (rate limit counter)
```

---

# مثال عملی با Redis

کلید:

```
rate_limit:user123
```

الگوریتم:

```
INCR key
EXPIRE key 60
```

اگر مقدار > limit:

```
reject request
```

✅ **جمع‌بندی**

تعریف API Rate Limiting برای کنترل تعداد درخواست‌ها استفاده می‌شود.

الگوریتم‌های رایج:

- Fixed Window
- Sliding Window
- Token Bucket
- Leaky Bucket

-----

در معماری **Microservices** معمولاً Rate Limiting را در **API Gateway** پیاده می‌کنند و برای نگه‌داشتن شمارنده‌ها از **Redis** استفاده می‌شود. دلیلش این است که در سیستم‌های توزیع‌شده چندین instance از API وجود دارد و همه باید یک شمارنده مشترک داشته باشند.

## معماری کلی

```
Client
   ↓
API Gateway
   ↓
Redis (Rate Limit Counter)
   ↓
Microservices
```

جریان درخواست:

1. کاربر درخواست را به API Gateway می‌فرستد.
2. و Gateway قبل از ارسال درخواست به سرویس‌ها، Redis را چک می‌کند.
3. در Redis شمارنده مربوط به آن کاربر یا IP را افزایش می‌دهد.
4. اگر از limit بیشتر شود → درخواست رد می‌شود.
5. اگر کمتر باشد → درخواست به microservice ارسال می‌شود.

---

# ابزار Redis چطور شمارنده را مدیریت می‌کند؟

فرض کنیم limit این است:

```
100 request per minute per user
```

کلید Redis معمولاً چیزی شبیه این است:

```
rate_limit:user123
```

---

# مرحله 1: افزایش شمارنده

وقتی درخواست می‌آید Gateway دستور زیر را به Redis می‌زند:

```
INCR rate_limit:user123
```

درواقع Redis مقدار را **۱ واحد افزایش می‌دهد**.

مثال:

```
request 1 → counter = 1
request 2 → counter = 2
request 3 → counter = 3
```

اگر مقدار:

```
> 100
```

شود Gateway پاسخ می‌دهد:

```
429 Too Many Requests
```

---

# مرحله 2: تنظیم زمان انقضا (Reset Window)

وقتی کلید برای اولین بار ساخته می‌شود، یک TTL برای آن می‌گذارند:

```
EXPIRE rate_limit:user123 60
```

یعنی:

```
این شمارنده بعد از 60 ثانیه حذف شود
```

پس چرخه اینطوری می‌شود:

```
t = 0   request → counter=1 → TTL=60
t = 10  request → counter=2
t = 20  request → counter=3
...
t = 60  key deleted
```

بعد از حذف:

```
request → counter=1 (window جدید)
```

---

# نکته مهم: Redis خودش شمارنده را کم نمی‌کند

سؤال مهمی که پرسیدی:

> Redis چه زمانی شمارنده را کم می‌کند؟

در مدل **Fixed Window**:

Redis **هیچ وقت decrement نمی‌کند**.

به جای کم کردن:

```
کلید expire می‌شود
```

و دوباره از صفر شروع می‌شود.

پس روند:

```
0 → 1 → 2 → 3 → ... → 100
بعد از 60 ثانیه
delete key
دوباره → 1
```

---

# چرا Redis برای این کار عالی است؟

چند دلیل مهم:

### 1️⃣ عملیات atomic

دستور `INCR` در Redis **atomic** است.

یعنی اگر 1000 درخواست همزمان برسد:

```
counter دقیق می‌ماند
```

مشکل race condition نداریم.

---

### 2️⃣ سرعت بسیار بالا

Redis در حافظه است:

```
latency ≈ زیر 1ms
```

برای Gateway بسیار مناسب است.

---

### 3️⃣ shared بین همه instanceها

فرض کن:

```
API Gateway Instance 1
API Gateway Instance 2
API Gateway Instance 3
```

همه به یک Redis وصل هستند:

```
counter مشترک
```

پس limit واقعی enforce می‌شود.

---

# مثال واقعی جریان درخواست

limit:

```
100 req/min
```

کاربر `user123`.

درخواست‌ها:

```
request 1 → INCR → 1 → allow
request 2 → INCR → 2 → allow
...
request 100 → INCR → 100 → allow
request 101 → INCR → 101 → reject (429)
```

بعد از 60 ثانیه:

```
key expired
```

و دوباره:

```
counter = 1
```

# مشکل Fixed Window

این الگوریتم مشکل **burst** دارد.

مثال:

```
59.9 sec → 100 request
60.1 sec → 100 request
```

در 0.2 ثانیه:

```
200 request
```

به همین دلیل در سیستم‌های پیشرفته از:

- **Sliding Window**
- **Token Bucket**

استفاده می‌شود.
