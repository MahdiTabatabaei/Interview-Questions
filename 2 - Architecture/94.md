### Vertical

افزایش منابع یک سرور
```markdown

RAM ↑
CPU ↑

```
### Horizontal

افزودن سرورهای بیشتر
```markdown

node1
node2
node3

```

سیستم Cloud systems ترجیح می‌دهند Horizontal.

----

در معماری نرم‌افزار، **Vertical Scaling** و **Horizontal Scaling** دو رویکرد مهم برای افزایش ظرفیت سیستم هستند.  
در ادامه هر کدام را با مثال‌های ساده و همچنین مثال‌های واقعی در **.NET / C#** توضیح می‌دهم.

---

# 1) مفهوم Vertical Scaling (مقیاس‌پذیری عمودی)

به آن **Scale Up** هم می‌گویند.

یعنی:

- افزایش قدرت **یک سرور**
- با اضافه کردن CPU، RAM، Disk بهتر

در این مدل شما **همان ماشین** را قوی‌تر می‌کنید.

مثال ساده:
- یک ماشین دارید با ۴GB RAM → ارتقا به ۱۶GB
- پردازنده CPU تک‌هسته → ارتقا به ۸ هسته

### نتیجه
برنامهٔ شما همان است، فقط روی ماشینی با منابع بیشتر اجرا می‌شود.

### مثال در دنیای .NET / C#

فرض کن یک API در ASP.NET Core نوشته‌ای و روی IIS یا Kestrel اجرا شده.

روش Vertical scaling در این حالت به این شکل است:

- ارتقای Plan در Azure App Service
- افزایش تعداد worker CPU
- افزایش RAM
- استفاده از SSD پرسرعت
- افزایش Thread pool برای پردازش بیشتر

کدی لازم نیست تغییر کند.

---

# 2) مفهوم Horizontal Scaling (مقیاس‌پذیری افقی)

به آن **Scale Out** هم می‌گویند.

یعنی:
- اضافه کردن **ماشین‌های جدید**
- اجرای چند نسخه از برنامه در چند سرور متفاوت
- توزیع بار بین سرورها توسط Load Balancer

مثال ساده:
```
Instead of 1 powerful server → 4 normal servers
```

### نتایج:

- رفتار توزیعی
- دسترس‌پذیری بالا (high availability)
- امکان افزایش ظرفیت با اضافه کردن node جدید

---

# تفاوت اصلی

| نوع | توضیح | مزایا | معایب |
|-----|-------|--------|---------|
| Vertical | قوی‌تر کردن یک سرور | ساده، بدون تغییر کد | محدودیت فیزیکی، ممکن است گران باشد |
| Horizontal | اضافه کردن چند سرور | مقیاس‌پذیری زیاد، High availability | نیازمند معماری توزیع‌شده |

---

# مثال عملی Horizontal Scaling در C#

فرض کن یک API داریم:

```csharp
app.MapGet("/hello", () => "Hello World!");
```

### برای Scale Out (افقی):

#### 1. چند instance از این API روی چند سرور اجرا می‌کنی
- Server1 → instance 1
- Server2 → instance 2
- Server3 → instance 3

یا در Docker:

```bash
docker-compose up --scale web=3
```

یعنی ۳ کانتینر از سرویس ویب اجرا می‌شود.

#### 2. یک Load Balancer جلو می‌گذاری:
- Nginx
- HAProxy
- Azure Load Balancer
- AWS ALB

### رفتار:
در این حالت Load balancer درخواست‌ها را بین instanceها تقسیم می‌کند (Round-robin، Least connections، ...).

#### 3. حواست باید به موارد زیر باشد:

- داده های Session state نباید در memory local ذخیره شود → استفاده از Redis
- فایل‌ها نباید local باشند → استفاده از Blob storage
- استفاده از cache نباید local باشد → distributed cache
- پیام‌رسانی → استفاده از Kafka/RabbitMQ برای async work

---

# مثال کد برای Distributed Cache در .NET (ضروری برای Horizontal Scaling)

این کد باعث می‌شود Session و Cache بین سرورها هماهنگ بماند:

```csharp
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = "localhost:6379";
});
```

در Horizontal Scaling، اگر Session یا Cache روی یک سرور باشد و درخواست بعدی به سرور دیگر برود → مشکل ایجاد می‌شود.

# مثال ساده Vertical vs Horizontal با #C

### Vertical example (افزایش منابع)
بدون تغییر کد:

- سرور از 2 core → 16 core
- میزان RAM از 4GB → 32GB

درواقع API همان است.

---

### Horizontal example (افزایش سرورها)

```bash
docker run -p 8081:80 myapi
docker run -p 8082:80 myapi
docker run -p 8083:80 myapi
```

بعد:

```
LoadBalancer → 
   http://server1:8081
   http://server2:8082
   http://server3:8083
```

درخواست‌ها بین این‌ها پخش می‌شود.

# جمع‌بندی نهایی

### Vertical Scaling  
افزایش قدرت **یک ماشین**  
ساده ولی محدود

### Horizontal Scaling  
افزودن **ماشین‌های بیشتر**  
پیچیده‌تر ولی Scalability و Availability بسیار بالاتر
