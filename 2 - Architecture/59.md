اختلاف ساعت بین سرورها.

مشکل:

- پیام با زمان اشتباه پردازش می‌شود
- ترتیب Sequence بهم می‌ریزد
- تنظیم TTLها خراب می‌شوند

راه‌حل:

- NTP
- Logical Clock (Lamport Clock)
- Vector Clock
---


مفهوم **Clock Skew** یا همان **اختلاف زمانی بین نودها** یکی از چالش‌های کلاسیک و ظریف در طراحی **سیستم‌های توزیع‌شده (Distributed Systems)** است.  
برای درک درستش باید بفهمیم که چرا «زمان» در یک سیستم چند‌نودی، مفهوم ساده و مطمئنی نیست.

---

## 🕰️ تعریف ساده

مفهوم **Clock Skew** (کلاک اِسکیو) یعنی زمانی که ساعت (Clock) دو سرور با هم هماهنگ نیستند،  
و در نتیجه دو رویداد که در دنیای واقعی به‌ترتیب A→B اتفاق افتاده‌اند،  
ممکن است سیستم **برعکس آن را گزارش کند (B→A)** چون ساعت‌ها اختلاف دارند.

به‌بیان دیگر:

> در سیستم‌های توزیع‌شده، هیچ دو ماشینی ساعت کاملاً هم‌زمان ندارند.  
> اختلاف بین آنها را **Clock Skew (اختلاف ساعت)** و تغییر تدریجی آن را **Clock Drift (کلاک دریفت -لغزش ساعت)** می‌نامیم.

---

## 🧩 تفاوت دو اصطلاح مرتبط

| اصطلاح | تعریف |
|--------|--------|
| **Clock Drift** | نرخ حرکت ساعت در هر ماشین کمی متفاوت است (یکی سریع‌تر، دیگری آهسته‌تر جلو می‌رود). با گذر زمان، اختلاف زیاد می‌شود. |
| **Clock Skew** | مقدار اختلاف فعلی بین ساعت دو ماشین (مثلاً Node A جلوتر از Node B به اندازه 200ms). |

🔹 درواقع Drift باعث Skew می‌شود.  
همان‌طور که تایر باد نابرابر باعث انحراف خودرو می‌شود 😅

---

## ⚙️ مثال ساده برای درک مشکل  

فرض کنید دو سرور داریم:

```
Server A time = 10:00:05.000
Server B time = 10:00:04.500
```

سرور B حدود 500 میلی‌ثانیه عقب‌تر است.

رویدادها:
1. A → "کاربر X سفارش ثبت کرد" در `10:00:05.010`
2. B → "پرداخت کاربر X انجام شد" در `10:00:04.800`

در دنیای واقعی، سفارش -> پرداخت بوده است.  
اما چون ساعت B عقب است، در لاگ‌ها به‌صورت برعکس دیده می‌شود:  
«پرداخت قبل از سفارش!»

## 🔥 چرا Clock Skew خطرناک است؟

در سیستم‌های توزیع‌شده، زمان در تصمیم‌گیری‌ها نقش مهمی دارد: 

مثل **ترتیب‌رویدادها، TTL پیام‌ها، Cache Expiration، Commit ordering، Replication، Concurrency resolution** و …

هر جا که زمان بخشی از منطق باشد، اختلاف ساعت باعث خطاهای منطقی می‌شود.

### نمونه‌های واقعی:
| حوزه | اثر Clock Skew |
|------|----------------|
| **Audit / Logs** | ترتیب نادرست رویدادها، دیباگ سخت |
| **Message Queue (مثلاً RabbitMQ)** | انقضا (TTL) نادرست، پیام زودتر یا دیرتر حذف شود |
| **Database Cluster (Replication)** | نسخهٔ جدیدتر با زمان کمتر، جای نسخه قدیمی را بگیرد |
| **Cache / Token Expiration** | توکن‌ها در یک نود معتبر، در نود دیگر منقضی دیده شوند |
| **Conflict Resolution (Last Write Wins)** | نوشتن قدیمی‌تر ممکن است تغییر جدید را بازنویسی کند |

## 🪄 درک ریاضی و نظری — Ordering Problem

در سیستم‌های توزیع‌شده، **ordering واقعی بین رویدادها (A happened before B)**  
را فقط با **زمان محلی** نمی‌توان تعیین کرد، چون:

> شبکه ممکن است تأخیر داشته باشد، و ساعت‌ها هم دقیق نباشند.

بنابراین **تکیه بر زمان واقعی (wall-clock time)** ناامن است.

اینجا مفاهیمی مثل **Logical Clocks** وارد می‌شوند.

---

## 🧮 راهکارهای مطرح‌شده در سیستم‌های توزیع‌شده

| راهکار                                  | توضیح                                                                                                                               |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **NTP (Network Time Protocol)**         | همگام‌سازی دوره‌ای ساعت سرورها با یک مبدا (مثل time.google.com). معمولاً خطای آن چند میلی‌ثانیه تا چندصد میلی‌ثانیه است.            |
| **Atomic Clocks / GPS time**            | برای سیستم‌های حساس (مثل دیتاسنترهای بانکی یا بورس). هزینه بالا.                                                                    |
| **Logical Clocks (Lamport Timestamps)** | زمان را حذف می‌کند و فقط ترتیب علیتی (happens-before) را دنبال می‌کند. هر رویداد یک مقدار منطقی می‌گیرد که صرفاً جهت مرتب‌سازی است. |
| **Vector Clocks**                       | نسخهٔ توسعه‌یافتهٔ Lamport برای کشف هم‌زمانی (Concurrency / Conflict Detection).                                                    |
| **Hybrid Logical Clock (HLC)**          | ترکیبی از زمان واقعی و Logical ordering — در دیتابیس‌هایی مثل CockroachDB برای حفظ ترتیب قابل‌اعتماد استفاده می‌شود.                |
| **TrueTime API (Google Spanner)**       | سرویسی برای ارائهٔ بازهٔ زمانی \([earliest, latest]\) با اطمینان از حداکثر Skew.                                                    |
|                                         | درواقع Spanner می‌گوید: «قبل از commit، چند میلی‌ثانیه صبر می‌کنم تا مطمئن شوم هیچ Skew باعث خطا نمی‌شود.»                          |

## 📉 سناریوی واقعی در پایگاه داده‌ها

### مثال: دو نود دیتابیس با Last-Write-Wins
- Node A زمان را می‌زند: `t = 100ms`
- Node B عقب است: `t = 95ms`
- اگر B بعد از A بنویسد اما زمانش کمتر دیده شود (`95ms < 100ms`)،
  → سیستم اشتباهاً فکر می‌کند تغییر B قدیمی‌تر است و آن را رد می‌کند.

**نتیجه:** از دست رفتن دادهٔ جدیدتر 😬

## 🛠️ تأثیر آن در معماری‌هایی مثل استک تو

در معماری شامل:
**Kubernetes + ASP.NET Core + RabbitMQ + Elasticsearch**

نمونه‌های محل خطر Clock Skew:

| بخش | اثر احتمالی |
|------|--------------|
| **RabbitMQ TTL / DLQ** | پیام ممکن است زودتر منقضی شود یا دیرتر منتقل شود |
| **ElasticSearch ingestion timestamp** | ترتیب ایندکس ناصحیح یا ترتیب نادرست در جستجوهای زمان‌محور |
| **Microservice logs** | ترتیب نادرست بین سرویس‌ها، دیباگ یا tracing سخت‌تر |
| **Cache expiration (Redis, Memory Cache)** | داده در یک نود منقضی شده ولی دیگری هنوز معتبر می‌بیند |
| **JWT / Token Validation** | «token expired» حتی وقتی از نظر کاربر هنوز معتبر است |

## ⏱️ روش‌های کنترل و کاهش Clock Skew

1. **استفاده از NTP در همه سرورها**
   - در Kubernetes و Cloud معمولاً خودکار انجام می‌شود.
   - اما در محیط‌های [[On-prem]] باید بررسی دوره‌ای انجام شود.
1. **عدم اعتماد به زمان سیستم در منطق تجاری**
   - سعی کن مرتب‌سازی، تاریخ‌گذاری و TTLها را **مرکز‌گرا یا منطقی (logical)** کنی، نه با `DateTime.Now`.
3. **در Log و Trace از Clock سرویس مرکزی (مثل OpenTelemetry time) استفاده کن.**
4. **در تصمیم‌ها "ordering by business logic"** مهم‌تر از ordering زمانی باشد.
5. **در دیتابیس یا سرویس پیام‌رسان، از فیلدهای monotonic sequence** به جای timestamp صرف استفاده کن.
6. **برای الگوهای حساس (مثل Eventual Consistency):**
   - از **Logical Clock یا نسخه SequenceNumber** در پیام‌ها استفاده کن تا ترتیب پردازش تضمین شود.
