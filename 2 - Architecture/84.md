در واقع Service Mesh لایه‌ای برای مدیریت ارتباط بین سرویس‌ها است.

وظایف:

- service discovery
- load balancing
- security
- observability

بدون تغییر کد سرویس‌ها.

### معماری
```markdown

Service A
  ↓
Sidecar Proxy
  ↓
Service Mesh
  ↓
Sidecar Proxy
  ↓
Service B

```
### ابزارها

- Istio
- Linkerd
- Consul
-----

درواقع **Service Mesh** یک لایهٔ زیرساختی برای مدیریت ارتباطات بین سرویس‌ها در معماری **Microservices** است.

وقتی یک سیستم از ده‌ها یا صدها سرویس تشکیل شده باشد، سرویس‌ها دائماً با هم از طریق شبکه (معمولاً HTTP/gRPC) ارتباط دارند. مدیریت این ارتباطات—مثل امنیت، لاگ، ریت‌لیمیت، رتری و مانیتورینگ—اگر داخل هر سرویس نوشته شود، کد بسیار پیچیده می‌شود.  
Service Mesh این مسئولیت‌ها را از داخل سرویس‌ها خارج می‌کند و در یک لایهٔ جدا مدیریت می‌کند.

به زبان ساده:

- **Application logic** داخل سرویس‌ها
- **Network communication logic** داخل Service Mesh

---

## اجزای اصلی Service Mesh

### 1. Data Plane
بخشی که واقعاً ترافیک بین سرویس‌ها را مدیریت می‌کند.

معمولاً با **Sidecar Proxy** پیاده‌سازی می‌شود.  
هر سرویس یک Proxy کنار خودش دارد (مثل **Envoy**).

ساختار معمول:

```
Service A → Proxy A → Proxy B → Service B
```

کارهای Data Plane:

- Load balancing
- Encryption (mTLS)
- Retry / timeout
- Traffic routing
- Metrics collection

---

### 2. Control Plane
بخشی که تنظیمات و قوانین را مدیریت می‌کند.

وظایف:

- مدیریت تنظیمات پروکسی‌ها
- اعمال policyها
- مدیریت امنیت
- مانیتورینگ

---

## مثال واقعی

فرض کنید سه سرویس دارید:

- User Service
- Order Service
- Payment Service

بدون Service Mesh:

```
User Service → Order Service
User Service → Payment Service
Order Service → Payment Service
```

هر سرویس باید خودش مدیریت کند:

- retry
- timeout
- TLS
- logging
- tracing

با Service Mesh:

```
User → Proxy → Proxy → Order
Order → Proxy → Proxy → Payment
```

تمام این قابلیت‌ها توسط **Mesh** مدیریت می‌شود.

---

## قابلیت‌های مهم Service Mesh

### 1. Service-to-Service Security
ارتباط امن با **mTLS**.

### 2. Traffic Management
مثلاً:

- Canary deployment
- Blue/Green deployment
- A/B testing

مثال:

```
90% → v1
10% → v2
```

### 3. Observability
- Metrics
- Distributed tracing
- Logging

### 4. Reliability
- Retry
- Circuit breaker
- Timeout

## مثال ساده در Kubernetes + Istio

اگر دو سرویس داشته باشیم، Istio می‌تواند مشخص کند ترافیک چگونه تقسیم شود:

```
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  http:
  - route:
    - destination:
        host: product-service
        subset: v1
      weight: 90
    - destination:
        host: product-service
        subset: v2
      weight: 10
```

این یعنی:

- 90٪ درخواست‌ها → نسخه v1  
- 10٪ درخواست‌ها → نسخه v2

بدون اینکه کد سرویس تغییر کند.

---

✅ خلاصه:

- **Service Mesh** یک لایه برای مدیریت ارتباط بین microservices است.  
- با استفاده از **sidecar proxies** ارتباطات را کنترل می‌کند.  
- قابلیت‌هایی مثل **security, routing, retry, monitoring** را بدون تغییر کد سرویس فراهم می‌کند.

---

این دو تکنولوژی معمولاً با هم اشتباه گرفته می‌شوند، اما وظایف کاملاً متفاوتی دارند. در واقع، در اکثر معماری‌های مدرن، هر دو در کنار هم استفاده می‌شوند.

### بخش اول: تفاوت API Gateway و Service Mesh

بهترین راه برای درک تفاوت این دو، استفاده از مفهوم **North-South** و **East-West** است.

#### 1. API Gateway (ترافیک North-South)
ترافیک **North-South** یعنی ترافیکی که از خارج از کلاستر (اینترنت/کاربر) وارد سیستم می‌شود.
*   **وظیفه:** مدیریت ورود کاربران، احراز هویت (AuthN/AuthZ)، محدود کردن نرخ درخواست‌ها (Rate Limiting) و مسیریابی به سرویس‌های داخلی.
*   **تمرکز:** روی **Edge** سیستم (لبه شبکه).
*   **مثال:** Kong، Ocelot، Nginx.

#### 2. Service Mesh (ترافیک East-West)
ترافیک **East-West** یعنی ارتباط بین خودِ سرویس‌های داخلی در یک کلاستر.
*   **وظیفه:** مدیریت امنیت بین سرویس‌ها (mTLS)، تاب‌آوری (Retry، Circuit Breaker) و مانیتورینگ ارتباطات داخلی.
*   **تمرکز:** روی **Internal Network** (شبکه داخلی).
*   **مثال:** Istio، Linkerd.

| ویژگی | API Gateway | Service Mesh |
| :--- | :--- | :--- |
| **محل قرارگیری** | لبه سیستم (Edge) | بین سرویس‌ها (Sidecar) |
| **نوع ترافیک** | North-South (خارج به داخل) | East-West (سرویس به سرویس) |
| **وظایف اصلی** | Auth، Billing، API Composition | mTLS، Retry، Observability |
| **مخاطب** | کلاینت‌های خارجی (App/Web) | خودِ میکروسرویس‌ها |

### بخش دوم: معماری Istio (آمادگی برای مصاحبه)

در مصاحبه‌ها، باید بدانید که Istio به دو بخش اصلی تقسیم می‌شود: **Data Plane** و **Control Plane**.

#### 1. Data Plane (صفحه داده)
از مجموعه‌ای از **Sidecar Proxy**ها تشکیل شده است. در Istio، این پروکسی‌ها از تکنولوژی **Envoy** استفاده می‌کنند. 
*   این پروکسی‌ها کنار هر کانتینر سرویس قرار می‌گیرند.
*   تمام ترافیک ورودی و خروجی سرویس از این پروکسی رد می‌شود.

#### 2. Control Plane (صفحه کنترل)
بخش مغز متفکر سیستم است که با نام **Istiod** شناخته می‌شود. وظیفه آن مدیریت و پیکربندی پروکسی‌های Data Plane است.
*   **Pilot:** مسئول مسیریابی و مدیریت ترافیک.
*   **Citadel:** مسئول تولید گواهی‌نامه‌های امنیتی برای mTLS.
*   **Galley:** مسئول اعتبارسنجی تنظیمات (Config).

               │              │             │
               └──────────────┼─────────────┘ (Push Config & Certificates)
                              ▼
   ┌─────────────────────────────────────────────────────────────┐
   │                       DATA PLANE                            │
   │                                                             │
   │   ┌───────────────┐                  ┌───────────────┐      │
   │   │   Service A   │                  │   Service B   │      │
   │   └───────┬───────┘                  └───────┬───────┘      │
   │           ▲                                  ▲              │
   │           │ (Local Traffic)                  │              │
   │           ▼                                  ▼              │
   │   ┌───────────────┐      mTLS        ┌───────────────┐      │
   │   │  Envoy Proxy  │ ◄──────────────► │  Envoy Proxy  │      │
   │   │   (Sidecar)   │      Traffic     │   (Sidecar)   │      │
   │   └───────────────┘                  └───────────────┘      │
   │                                                             │
   └─────────────────────────────────────────────────────────────┘

### خلاصه برای پاسخ در مصاحبه:

1.  **API Gateway** برای مدیریت درخواست‌های ورودی از "بیرون به درون" است (North-South) و وظایفی مثل لاگین کاربر و ریت‌لیمیت را دارد.
2.  **Service Mesh** (مثل Istio) برای مدیریت ارتباط "سرویس به سرویس" است (East-West) تا امنیت داخلی، مانیتورینگ و پایداری شبکه را تامین کند.
3.  در **Istio**، هر سرویس یک پروکسی **Envoy** در کنار خود دارد (Sidecar) که ترافیک را کنترل می‌کند و یک بخش مرکزی به نام **Istiod** تمام این پروکسی‌ها را مدیریت و تنظیم می‌کند.

آیا نیاز هست در مورد یکی از این قابلیت‌ها مثل **mTLS** یا **Circuit Breaker** در Istio بیشتر توضیح بدهم؟
