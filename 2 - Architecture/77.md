تفاوت اصلی لاگ‌گیری در **Monolith** و **Microservices** بیشتر به خاطر **تعداد سرویس‌ها، محل اجرا، و نحوه جمع‌آوری لاگ‌ها** است. در Monolith همه چیز در یک برنامه اتفاق می‌افتد، ولی در Microservices لاگ‌ها بین چندین سرویس پخش می‌شوند.

---

# مفهوم Logging در Monolith

در معماری Monolith معمولاً فقط **یک اپلیکیشن** دارید.

مثلاً:

```
Web App
 ├── Controller
 ├── Service
 └── Repository
```

وقتی درخواست می‌آید:

```
Client → Web App → Database
```

همه لاگ‌ها در همان اپلیکیشن تولید می‌شوند.

مثلاً:

```
[INFO] Request started /orders/12
[INFO] Getting order from DB
[ERROR] Order not found
```

ویژگی‌ها:

- همه لاگ‌ها در **یک process** هستند
- معمولاً در **یک فایل** یا **یک سیستم logging** ذخیره می‌شوند
- فرایند Debug کردن ساده است
- نیاز به correlation خاصی ندارید

ابزارها:

- Serilog
- NLog
- Log4Net
- فایل log ساده

---

# مفهوم Logging در Microservices

در Microservices چندین سرویس مستقل دارید.

مثلاً:

```
API Gateway
OrderService
PaymentService
InventoryService
ShippingService
```

یک درخواست ممکن است این مسیر را طی کند:

```
Client
  ↓
Gateway
  ↓
OrderService
  ↓
PaymentService
  ↓
InventoryService
```

حالا هر سرویس **لاگ خودش را جداگانه تولید می‌کند**.

مثلاً:

Gateway log

```
Request POST /order
TraceId=abc123
```

OrderService log

```
Creating order
TraceId=abc123
```

PaymentService log

```
Charging credit card
TraceId=abc123
```

اگر TraceId نداشته باشید، فهمیدن اینکه این لاگ‌ها مربوط به **یک درخواست واحد** هستند بسیار سخت می‌شود.

---

# مشکل اصلی Logging در Microservices

در Microservices چند چالش وجود دارد:

### 1️⃣ لاگ‌ها پراکنده هستند

لاگ‌ها در چندین سرویس تولید می‌شوند:

```
Gateway logs
Order logs
Payment logs
Inventory logs
```

پس باید **مرکزی جمع شوند**.

---

### 2️⃣ نیاز به Correlation

باید بدانیم کدام لاگ‌ها متعلق به یک درخواست هستند.

برای همین استفاده می‌شود از:

```
CorrelationId
TraceId
RequestId
```

مثال:

```
TraceId = 7fa23d
```

تمام سرویس‌ها همان TraceId را در لاگ می‌نویسند.

---

### 3️⃣ لاگ‌ها در container ها هستند

در Kubernetes یا Docker:

```
service-1 container
service-2 container
service-3 container
```

اگر container restart شود ممکن است لاگ‌ها از بین بروند.

پس معمولاً لاگ‌ها به سیستم مرکزی ارسال می‌شوند.

---

# معماری Logging در Microservices

معمولاً چیزی شبیه این است:

```
Services
   ↓
Structured Logs
   ↓
Log Collector
   ↓
Log Storage
   ↓
Visualization
```

ابزارهای رایج:

```
Serilog
Fluentd
Logstash
Elasticsearch
Kibana
Grafana Loki
```

مثال معروف:

```
Services → Logstash → Elasticsearch → Kibana
```

یا:

```
Services → Promtail → Loki → Grafana
```

# ساختار Structured Logging (خیلی مهم در Microservices)

در Monolith ممکن است این لاگ کافی باشد:

```
User created successfully
```

اما در Microservices بهتر است لاگ **ساختاریافته (structured)** باشد:

مثلاً JSON:

```
{
 "timestamp":"2026-05-17",
 "service":"OrderService",
 "level":"Information",
 "message":"Order created",
 "orderId":123,
 "traceId":"abc123"
}
```

این باعث می‌شود بتوانید در Kibana یا Grafana جستجو کنید:

```
traceId=abc123
```

و همه لاگ‌های یک درخواست را ببینید.

---

# تفاوت کلیدی در یک نگاه

Monolith

- یک اپلیکیشن
- یک منبع لاگ
- فرایند debug ساده
- داشتن correlation معمولاً لازم نیست

Microservices

- چندین سرویس
- لاگ‌های پراکنده
- نیاز به centralized logging
- نیاز به TraceId / CorrelationId
- استفاده از structured logging

---

✅ خلاصه ساده:

Monolith  
→ داشتن Logging ساده، همه چیز در یک برنامه

Microservices  
→ داشتن Logging توزیع‌شده، نیاز به **centralized logging + correlation**

---

مثال ترکیب **Serilog + Elasticsearch + Jaeger** یک استک خیلی رایج برای Observability در Microservices است.  
معمولاً معماری واقعی این شکلی می‌شود:

```
Microservices (.NET)
     │
     ├─ Logs → Serilog → Elasticsearch → Kibana
     │
     └─ Traces → OpenTelemetry → Jaeger
```

یعنی:

- **Serilog** برای تولید و ارسال لاگ‌ها
- **Elasticsearch** برای ذخیره لاگ‌ها
- **Kibana** برای جستجو و مشاهده لاگ‌ها
- **OpenTelemetry + Jaeger** برای Distributed Tracing

حالا یک پیاده‌سازی واقعی در .NET را قدم‌به‌قدم ببینیم.

# 1️⃣ اجرای Elasticsearch + Kibana + Jaeger با Docker

یک `docker-compose.yml` ساده:

```yaml
version: "3.8"

services:

  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.12.0
    container_name: elasticsearch
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
    ports:
      - "9200:9200"

  kibana:
    image: docker.elastic.co/kibana/kibana:8.12.0
    container_name: kibana
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch

  jaeger:
    image: jaegertracing/all-in-one:latest
    container_name: jaeger
    ports:
      - "16686:16686"
      - "4317:4317"
      - "4318:4318"
```

بعد اجرا:

```
Kibana UI
http://localhost:5601

Jaeger UI
http://localhost:16686
```

# 3️⃣ تنظیم Serilog برای Elasticsearch

در `Program.cs`

```csharp
using Serilog;
using Serilog.Sinks.Elasticsearch;

var builder = WebApplication.CreateBuilder(args);

Log.Logger = new LoggerConfiguration()
    .Enrich.FromLogContext()
    .Enrich.WithMachineName()
    .WriteTo.Console()
    .WriteTo.Elasticsearch(new ElasticsearchSinkOptions(new Uri("http://localhost:9200"))
    {
        AutoRegisterTemplate = true,
        IndexFormat = "microservices-logs-{0:yyyy.MM.dd}"
    })
    .CreateLogger();

builder.Host.UseSerilog();
```

این کار باعث می‌شود:

- لاگ در کنسول
- لاگ در Elasticsearch

---

# 4️⃣ فعال کردن OpenTelemetry برای Jaeger

در همان `Program.cs`:

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracer =>
    {
        tracer
            .AddAspNetCoreInstrumentation()
            .AddHttpClientInstrumentation()
            .AddOtlpExporter(options =>
            {
                options.Endpoint = new Uri("http://localhost:4317");
            });
    });
```

این باعث می‌شود:

- هر HTTP request یک span بسازد
- و trace به Jaeger ارسال شود

# 5️⃣ مثال یک endpoint با logging

```csharp
app.MapGet("/order/{id}", (int id, ILogger<Program> logger) =>
{
    logger.LogInformation("Getting order {OrderId}", id);

    if (id == 0)
    {
        logger.LogError("Invalid order id");
        return Results.BadRequest();
    }

    return Results.Ok(new { id, status = "created" });
});
```

ابزار Serilog این لاگ را به صورت structured ذخیره می‌کند.

مثلاً در Elasticsearch:

```
message: "Getting order {OrderId}"
OrderId: 10
level: Information
service: OrderService
timestamp: ...
```

# جمع‌بندی

در این معماری:

### Logs

```
Service → Serilog → Elasticsearch → Kibana
```

### Traces

```
Service → OpenTelemetry → Jaeger
```

### نتیجه

- Kibana → جستجوی لاگ‌ها
- Jaeger → مشاهده مسیر درخواست بین سرویس‌ها

---

خوب، بیایید یک **نسخه نزدیک به Production** از استک Observability با این ابزارها بسازیم:

- **Serilog** → تولید لاگ در سرویس‌ها  
- **Fluent Bit** → جمع‌آوری و ارسال لاگ‌ها  
- **Elasticsearch** → ذخیره لاگ‌ها  
- **Kibana** → مشاهده لاگ‌ها  
- **OpenTelemetry** → تولید Trace  
- **OpenTelemetry Collector** → پردازش Trace  
- **Jaeger** → نمایش Trace  

معماری کلی:

```
.NET Microservices
      │
      ├─ Logs → Serilog → stdout → FluentBit → Elasticsearch → Kibana
      │
      └─ Traces → OpenTelemetry → OTEL Collector → Jaeger
```

نکته مهم:  
در Production معمولاً سرویس‌ها **مستقیم به Elasticsearch لاگ نمی‌فرستند**.  
آنها فقط در **stdout** می‌نویسند و یک log collector (مثل FluentBit) لاگ‌ها را جمع می‌کند.

# 1️⃣ فایل docker-compose برای کل استک

نمونه ساده ولی نزدیک به Production:

```yaml
version: "3.8"

services:

  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.12.0
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
    ports:
      - "9200:9200"

  kibana:
    image: docker.elastic.co/kibana/kibana:8.12.0
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch

  jaeger:
    image: jaegertracing/all-in-one:latest
    ports:
      - "16686:16686"

  otel-collector:
    image: otel/opentelemetry-collector:latest
    volumes:
      - ./otel-config.yaml:/etc/otel/config.yaml
    command: ["--config=/etc/otel/config.yaml"]
    ports:
      - "4317:4317"
    depends_on:
      - jaeger
```

# 2️⃣ تنظیم OpenTelemetry Collector

فایل `otel-config.yaml`

```yaml
receivers:
  otlp:
    protocols:
      grpc:

exporters:
  jaeger:
    endpoint: jaeger:14250
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [jaeger]
```

این یعنی:

```
App → OTLP → Collector → Jaeger
```
