در Microservices آدرس سرویس‌ها ثابت نیست.

مفهوم Service Discovery یعنی:

- هر سرویس خودش را ثبت کند (Register)
- سرویس‌ها بتوانند همدیگر را پیدا کنند (Lookup)

این کار معمولاً با Service Registry انجام می‌شود.

----

مفهوم **Service Discovery** یعنی این‌که سرویس‌ها بدون اینکه آدرس ثابت همدیگر را بدانند، بتوانند **به‌صورت داینامیک همدیگر را پیدا کنند و صدا بزنند**.  

در معماری میکروسرویس چون IP پادها یا سرویس‌ها مدام عوض می‌شود (scale، restart، reschedule)، نگه داشتن آدرس ثابت عملاً ممکن نیست. Service Discovery این مشکل را حل می‌کند.

ایدهٔ ساده:  
به‌جای اینکه سرویس A بداند سرویس B روی `10.3.15.7:5000` است، فقط می‌گوید:  
`http://order-service`  
و سیستم زیرساخت خودش سرویس واقعی را پیدا می‌کند.

---


فرض کنیم این استک را دارید:

- Kubernetes
- Traefik (Ingress)
- Keycloak
- چند Microservice با **ASP.NET Core**

در چنین سیستمی  Service Discovery وجود دارد و معمولاً **خود Kubernetes آن را انجام می‌دهد**.

ابزار Kubernetes با **DNS داخلی + Service objects** این کار را می‌کند.

---

# ساختار معمول

فرض کنید این سرویس‌ها دارید:

- `user-service`
- `order-service`
- `payment-service`
- `keycloak`
- `traefik`

در Kubernetes برای هر کدام یک **Service** تعریف می‌شود.

مثال:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order
  ports:
    - port: 80
      targetPort: 8080
```

ابزار Kubernetes برای آن **DNS داخلی** می‌سازد.

مثلاً:

```
order-service.default.svc.cluster.local
```

# نحوه دسترسی سرویس‌ها به هم

فرض کنیم `user-service` می‌خواهد `order-service` را صدا بزند.

در ASP.NET Core:

```csharp
var response = await httpClient.GetAsync("http://order-service/api/orders");
```

بدون دانستن IP.

در DNS کوبرنتیز پشت صحنه resolve می‌کند:

```
order-service → یکی از Pod های order
```

اگر ۵ پاد داشته باشد:

```
order-service
   ↓
Pod1
Pod2
Pod3
Pod4
Pod5
```

درواقع Kubernetes load balancing هم انجام می‌دهد.

# نقش Traefik

ابزار Traefik برای **ورود ترافیک از بیرون کلاستر** است.

کارش:

```
Internet
   ↓
Traefik
   ↓
microservices
```

مثال:

```
api.example.com/users → user-service
api.example.com/orders → order-service
```

Ingress مثال:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api
spec:
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /orders
        pathType: Prefix
        backend:
          service:
            name: order-service
            port:
              number: 80
```

# نقش Keycloak

ابزار Keycloak معمولاً یک **Service در Kubernetes** است.

مثلاً:

```
keycloak.default.svc.cluster.local
```

میکروسرویس ASP.NET Core برای اعتبارسنجی توکن ممکن است این آدرس را استفاده کند:

```
http://keycloak/realms/myrealm
```

یا از بیرون:

```
https://auth.example.com
```

# دو نوع Service Discovery

## 1️⃣ Client-side discovery
کلاینت خودش سرویس را پیدا می‌کند.

مثال‌ها:
- Netflix Eureka
- Consul

---

## 2️⃣ Server-side discovery
یک لایه واسط سرویس را پیدا می‌کند.

مثال‌ها:
- Kubernetes Service
- Envoy
- Traefik

در **Kubernetes معمولاً server-side discovery است**.

---

# جمع‌بندی در سیستم نمونه

در سیستم:

- Kubernetes
- Traefik
- Keycloak
- ASP.NET Core Microservices

مفهوم Service Discovery این‌گونه انجام می‌شود:

1. هر سرویس یک **Kubernetes Service** دارد.
2. ابزار Kubernetes **DNS داخلی** می‌سازد.
3. سرویس‌ها با **نام سرویس** همدیگر را صدا می‌زنند.
4. ابزار Kubernetes **Load Balancing بین Pod ها** انجام می‌دهد.
5. و Traefik فقط برای **دسترسی خارجی** است.
