مفهوم **Token Introspection** یکی از ویژگی‌های مهم در استاندارد **OAuth 2.0** است.  
این مفهوم دقیقاً برای زمانی طراحی شده که **توکن قابل بررسی محلی (مثل JWT)** نیست یا نیاز داری **وضعیت فعلی توکن را از سرور صادرکننده بپرسی**.

در ادامه به شکلی ساده، دقیق و کاربردی توضیح می‌دهم.

---

# Token Introspection چیست؟

**Token Introspection یعنی:  
یک سرویس (Resource Server / API) از Authorization Server می‌پرسد که این توکن هنوز معتبر است یا نه.**

این کار با یک درخواست HTTP به مسیر استاندارد انجام می‌شود:

```
POST /introspect
```

و توکن را ارسال می‌کنی:

```
token=<access_token>
```

Authorization Server (مثلاً Keycloak، IdentityServer، OAuth Server) پاسخ می‌دهد که:

- توکن فعال است یا نه
- تاریخ انقضا چقدر است
- متعلق به کدام کاربر است
- چه Scopeهایی دارد
- چه Clientی آن را گرفته
- و...

نمونه پاسخ:

```json
{
  "active": true,
  "exp": 1732258392,
  "client_id": "mobile-app",
  "username": "john",
  "scope": "read write",
  "sub": "user-123"
}
```

---

# چرا Token Introspection لازم است؟

برای زمانی که:

## ۱) توکن **JWT نیست**
اگر Access Token از نوع **Opaque Token** باشد (یک رشته تصادفی بدون اطلاعات داخلش):

```
a8a8f3b1a0d2c7514f8a92d...
```

API **نمی‌تواند آن را محلی validate کند**  
پس مجبور است از سرور سؤال بپرسد:

"این توکن معتبره؟"

---

## ۲) می‌خواهی توکن را *Real-time* از کار بیندازی

JWT مشکل معروف دارد:

- تا وقتی expire نشده، معتبر است  
- حتی اگر کاربر logout کند  
- حتی اگر حسابش حذف شود

اما با Introspection:

- می‌توانی توکن را revoke کنی  
- API هر بار از سرور status واقعی را بپرسد

---

## ۳) نیاز به سیاست‌های امنیتی سازمانی داری  
سازمان‌ها گاهی می‌خواهند:

- توکن فقط در یک device کار کند  
- توکن فقط تا زمانی معتبر است که session فعال باشد  
- توکن بسته به risk score مسدود شود

این موارد با JWT قابل انجام نیست  
وقتی API هر بار از سرور status می‌پرسد،  
می‌توانی هر لحظه وضعیت را تغییر بدهی.

---

# نکته مهم: Token Introspection = Stateful  
یعنی:

- هر بار API نیاز دارد از Authorization Server سؤال بپرسد  
- این باعث *Latency* و *Load* روی سرور می‌شود  
- در معماری Microservices معمولاً توصیه نمی‌شود مگر در شرایط خاص

---

# مقایسه JWT vs Introspection

## JWT (Stateless)
API بدون تماس با Keycloak از روی public key:

- signature را چک می‌کند  
- exp را بررسی می‌کند  

❌ اما نمی‌تواند invalidate را فوراً تشخیص دهد.

## Opaque Token + Introspection (Stateful)
API هر بار به Keycloak می‌گوید:

"این توکن هنوز معتبر است؟"

✔ امنیت بالاتر  
✔ امکان revoke real-time  
❌ اعمال بار روی سرور

---

# نقش Token Introspection در Keycloak

Keycloak **هر دو مدل** را پشتیبانی می‌کند:

۱) JWT Access Token (سریع‌تر – بدون تماس با Keycloak)  
۲) Opaque Token + Introspection (امن‌تر – Stateful)

Endpoint introspection در Keycloak:

```
/realms/<realm-name>/protocol/openid-connect/token/introspect
```

# چه زمانی از Introspection استفاده کنیم؟

### ✔ وقتی API ارزش امنیتی بالا دارد
مثلاً:

- تراکنش مالی
- پنل مدیریت حساس
- عملیات خطرناک

### ✔ وقتی توکن باید سریع حذف شود  
logout، block account، rotation

### ✔ وقتی توکن Opaque است  
API نمی‌تواند آن را local validate کند

### ✔ وقتی نیاز به Dynamic Policy داری  
- device binding  
- location-based access  
- risk-based access

### ❌ وقتی microservice زیاد داریم  
بار زیاد به Authorization Server وارد می‌شود  
معمولاً در Microservice Architecture از JWT استفاده می‌شود.

---

# جمع‌بندی ساده

Token Introspection یعنی:

> API از Authorization Server می‌پرسد که  
> «این توکن معتبره یا نه؟ و متعلق به چه کسیه؟»

استفاده می‌شود برای:

- توکن‌های Opaque  
- بررسی real-time وضعیت توکن  
- افزایش امنیت  
- امکان revoke فوری

ولی:

- Stateful است  
- نسبت به JWT کندتر و سنگین‌تر است
