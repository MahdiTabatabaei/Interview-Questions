تفاوت **Symmetric Signing** و **Asymmetric Signing** در نحوه استفاده از **کلیدها برای امضای توکن و اعتبارسنجی آن** است.

---

# 1️⃣ Symmetric Signing (امضای متقارن)

در این روش **یک کلید مشترک (Secret Key)** وجود دارد.

همان کلیدی که برای **امضا کردن (sign)** استفاده می‌شود، برای **اعتبارسنجی (verify)** هم استفاده می‌شود.

### ساختار

```
Identity Server
      |
      |  sign token with SECRET
      v
     JWT
      |
      v
      API
      |
      | verify with SAME SECRET
```

### مثال الگوریتم
```
HS256
HS384
HS512
```

### ویژگی‌ها

- یک **secret مشترک** بین صادرکننده توکن و APIها
- سریع‌تر از asymmetric
- پیاده‌سازی ساده‌تر

### مشکل امنیتی

همه سرویس‌ها باید **secret مشترک** را بدانند.

اگر یکی از سرویس‌ها هک شود:

- attacker به secret دسترسی پیدا می‌کند
- می‌تواند **JWT جعلی بسازد**

بنابراین در سیستم‌های بزرگ خطرناک می‌شود.

---

# 2️⃣ Asymmetric Signing (امضای نامتقارن)

در این روش **دو کلید متفاوت** وجود دارد:

```
Private Key
Public Key
```

### ساختار

```
Identity Server
      |
      | sign with PRIVATE KEY
      v
     JWT
      |
      v
      API
      |
      | verify with PUBLIC KEY
```

### مثال الگوریتم

```
RS256
RS384
RS512
ES256
```

### ویژگی‌ها

- **Private Key** فقط در Identity Server نگه‌داری می‌شود
- **Public Key** در اختیار همه APIها قرار می‌گیرد
- APIها فقط می‌توانند **verify** کنند نه **sign**

---

# چرا این امن‌تر است؟

اگر یک API هک شود:

- فقط **Public Key** لو می‌رود
- با public key **نمی‌توان JWT ساخت**

چون برای ساخت JWT نیاز به **Private Key** است.

---

# مثال واقعی با Keycloak

Keycloak از **RS256 (asymmetric)** استفاده می‌کند.

روند کار:

### 1️⃣ کاربر login می‌کند

Keycloak:

```
sign JWT with private key
```

### 2️⃣ API Gateway یا Microservice

کلید عمومی را از این endpoint می‌گیرد:

```
/realms/{realm}/protocol/openid-connect/certs
```

که به آن **JWKS endpoint** می‌گویند.

### 3️⃣ اعتبارسنجی

API:

- signature را با public key بررسی می‌کند
- exp را بررسی می‌کند
- issuer را بررسی می‌کند

بدون تماس با Keycloak.

---

# مقایسه ساده

| ویژگی | Symmetric | Asymmetric |
|------|-----------|-----------|
| تعداد کلید | 1 | 2 |
| کلید امضا | Secret | Private Key |
| کلید اعتبارسنجی | Secret | Public Key |
| امنیت در سیستم بزرگ | کمتر | بیشتر |
| مناسب برای microservices | ❌ نه خیلی | ✅ بله |

---

# چرا در Microservices تقریباً همیشه Asymmetric استفاده می‌شود؟

چون در Microservices:

```
Identity Server
      |
      +---- API 1
      +---- API 2
      +---- API 3
      +---- API 10
```

اگر symmetric باشد:

- همه APIها باید secret داشته باشند

اگر asymmetric باشد:

- فقط public key را دارند
- فقط Identity Server private key دارد

پس امنیت بسیار بالاتر است.

---

✅ خلاصه کوتاه:

**Symmetric Signing**

```
same key for sign and verify
```

**Asymmetric Signing**

```
private key -> sign
public key  -> verify
```

و به همین دلیل در **OAuth2 / OpenID / Keycloak / IdentityServer / Microservices** تقریباً همیشه **Asymmetric Signing (مثل RS256)** استفاده می‌شود.
