این دو مفهوم، ستون‌های اصلی امنیت در **JWT (JSON Web Token)** و سیستم‌های مدرن احراز هویت مثل **Keycloak** هستند. بدون این‌ها، هر کسی می‌تواند یک توکن فیک بسازد و ادعا کند مدیر سیستم است.

در ادامه به زبان ساده و فنی این مفاهیم را باز می‌کنم.

---

# ۱. امضای توکن (Token Signing) چیست؟

**هدف:** اطمینان از اینکه توکن توسط **منبع معتبر** صادر شده و **تغییر نکرده** است.

وقتی کاربر لاگین می‌کند، سرور (Keycloak) یک توکن می‌سازد. این توکن شامل اطلاعات کاربر (Payload) است. اما قبل از ارسال، سرور باید آن را «مهر و موم» کند.

### فرآیند Signing:
1.  **Header + Payload:** سرور اطلاعات فنی و دیتای کاربر را برمی‌دارد.
2.  **Secret Key:** سرور یک «کلید مخفی» یا «کلید خصوصی» (Private Key) دارد.
3.  **Hashing:** با استفاده از یک الگوریتم (مثل RS256 یا HS256)، ترکیب اطلاعات و کلید را هش (Hash) می‌کند.
4.  **Signature:** خروجی این مرحله همان «امضا» است که به انتهای توکن چسبانده می‌شود.

**مثال ساده:**  
مثل این است که یک نامه بنویسید (Payload) و زیر آن را با یک خودکار خاص که فقط دست شماست امضا کنید (Signature). اگر کسی متن نامه را تغییر دهد، امضای شما دیگر با متن همخوانی نخواهد داشت.

---

# ۲. اعتبارسنجی توکن (Token Validation) چیست؟

**هدف:** اطمینان از اینکه توکن معتبر، دست‌نخورده و منقضی‌نشده است.

وقتی Microservice یا API Gateway توکن را دریافت می‌کند، نباید به آن اعتماد کند مگر اینکه آن را **Validate** کند.

### مراحل Validation:
1.  **بررسی ساختار:** آیا توکن سه قسمتی (Header.Payload.Signature) است؟
2.  **بررسی امضا (Signature Verification):** 
    *   اگر سیستم از **RS256** استفاده کند، API کلید عمومی (Public Key) را از Keycloak می‌گیرد.
    *   API با کلید عمومی چک می‌کند که آیا امضا با دیتای توکن همخوانی دارد یا نه.
    *   **نکته:** اگر حتی یک کاراکتر در ID کاربر تغییر کرده باشد، امضا باطل می‌شود.
3.  **بررسی انقضا (Expiration - `exp`):** آیا زمان فعلی از زمان انقضای توکن گذشته است؟
4.  **بررسی صادرکننده (Issuer - `iss`):** آیا این توکن واقعاً توسط Keycloak ما صادر شده یا یک Keycloak دیگر؟
5.  **بررسی مخاطب (Audience - `aud`):** آیا این توکن برای این سرویس خاص صادر شده است؟

# ۳. انواع الگوریتم‌های امضا (خیلی مهم)

در دنیای واقعی دو مدل اصلی داریم:

### الف) Symmetric (متقارن) - الگوریتم HS256
*   **یک کلید مشترک** وجود دارد.
*   هم سرور صادرکننده و هم API باید این کلید (Secret) را داشته باشند.
*   **مشکل:** اگر کلید لو برود، نفوذگر می‌تواند توکن معتبر بسازد. برای میکروسرویس‌های زیاد، اشتراک‌گذاری این کلید خطرناک است.

### ب) Asymmetric (نامتقارن) - الگوریتم RS256 ✅ (استاندارد Keycloak)
*   **کلید خصوصی (Private Key):** فقط دست Keycloak است و با آن توکن را **امضا (Sign)** می‌کند.
*   **کلید عمومی (Public Key):** در اختیار همه (APIها و Gateway) قرار می‌گیرد تا فقط توکن را **تأیید (Validate)** کنند.
*   **مزیت:** حتی اگر کلید عمومی لو برود، کسی نمی‌تواند توکن جعلی بسازد (چون کلید خصوصی را ندارد).

---

# ۴. چرا این فرآیند باعث Stateless بودن می‌شود؟

چون تمام اطلاعات لازم برای اعتبارسنجی (امضا، تاریخ انقضا و دیتای کاربر) **داخل خود توکن** است.  
API برای چک کردن توکن، نیاز ندارد به دیتابیس یا سرور Keycloak زنگ بزند (البته اگر کلید عمومی را از قبل داشته باشد). او فقط محاسبات ریاضی روی امضا انجام می‌دهد.

---

# ۵. سناریوی حمله (اگر Signing نبود چه می‌شد؟)

فرض کن توکن من این است:  
`{"user": "ali", "role": "user"}`

بدون Signing، من می‌توانم در مرورگر خود این را به راحتی تغییر دهم به:  
`{"user": "ali", "role": "admin"}`

و آن را به API بفرستم. اما چون توکن **Sign** شده است، اگر من دیتای داخل توکن را عوض کنم، **Signature با Payload جدید همخوانی نخواهد داشت** و API درخواست من را با خطای `401 Unauthorized` رد می‌کند.

# جمع‌بندی نهایی

| مفهوم | مسئولیت | محل انجام |
| :--- | :--- | :--- |
| **Token Signing** | ایجاد امضای دیجیتال برای تضمین عدم دستکاری | در **Identity Provider** (مثل Keycloak) |
| **Token Validation** | چک کردن امضا، تاریخ انقضا و صحت اطلاعات | در **API Gateway** یا **Microservice** |
