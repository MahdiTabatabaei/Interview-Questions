 تفاوت **Authentication Cookie** و **JWT (JSON Web Token)** یکی از پایه‌های درک معماری‌های مدرن احراز هویت وب است.  
بیایید با توضیح واضح، مرحله‌به‌مرحله و با مقایسه کنار هم بررسی کنیم.  

---

## 🔹 هدف مشترک هر دو
هر دو مکانیزم برای انجام **احراز هویت کاربر در وب‌اپ** استفاده می‌شوند.  
یعنی وقتی کاربر وارد سیستم شد، شما باید راهی داشته باشید تا در درخواست‌های بعدی بدانی «این کاربر همان کسی است که لاگین کرده».

اما روش انجام و محدوده کاربردشان **کاملاً متفاوت** است 👇

---

## 🧩 1. Authentication Cookie

### مفهوم
- **Cookie** یک فایل کوچک است که مرورگر پس از لاگین از سرور دریافت می‌کند.
- شامل یک **Session ID یا اطلاعات رمز‌شده** است.
- در هر درخواست بعدی مرورگر، خود به‌خود آن کوکی را به سرور می‌فرستد.

### خصوصیات
| ویژگی | توضیح |
|--------|--------|
| ذخیره‌سازی | در مرورگر (به‌صورت HttpOnly Cookie) |
| ارسال خودکار | مرورگر خودش در هر درخواست HTTP به همان دامنه کوکی را می‌فرستد |
| سرور وضعیت را نگه می‌دارد؟ | ✅ بله — سرور session را در حافظه یا دیتابیس ذخیره می‌کند |
| مناسب برای | اپلیکیشن‌های **سِرور-رندر‌شده (MVC یا Razor Pages)** |
| امنیت | خوب است، ولی نیاز به محافظت از CSRF دارد |
| کاربرد در | معماری سنتی یا وب‌اپ‌های کلاسیک با stateful server |

### خلاصه
> **Cookie-based authentication = session-centric (stateful)**.  
سرور باید خودش بداند session به کدام کاربر تعلق دارد.

## 🧩 2. JWT (JSON Web Token)

### مفهوم
- بعد از لاگین، سرور یک **توکن رمزنگاری‌شده (JWT)** تولید و به کلاینت می‌دهد.
- این توکن شامل اطلاعات کاربر (claims مثل userId, roles, exp) است.
- کلاینت در هر درخواست به API، توکن را در **Header** (معمولاً `Authorization: Bearer <token>`) می‌فرستد.

### خصوصیات
| ویژگی | توضیح |
|--------|--------|
| ذخیره‌سازی | LocalStorage یا SessionStorage یا Cookie |
| ارسال | دستی در Header با هر درخواست |
| سرور وضعیت را نگه می‌دارد؟ | ❌ خیر — Stateless (اطلاعات هویت داخل خود توکن است) |
| مناسب برای | API و SPA و موبایل |
| امنیت | باید مراقب XSS و Token Theft باشید |
| کاربرد در | معماری‌های **مدرن و Distributed (Microservices, REST)** |

### خلاصه
> **JWT Authentication = token-centric (stateless)**.  
سرور نیازی به نگهداری session ندارد؛ فقط امضای توکن را بررسی می‌کند.

---

## ⚖️ مقایسه کلی

| ویژگی             | Authentication Cookie | JWT Token |
|-------------------|-----------------------|------------|
| **نوع ارتباط**    | Stateful              | Stateless |
| **نحوه نگهداری** | Session در سرور       | دیتا در خود Token |
| **ارسال به سرور** | خودکار توسط مرورگر   | در Header (Bearer Token) |
| **مناسب برای**   | اپ‌های MVC سنتی      | SPA، موبایل، API |
| **Cross-domain**  | محدود (به دامنه خاص) | آسان‌تر |
| **امنیت**         | مقاوم در برابر XSS اگر HttpOnly باشد | آسیب‌پذیر در XSS اگر در storage باشد |
| **ابزار ریکوکیشن (log out)** | نیاز به حذف Session | با Blacklist یا تغییر secret key |
| **مقیاس‌پذیری**   | ضعیف‌تر (Stateful) | عالی (Stateless) |
| **کد ساده‌تر؟** | برای اپ‌های تک‌دامنه آسان‌تر | برای اپ‌های چنددامنه و API راحت‌تر |

---

## 🔸 مثال ساده برای تفاوت

### Cookie:
1. کاربر لاگین می‌کند → سرور Session می‌سازد → کوکی می‌دهد.  
2. مرورگر هر بار به همان دامنه درخواست می‌زند، کوکی خودکار ارسال می‌شود.  
3. سرور Session را بررسی می‌کند و هویت را تشخیص می‌دهد.

### JWT:
1. کاربر لاگین می‌کند → سرور JWT صادر می‌کند.  
2. Frontend در هر درخواست توکن را در Header می‌فرستد.  
3. API فقط امضای توکن را اعتبارسنجی می‌کند (بدون مراجعه به دیتابیس).

## 🔸 انتخاب در عمل

| نوع پروژه | بهترین روش |
|------------|-------------|
| Razor Pages / MVC سایت ساده | ✅ Authentication Cookie |
| React / Angular با API جدا | ✅ JWT |
| موبایل / Microservice | ✅ JWT |

## 🧠 نتیجه نهایی
- **Cookie** مناسب برنامه‌های سنتی **stateful** با یک سرور مرکزی  
- **JWT** مناسب معماری‌های **مدرن stateless** با چند سرویس و چند کلاینت
