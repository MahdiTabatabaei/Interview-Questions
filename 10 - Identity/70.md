در معماری **Microservices**، Keycloak معمولاً به عنوان **Identity Provider (IdP)** و **Authorization Server** عمل می‌کند و تمام سرویس‌ها برای احراز هویت به آن اعتماد می‌کنند. ایده اصلی این است که **احراز هویت متمرکز** باشد ولی **سرویس‌ها مستقل بمانند**.

در ادامه جریان معماری را ساده توضیح می‌دهم.

---

## 1. اجزای معماری

معمولاً این اجزا وجود دارند:

- **Client / Frontend**
  - وب‌اپ (React, Angular, Vue)
  - موبایل
- **API Gateway (اختیاری ولی رایج)**
  - مثل Kong, Nginx, Spring Gateway, YARP
- **Microservices**
  - Service A
  - Service B
  - Service C
- **Keycloak Server**
  - مدیریت کاربران
  - احراز هویت
  - صدور توکن

---

## 2. جریان احراز هویت (Login Flow)

سناریوی رایج **OpenID Connect + JWT** است.

### مرحله 1 – درخواست کاربر
کاربر وارد Frontend می‌شود و می‌خواهد به سیستم وارد شود.

بخش Frontend کاربر را به **Keycloak login page** ریدایرکت می‌کند.

---

### مرحله 2 – احراز هویت در Keycloak

کاربر در Keycloak لاگین می‌کند:

- username / password
- یا LDAP
- یا SSO
- یا MFA

بعد از موفقیت، Keycloak توکن صادر می‌کند.

---

### مرحله 3 – صدور Token

در این حالت Keycloak چند توکن صادر می‌کند:

- **Access Token (JWT)** → برای دسترسی به API  
- **ID Token** → اطلاعات هویت کاربر  
- **Refresh Token** → گرفتن توکن جدید

نمونه Access Token:

```
{
  "sub": "12345",
  "preferred_username": "ali",
  "email": "ali@test.com",
  "realm_access": {
    "roles": ["admin"]
  }
}
```

---

### مرحله 4 – ارسال درخواست به Microservice

در بخش Frontend هنگام درخواست API:

```
Authorization: Bearer ACCESS_TOKEN
```

را به سرویس می‌فرستد.

---

### مرحله 5 – اعتبارسنجی Token در Microservice

هر **Microservice** توکن را بررسی می‌کند.

دو روش وجود دارد:

**1️⃣ JWT validation (رایج‌تر)**  
سرویس با **public key** مربوط به Keycloak توکن را validate می‌کند.

مزیت:
- سریع
- بدون تماس با Keycloak
- مناسب Microservices

---

**2️⃣ Token Introspection**

سرویس توکن را به Keycloak می‌فرستد:

```
POST /introspect
```

در این وضعیت Keycloak می‌گوید توکن معتبر است یا نه.

عیب:
- تماس شبکه
- کندتر

---

## 3. نقش Role و Permission

در Keycloak می‌توان تعریف کرد:

- **Realm Roles**
- **Client Roles**

مثلاً:

```
admin
user
manager
```

این Role ها داخل JWT قرار می‌گیرند و سرویس‌ها بر اساس آن تصمیم می‌گیرند.

مثال در سرویس:

```
if role == "admin":
   allow
```

---

## 4. Single Sign-On (SSO)

مزیت بزرگ Keycloak در Microservices:

اگر کاربر در یک سیستم لاگین کند:

```
Service A
Service B
Service C
```

همه از همان **Session / Token** استفاده می‌کنند.

کاربر فقط **یک بار Login** می‌کند.

---

## 5. معماری معمول در Production

یک معماری رایج:

```
User
  |
Frontend (React)
  |
API Gateway
  |
-------------------------
| Service A             |
| Service B             |
| Service C             |
-------------------------
        |
     Keycloak
        |
     Database
```

Keycloak:

- کاربران
- نقش‌ها
- احراز هویت
- صدور توکن

را مدیریت می‌کند.

---

## 6. مزایای استفاده از Keycloak در Microservices

- SSO آماده
- استانداردهای امنیتی (OAuth2, OIDC)
- مدیریت Role
- مدیریت کاربران
- MFA
- اتصال LDAP / AD
- مناسب Kubernetes و Docker

---

✅ خلاصه:

در معماری Microservices:

- **Keycloak = مرکز احراز هویت**
- **JWT Token = بلیت دسترسی به سرویس‌ها**
- هر **Microservice مستقل توکن را اعتبارسنجی می‌کند**
