برای جلوگیری از این مشکل:

- تراکنش DB موفق شود
- اما ارسال پیام به Broker شکست بخورد

در این روش Outbox می‌گوید:

- پیام در جدول Outbox ذخیره شود
- سپس توسط یک Worker به broker ارسال شود
- درنهایت Broker و DB همیشه هماهنگ می‌مانند

---

## مشکل اصلی (Dual Write Problem)

فرض کنید یک سرویس باید دو کار انجام دهد:

1. تغییر را در **Database** ذخیره کند  
2. یک **Event/Message** به Broker (Kafka / RabbitMQ) بفرستد

مثال:

```
CreateOrder()
 ├─ Save Order in DB
 └─ Publish OrderCreated event
```

حالا مشکل:

### سناریوهای خطرناک

1️⃣ دیتابیس ذخیره شد ولی ارسال پیام شکست خورد

```
DB ✅
Broker ❌
```

در نتیجه:
- بقیه سرویس‌ها از ایجاد سفارش خبردار نمی‌شوند.

---

2️⃣ پیام ارسال شد ولی ذخیره DB شکست خورد

```
DB ❌
Broker ✅
```

در نتیجه:
- رویداد event منتشر شده برای سفارشی که اصلاً وجود ندارد.

---

این مشکل به نام **Dual Write Problem** شناخته می‌شود چون ما داریم به دو سیستم مستقل می‌نویسیم:

```
Database
Message Broker
```

و هیچ **transaction مشترکی** بین آن‌ها وجود ندارد.

---

# راه‌حل: Transactional Outbox Pattern

ایده اصلی:

به‌جای ارسال مستقیم پیام به بروکر، ابتدا پیام را در **همان دیتابیس** ذخیره می‌کنیم.

یعنی:

```
Business Table
Outbox Table
```

هر دو در **یک transaction دیتابیس** نوشته می‌شوند.

---

## ساختار Outbox

یک جدول اضافه در دیتابیس:

```
outbox_events
-------------
id
event_type
payload
status
created_at
```

---

## مرحله 1 — داخل transaction دیتابیس

وقتی یک عملیات انجام می‌شود:

```
BEGIN TRANSACTION

Insert Order
Insert Outbox Event (OrderCreated)

COMMIT
```

نتیجه:

```
DB ✅
Outbox ✅
```

پس:
- اگر transaction fail شود → هیچ چیز نوشته نمی‌شود
- اگر commit شود → هر دو نوشته شده‌اند

---

## مرحله 2 — ارسال به Broker

یک **Background Worker / Relay** وجود دارد که مرتب جدول outbox را می‌خواند.

```
Outbox Poller
   ↓
read new events
   ↓
publish to broker
   ↓
mark as sent
```

مثال:

```
SELECT * FROM outbox WHERE status='NEW'
```

سپس:

```
publish → Kafka
update status=sent
```

---

## معماری کامل

```
Service
   │
   │ DB Transaction
   ▼
Database
 ├─ orders
 └─ outbox_events
        │
        │ poll
        ▼
Outbox Relay
        │
        ▼
Kafka / RabbitMQ
```

---

# چرا این روش مشکل را حل می‌کند؟

چون فقط **یک عملیات atomic** داریم:

```
write to database
```

و database transaction **کاملاً قابل اعتماد** است.

پس دیگر حالت زیر نداریم:

```
DB ✅ Broker ❌
```

چون پیام ابتدا در DB ذخیره شده و بعداً ارسال می‌شود.

اگر broker down باشد:

```
DB ✅
Outbox ✅
Broker (later)
```

پیام بعداً ارسال خواهد شد.

---

# مزیت‌های Transactional Outbox

• جلوگیری از **Dual Write Problem**  
• سازگار با **Microservices**  
• کار می‌کند با هر بروکری (Kafka / RabbitMQ / SQS)  
• نیاز به **distributed transaction (2PC)** ندارد  
• بسیار **قابل اعتماد**

---

# چالش‌ها

### 1) ایجاد Duplicate Messages

ممکن است worker دوبار پیام بفرستد:

```
publish success
crash before marking sent
```

پس consumer باید **idempotent** باشد.

---

### 2) مشکل Polling Load

خواندن مداوم جدول outbox می‌تواند فشار ایجاد کند.

راه‌حل‌ها:

- polling با interval
- batch processing
- CDC

---

### 3) مکانیزم Cleanup

باید eventهای قدیمی حذف شوند.

---

# نسخه پیشرفته‌تر: CDC + Outbox

به‌جای polling، از **Change Data Capture** استفاده می‌شود.

مثلاً:

```
Database → Debezium → Kafka
```

در Debezium تغییرات جدول outbox را از log دیتابیس می‌خواند.

مزایا:

- باعث latency کمتر
- بدون polling
- و قابلیت scalable

---

# مثال ساده (Pseudo C#)

### داخل سرویس

```csharp
using var tx = db.BeginTransaction();

db.Orders.Add(order);

db.Outbox.Add(new OutboxEvent {
    Type = "OrderCreated",
    Payload = Json(order)
});

tx.Commit();
```

---

### Outbox Worker

```csharp
var events = db.Outbox.Where(x => x.Status == "NEW");

foreach (var e in events)
{
    kafka.Publish(e.Payload);
    e.Status = "SENT";
}

db.SaveChanges();
```

# چه زمانی این الگو استفاده می‌شود؟

تقریباً در همه معماری‌های **Event‑Driven Microservices**:

مثال‌ها:

- Order Service → Payment Service
- User Service → Email Service
- Inventory Service → Shipping Service

---

✅ **خلاصه یک خطی**

الگوی Transactional Outbox با ذخیره کردن پیام در **همان transaction دیتابیس** و ارسال بعدی آن توسط یک worker، مشکل **Dual Write بین Database و Message Broker** را حل می‌کند.
