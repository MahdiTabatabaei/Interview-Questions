تعریف **Poison Message** پیامی است که هر بار توسط Consumer پردازش می‌شود اما همیشه خطا ایجاد می‌کند.

دلایل:

- فرمت اشتباه داده
- نسخه ناسازگار پیام
- خطای بیزینسی غیرقابل حل

روش‌های مدیریت:

1. داشتن Retry محدود
2. انتقال به **Dead Letter Queue (DLQ)**
3. نمایش Alert برای بررسی دستی
4. استفاده از Message validation قبل از پردازش

مثال RabbitMQ با retry:
```csharp

try
{
    ProcessMessage(message);
    channel.BasicAck(tag, false);
}
catch
{
    channel.BasicNack(tag, false, false); // ارسال به DLQ
}

```
مثال زندگی:

اگر یک بسته پستی همیشه آدرس اشتباه داشته باشد، بعد از چند تلاش به **بخش بررسی دستی** منتقل می‌شود.


----


تعریف **Poison Message** یعنی پیامی که هر بار Consumer آن را پردازش می‌کند **fail می‌شود** و اگر دوباره تحویل داده شود باز هم fail می‌شود.  
مثلاً:

- داده خراب (invalid JSON)
- وجود schema اشتباه
- ارجاع reference به دیتای حذف شده
- وجود bug در business logic
- پیام مربوط به version قدیمی سیستم

اگر این پیام مدیریت نشود می‌تواند باعث شود:

- در این حالت Consumer دائم crash کند
- وضعیت Queue/Partition جلو نرود
- کل سیستم block شود

به همین دلیل باید **Poison Message Handling Strategy** داشته باشیم.

---

# 1️⃣ Retry (اولین مرحله)

اولین کار معمولاً **retry** است، چون ممکن است خطا موقتی باشد.

انواع retry:

### Immediate Retry
چند بار پشت سر هم retry.

مثال:

```
maxRetry = 3
```

اگر fail شد:

```
retry 1
retry 2
retry 3
```

اگر هنوز fail شد → مرحله بعد.

---

### Exponential Backoff

به جای retry فوری:

```
1s
5s
30s
2m
```

مزیت:

- فشار روی سیستم کم می‌شود
- برای خطاهای موقتی خوب است (مثلاً DB down)

---

# 2️⃣ Dead Letter Queue (DLQ)

اگر بعد از چند retry هنوز fail شد:

```
message → DLQ
```

معنای DLQ یعنی:

> یک queue/topic جدا برای پیام‌های مشکل‌دار

مثال:

```
order-created
order-created-dlq
```

پیام مشکل‌دار منتقل می‌شود به:

```
order-created-dlq
```

و سیستم اصلی ادامه می‌دهد.

---

# 3️⃣ Logging و Monitoring

هر Poison Message باید:

- log شود
- trace داشته باشد
- alert ایجاد کند

مثلاً:

```
OrderId = 93423
Error = Invalid currency code
RetryCount = 5
```

ابزارهای معمول:

- OpenTelemetry
- Prometheus
- Grafana
- ELK

---

# 4️⃣ Manual Inspection

پیام‌های DLQ معمولاً:

- بررسی می‌شوند
- اصلاح می‌شوند
- دوباره replay می‌شوند

مثلاً:

```
Fix data → resend to main topic
```

---

# 5️⃣ Parking Queue

گاهی به جای DLQ از **Parking Queue** استفاده می‌شود.

تفاوت:

DLQ:

```
پیام شکست خورده → نگهداری برای بررسی
```

Parking Queue:

```
پیام فعلاً پردازش نشود
بعداً دوباره امتحان شود
```

---

# 6️⃣ Circuit Breaker

اگر تعداد خطا زیاد شود:

```
Consumer temporarily stops
```

تا:

- dependency recover شود
- flood ایجاد نشود

---

# 7️⃣ Validation قبل از Queue

یکی از بهترین روش‌ها این است که Poison Message اصلاً وارد سیستم نشود.

مثلاً:

- Schema validation
- JSON schema
- Avro schema registry

---

# 8️⃣ در Kafka چگونه انجام می‌شود؟

ابزار Kafka DLQ داخلی ندارد ولی معمولاً این کار انجام می‌شود:

```
main-topic
main-topic-retry
main-topic-dlq
```

Flow:

```
main-topic
     ↓
processing error
     ↓
retry-topic
     ↓
retry fail
     ↓
DLQ-topic
```

---

# 9️⃣ در RabbitMQ چگونه انجام می‌شود؟


ابزار RabbitMQ مکانیزم **DLX (Dead Letter Exchange)** دارد.

تنظیم:

```
x-dead-letter-exchange
x-dead-letter-routing-key
```

اگر:

- reject
- nack
- TTL expire

پیام به DLQ منتقل می‌شود.

---

# ✅ یک Flow استاندارد Production

```
Producer
   ↓
Main Queue
   ↓
Consumer
   ↓
Processing Error
   ↓
Retry Queue (with delay)
   ↓
Retry Fail
   ↓
Dead Letter Queue
   ↓
Monitoring / Manual Fix
```

---

# خلاصه

مدیریت Poison Message معمولاً شامل:

1️⃣ Retry (چند بار)  
2️⃣ Backoff  
3️⃣ Dead Letter Queue  
4️⃣ Logging و Monitoring  
5️⃣ بررسی دستی  
6️⃣ Replay
