برای مانیتورینگ یک **Message Broker** (مثل Kafka یا RabbitMQ) هدف این است که بفهمیم:

- سیستم **سالم است یا نه**
- **پیام‌ها با سرعت مناسب پردازش می‌شوند یا نه**
- **گلوگاه (bottleneck)** کجاست

معمولاً مانیتورینگ با ابزارهایی مثل:

- **Prometheus**
- **Grafana**
- **ELK**
- **Datadog / New Relic**

انجام می‌شود.

مهم‌ترین **Metrics** چند دسته هستند:

---

# 1. Throughput (نرخ پردازش پیام)

مهم‌ترین معیار.

نشان می‌دهد در هر ثانیه چند پیام:

- تولید (produce)
- مصرف (consume)

می‌شود.

مثال:

```
messages produced/sec
messages consumed/sec
bytes/sec
```

اگر throughput ناگهان کاهش یابد ممکن است:

- consumer کند شده
- broker overload شده
- network مشکل دارد

---

# 2. Latency

زمانی که طول می‌کشد یک پیام از producer به consumer برسد.

انواع latency:

- **publish latency**
- **end‑to‑end latency**
- **consumer processing latency**

افزایش latency معمولاً نشانه:

- backlog
- کندی consumer
- فشار روی broker

---

# 3. Queue / Topic Lag

خیلی مهم در سیستم‌های streaming.

**Lag = تعداد پیام‌هایی که هنوز پردازش نشده‌اند**

در Kafka:

```
Consumer Lag = latest offset - consumer offset
```

اگر lag زیاد شود یعنی:

- consumerها عقب افتاده‌اند
- throughput consumer کافی نیست

---

# 4. Queue Length / Backlog

در RabbitMQ:

```
messages_ready
messages_unacked
```

اگر queue length زیاد شود:

- consumer کند است
- یا crash کرده

---

# 5. Error Rate

نرخ خطا در سیستم.

مثلاً:

- failed publishes
- rejected messages
- consumer exceptions

افزایش error rate نشانه:

- poison messages
- bug در consumer
- schema mismatch

---

# 6. Resource Usage

باید منابع broker را مانیتور کنیم:

### CPU

اگر:

```
CPU ≈ 100%
```

broker ممکن است bottleneck باشد.

---

### Memory

در RabbitMQ بسیار مهم است چون:

```
queues often stay in RAM
```

اگر RAM پر شود:

```
flow control
```

فعال می‌شود.

---

### Disk I/O

در Kafka بسیار مهم است چون Kafka روی disk می‌نویسد.

Metrics:

```
disk read/write throughput
disk latency
```

---

### Network

Message broker معمولاً network heavy است.

Metrics:

```
network throughput
packet drops
connection count
```

---

# 7. Consumer Health

باید بدانیم consumerها سالم هستند.

موارد مهم:

- active consumers
- consumer restart rate
- consumer processing time

---

# 8. Message Size

اگر اندازه پیام‌ها ناگهان بزرگ شود:

- throughput کم می‌شود
- latency زیاد می‌شود

---

# 9. Partition / Queue Distribution

در Kafka مهم است.

اگر load روی یک partition بیشتر باشد:

```
hot partition
```

که باعث bottleneck می‌شود.

---

# 10. Dead Letter Queue Metrics

باید مانیتور شود:

```
DLQ message count
```

اگر زیاد شود یعنی:

- پیام‌های سمی زیاد شده‌اند
- consumer مشکل دارد

---

# مثال یک Dashboard واقعی

یک dashboard معمولاً شامل:

- messages/sec
- consumer lag
- queue size
- CPU / RAM
- disk I/O
- error rate
- DLQ size

---

# Alert هایی که معمولاً تنظیم می‌کنیم

مثلاً:

```
Consumer lag > 10000
Queue size > 50000
CPU > 85%
Error rate > 2%
DLQ messages increasing
```

---

# خلاصه

مهم‌ترین Metrics برای مانیتورینگ Message Broker:

- **Throughput (messages/sec)**
- **Latency**
- **Consumer Lag**
- **Queue Length / Backlog**
- **Error Rate**
- **CPU / Memory**
- **Disk I/O**
- **Network**
- **Consumer Health**
- **DLQ size**
