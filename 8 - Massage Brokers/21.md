در Kafka، **Rebalancing** فرایندی است که طی آن **پارتیشن‌های یک Topic بین اعضای یک Consumer Group دوباره توزیع می‌شوند**.  
اگر بخواهیم ساده بگوییم:

**Rebalancing = بازتقسیم پارتیشن‌ها بین مصرف‌کننده‌ها برای حفظ تعادل و هماهنگی گروه**

---

# چرا اصلاً Rebalance لازم است؟

ابزار Kafka تضمین می‌کند:

- *هر پارتیشن فقط توسط یک Consumer در گروه مصرف شود*  
- ولی اگر تعداد Consumerها یا پارتیشن‌ها تغییر کند، باید توزیع جدیدی ساخته شود  
→ این کار همان Rebalancing است.

---

# چه زمانی Rebalance رخ می‌دهد؟

عمل Rebalancing در ۴ سناریو اصلی اتفاق می‌افتد:

---

## 1) وقتی یک Consumer جدید به گروه اضافه شود

مثال:

```
Topic: orders
Partitions: 4
Consumer Group: order-processors
```

قبل:
```
C1 → p0, p1
C2 → p2, p3
```

اگر **C3 وارد شود**:

Kafka مجبور است پارتیشن‌ها را دوباره بین ۳ مصرف‌کننده توزیع کند:

بعد:
```
C1 → p0
C2 → p1
C3 → p2, p3
```

**=> Rebalance**

---

## 2) وقتی یک Consumer از گروه خارج شود (Crash یا Shutdown)

اگر یکی از Consumerها خراب یا قطع شود، Kafka باید پارتیشن‌هایش را به دیگران بدهد.

مثال:

```
C1 → p0, p1
C2 → p2, p3
```

اگر C2 از کار بیفتد:

```
C1 → p0, p1, p2, p3
```

**=> Rebalance**

چون پارتیشن‌ها بدون صاحِب می‌مانند و باید دوباره assign شوند.

---

## 3) وقتی Topic یا Partition جدید اضافه شود یا تعداد Partitionها افزایش یابد

مثلاً Topic از 4 پارتیشن به 6 پارتیشن افزایش می‌یابد:

قبلاً:
```
C1 → p0, p1
C2 → p2, p3
```

بعد از افزایش Partition:
```
C1 → p0, p1, p4
C2 → p2, p3, p5
```

Kafka باید توزیع جدید ایجاد کند  
→ **Rebalance**

---

## 4) وقتی Coordinator گروه یا Leader از بین برود

ابزار Kafka یک **Group Coordinator** دارد (در Broker).  

اگر آن Broker از کار بیفتد:

- گروه باید از ابتدا هماهنگ شود  
- همچنین Consumerها باید Join Group انجام دهند  

→ **Rebalance رخ می‌دهد**

---

# چه اتفاقی در Rebalancing رخ می‌دهد؟ (مرحله به مرحله)

ابزار Kafka از پروتکل **Group Membership** استفاده می‌کند.

مراحل:

1. Consumerها به Coordinator پیام می‌دهند که *آماده Rebalance هستند* (JoinGroup)
2. Kafka یک Consumer را به عنوان **Leader** گروه انتخاب می‌کند
3. Leader پارتیشن‌ها را بین Consumerها تقسیم می‌کند (Assignment)
4. بقیه Consumerها Assignment را می‌گیرند و شروع به مصرف از پارتیشن‌های جدید می‌کنند

در این زمان:

**تا پایان Rebalance هیچ Consumerی نمی‌تواند پیام مصرف کند → توقف لحظه‌ای پردازش**

---

# فرایند Rebalance چقدر طول می‌کشد؟

به تنظیمات heartbeat و session.timeout بستگی دارد:

- `session.timeout.ms` → زمان تشخیص قطع شدن یک Consumer  
- `heartbeat.interval.ms` → نرخ ارسال heartbeat توسط Client  
- `max.poll.interval.ms` → اگر Consumer خیلی طولانی poll نکند، Kafka فکر می‌کند مرده

اگر این‌ها بد تنظیم شوند، **Rebalance غیرضروری** رخ می‌دهد.

---

# Sticky Rebalancing چیست؟

از Kafka 2.4 به بعد، الگوریتم جدیدی معرفی شد:

**Sticky Assignor**

هدفش:

- حفظ پارتیشن‌های قبلی تا حد ممکن  
- کمتر جابه‌جا شدن پارتیشن‌ها  
- کاهش مدت Rebalance

قبلاً Kafka همه چیز را از صفر تقسیم می‌کرد.  
اما Sticky باعث می‌شود فقط تغییرات ضروری اعمال شود.

---

# مثال ساده از Rebalance

فرض کنیم:

Topic: payments  
Partitions: 3  
Consumers: C1, C2

ابتدا:

```
C1 → p0, p1
C2 → p2
```

اگر C2 Crash کند:

```
C1 → p0, p1, p2
```

و وقتی C2 برگردد:

Kafka دوباره Rebalance می‌کند:

```
C1 → p0
C2 → p1, p2
```

---

# جمع‌بندی

درواقع **Rebalancing** در Kafka یک فرایند ضروری برای هماهنگی Consumer Group است.

زمان وقوع:

- اضافه شدن Consumer جدید  
- حذف یا Crash شدن Consumer  
- افزایش پارتیشن‌ها  
- از دست رفتن Coordinator

مزایا:

- مدیریت خودکار Load balancing  
- جلوگیری از مصرف تکراری پیام‌ها توسط چند مصرف‌کننده

معایب:

- وقفه موقتی در مصرف پیام‌ها  
- در Rebalanceهای زیاد پرفورمنس افت می‌کند
