- فقط **یک Consumer برای هر Queue**

Kafka:

حفظ **ترتیب پیام‌ها (Message Ordering)** وقتی چندین Consumer داریم چالش مهمی است، چون پردازش موازی می‌تواند ترتیب طبیعی پیام‌ها را به‌هم بزند. راه‌حل به معماری سیستم و بروکری که استفاده می‌کنید بستگی دارد، اما چند الگوی استاندارد وجود دارد.

---

# 1) روش Partition / Sharding بر اساس Key (رایج‌ترین روش – مخصوصاً در Kafka)

ایده اصلی این است که پیام‌های مرتبط با یک **کلید (Key)** همیشه به **یک پارتیشن مشخص** بروند.

در Kafka:

- ترتیب پیام‌ها **فقط داخل یک partition تضمین می‌شود**.
- هر partition در یک consumer group فقط به **یک consumer** اختصاص داده می‌شود.

مثال:

فرض کنید پیام‌ها مربوط به سفارش‌ها هستند.

```
OrderCreated(orderId=10)
OrderPaid(orderId=10)
OrderShipped(orderId=10)
```

اگر `orderId` به عنوان **key** استفاده شود:

```
Partition 1
Order 10 → Created
Order 10 → Paid
Order 10 → Shipped
```

همه این پیام‌ها به یک consumer می‌رسند و ترتیب حفظ می‌شود.

اما سفارش‌های دیگر می‌توانند روی partitionهای دیگر پردازش شوند.

```
Partition 1 → Consumer A → Order 10
Partition 2 → Consumer B → Order 25
Partition 3 → Consumer C → Order 31
```

نتیجه:

- ترتیب داخل هر entity حفظ می‌شود
- سیستم همچنان **مقیاس‌پذیر** باقی می‌ماند

---

# 2) روش Single Consumer (ساده‌ترین ولی غیرمقیاس‌پذیر)

اگر ترتیب **در کل سیستم** مهم باشد:

```
Producer → Queue → Single Consumer
```

مزیت:
- ترتیب 100٪ حفظ می‌شود

مشکل:
- در این حالت throughput پایین
- عدم مقیاس‌پذیری

این روش معمولاً فقط در سیستم‌های کوچک استفاده می‌شود.

---

# 3) روش Serial Processing per Key (Worker Pool + Key Lock)

در بعضی سیستم‌ها پیام‌ها به چند worker می‌روند، ولی برای هر **کلید خاص** فقط یک worker همزمان کار می‌کند.

ایده:

```
hash(key) → worker
```

مثال:

```
Order 10 → Worker 2
Order 11 → Worker 5
Order 12 → Worker 1
```

این همان مفهوم **consistent hashing** است.

مزیت:
- ترتیب برای هر entity حفظ می‌شود
- موازی‌سازی بالا

---

# 4) روش Sequence Number + Reordering

گاهی ترتیب در شبکه به‌هم می‌ریزد. در این حالت:

- هر پیام **sequence number** دارد
- و consumer پیام‌ها را **buffer** می‌کند
- سپس مرتب پردازش می‌کند

مثال:

```
msg(1)
msg(3)
msg(2)
```

در این حالت consumer صبر می‌کند تا 2 برسد.

این روش در سیستم‌های real‑time و networking زیاد استفاده می‌شود.

---

# 5) روش Transaction / Exactly‑Once Pipeline

در سیستم‌هایی مثل Kafka Streams:

- offset
- state store
- transaction

با هم ترکیب می‌شوند تا:

- ترتیب
- عدم تکرار
- حالت atomic processing

حفظ شود.

---

# 6) Ordered Queues (در RabbitMQ)

در RabbitMQ:

- معماری **queue ذاتاً FIFO است**
- اما اگر چند consumer داشته باشید ممکن است ترتیب به‌هم بخورد چون:

```
Msg1 → Consumer A
Msg2 → Consumer B
```

اگر B زودتر تمام کند:

```
Msg2 processed before Msg1
```

راه‌حل‌ها:

- **prefetch = 1**
- یا **single consumer**
- یا **partitioned queues**

✅ **قانون طلایی در سیستم‌های توزیع‌شده**

تقریباً هیچ سیستمی **ترتیب global کامل** را در مقیاس بزرگ تضمین نمی‌کند.  
معمولاً ترتیب فقط برای **یک entity یا key خاص** حفظ می‌شود.

مثلاً:

- ترتیب تراکنش‌های یک حساب بانکی
- ترتیب رویدادهای یک سفارش
- ترتیب پیام‌های یک کاربر

نه ترتیب کل سیستم.
