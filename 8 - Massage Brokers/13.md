مفهوم **Split Brain** در RabbitMQ یکی از موضوعات حیاتی در **RabbitMQ Cluster** است، چون اگر درست مدیریت نشود می‌تواند باعث **از دست رفتن پیام‌ها یا ناسازگاری داده** شود.

در ادامه، هم مفهوم را شفاف توضیح می‌دهم، هم اینکه RabbitMQ **چطور با آن برخورد می‌کند** و بهترین راه‌حل‌ها چیست.

---

## 1️⃣ تعریف Split Brain یعنی چه؟

درواقع **Split Brain** زمانی رخ می‌دهد که:

- یک cluster از چند node تشکیل شده
- ارتباط شبکه‌ای بین nodeها قطع می‌شود
- هر بخش فکر می‌کند که بخش دیگر از cluster جدا شده یا مرده است
- در نتیجه، cluster به **چند زیر-cluster مستقل** تقسیم می‌شود

مثال:
```
Node A ——x—— Node B
Node C ——x—— Node B
```

نتیجه:
- نود های A و C فکر می‌کنند B مرده
- همچنین نود B فکر می‌کند A و C مرده‌اند
- هر کدام شروع به پذیرش درخواست می‌کنند ❌

---

## 2️⃣ چرا Split Brain خطرناک است؟

- پیام‌ها ممکن است **دو بار پردازش شوند**
- ترتیب پیام‌ها از بین می‌رود
- در این وضعیت Metadata (queue, exchange, binding) ناسازگار می‌شود
- بعد از reconnect، ادغام state تقریباً **غیرممکن** است

به همین دلیل RabbitMQ اصولاً **اجازه نمی‌دهد cluster به‌صورت split ادامه دهد**.

---

## 3️⃣ ابزار RabbitMQ چگونه Split Brain را مدیریت می‌کند؟

ابزار RabbitMQ از مفهومی به نام **Partition Handling** استفاده می‌کند.

تنظیم مهم:

```conf
cluster_partition_handling = ...
```

### سه استراتژی اصلی وجود دارد:

---

## 4️⃣ استراتژی‌ها‌ی مدیریت Partition

### ✅ 1. ویژگی `pause_minority` (پیشنهادی و پیش‌فرض در نسخه‌های جدید)

**ایده:**  
بخشی که **اکثریت nodeها را ندارد، متوقف می‌شود**.

مثال:
- در Cluster سه‌نودی: A, B, C
- سیستم Partition:  
  - گروه ۱: A + B (اکثریت)
  - گروه ۲: C (اقلیت)

نتیجه:
- نود های A و B فعال می‌مانند ✅
- و نود C تمام queueها و connectionها را **pause** می‌کند ❌

مزایا:
- جلوگیری کامل از split brain
- بدون از دست رفتن consistency

معایب:
- اگر اکثریت از دست برود، کل cluster می‌خوابد

---

### ✅ 2. الگوی `autoheal`

**ایده:**  
هر دو طرف فعال می‌مانند، ولی بعد از reconnect، RabbitMQ به‌صورت خودکار یکی را خاموش و state را sync می‌کند.

مکانیزم:
- وضعیت partition رخ می‌دهد
- هر طرف کار می‌کند
- بعد از reconnect:
  - یک طرف shutdown می‌شود
  - و metadata و queueها دوباره sync می‌شوند

مزایا:
- قابلیت availability بالاتر در لحظهٔ partition

معایب:
- خطر از دست رفتن پیام
- پیچیدگی بالا
- برای سیستم‌های حساس توصیه نمی‌شود

---

### ❌ 3. حالت `ignore`

**ایده:**  
ابزار RabbitMQ هیچ کاری نمی‌کند 😐

نتیجه:
- وضعیت Split brain واقعی رخ می‌دهد
- احتمال corruption شدید داده

تقریباً همیشه **بدترین انتخاب** است.

---

## 5️⃣ کدام استراتژی بهتر است؟

| سناریو | انتخاب مناسب |
|------|-------------|
| سیستم‌های production حساس | ✅ `pause_minority` |
| سیستم‌هایی که availability از consistency مهم‌تر است | ⚠️ `autoheal` |
| تست یا محیط‌های موقت | ❌ `ignore` |

---

## 6️⃣ نقش Quorum Queue در جلوگیری از Split Brain

از RabbitMQ 3.8+:

### ✅ حالت Quorum Queue (بر پایه Raft)

- فقط روی **اکثریت nodeها** leader انتخاب می‌شود
- اگر اکثریت نباشد → queue متوقف می‌شود
- وضعیت consistency قوی‌تر از classic queue

یعنی حتی اگر cluster partition شود:
- فقط یک طرف حق نوشتن دارد ✅
- طرف دیگر هیچ پیامی نمی‌پذیرد ❌

📌 **بهترین practice امروزی:**
- استفاده از **Quorum Queue**
- همراه با `pause_minority`

---

## 7️⃣ جمع‌بندی نهایی

ابزار **RabbitMQ با Split Brain به‌صورت فعال برخورد می‌کند و اجازهٔ ادامهٔ کار ناسازگار را نمی‌دهد.**

کلیدهای اصلی مدیریت:

- تعریف `cluster_partition_handling = pause_minority`
- استفاده از **Quorum Queue**
- پرهیز از `ignore`
- درک اینکه consistency مهم‌تر از availability است

---

- یا تنظیمات recommended برای production RabbitMQ Cluster رو قدم‌به‌قدم بنویسم
