حالت **Split Brain** یعنی وضعیتی که در یک سیستم توزیع‌شده **دو یا چند نود تصور می‌کنند که Leader هستند** و هر کدام مستقل عمل می‌کنند. نتیجه معمولاً **ناسازگاری داده (data inconsistency)** است.

در Kafka این سناریو بسیار خطرناک است چون ممکن است:

- دو Broker برای یک **Partition** همزمان Leader شوند  
- در این حالت Producerها به هر دو Leader بنویسند  
- و logها از هم جدا شوند

ابزار Kafka برای جلوگیری از این مشکل چند مکانیزم دارد.

---

# 1. وجود یک Controller واحد در Cluster

در Kafka همیشه **یک Controller فعال** وجود دارد.

وظیفه Controller:

- مدیریت Metadata
- تشخیص خرابی Brokerها
- انجام Leader election برای Partitionها

اگر دو Controller وجود داشته باشند، خطر split brain زیاد می‌شود. برای جلوگیری از این موضوع:

- در **Kafka قدیمی → Zookeeper** اجماع را کنترل می‌کرد  
- در **Kafka جدید → KRaft** از **Raft consensus** استفاده می‌شود

درواقع Raft تضمین می‌کند:

- در هر لحظه فقط **یک Leader معتبر** وجود دارد.

---

# 2. استفاده از Quorum (اکثریت)

در KRaft، Controllerها یک **Raft quorum** تشکیل می‌دهند.

مثال:

```
Controller nodes: 3
```

برای تصمیم‌گیری باید **اکثریت (2 از 3)** موافق باشند.

اگر شبکه split شود:

```
Partition A → 2 node
Partition B → 1 node
```

فقط گروهی که **اکثریت دارد** می‌تواند Leader داشته باشد.

گروه کوچک‌تر:

- نمی‌تواند Leader انتخاب کند
- فقط read-only یا inactive می‌شود

این دقیقاً همان چیزی است که **Split Brain را جلوگیری می‌کند**.

---

# 3. محدود کردن Leader Election به ISR

در سطح Partition نیز Kafka محافظت دارد.

درواقع Leader جدید فقط از میان:

```
ISR = In-Sync Replicas
```

انتخاب می‌شود.

چرا؟

چون Replica خارج از ISR ممکن است داده عقب‌افتاده داشته باشد و اگر Leader شود:

- دراین حالت logها diverge می‌شوند
- ناسازگاری ایجاد می‌شود

---

# 4. جلوگیری از این‌که **یک موجودیت قدیمی** fencing با Epoch ها

[[Fencing - Epoch]]

ابزار Kafka از مفهوم **epoch** استفاده می‌کند.

دو نوع مهم:

- **Leader Epoch**
- **Producer Epoch**

هر بار که Leader عوض می‌شود:

```
leader epoch++
```

اگر یک Leader قدیمی دوباره ظاهر شود:

- درخواست‌هایش رد می‌شود
- چون epoch آن قدیمی است

این مکانیزم عملاً **Leader قدیمی را "fence" می‌کند**.

---

# 5. ویژگی Metadata Log در KRaft

در KRaft تمام تغییرات cluster در یک **Metadata Log** ذخیره می‌شود.

این log:

- با **Raft consensus** replicate می‌شود
- ترتیب واحدی برای تغییرات ایجاد می‌کند

بنابراین:

- تمام Brokerها یک دید یکسان از وضعیت cluster دارند
- اختلاف حالت (state divergence) رخ نمی‌دهد

---

# 6. مثال واقعی Split Brain در شبکه

فرض کنیم 3 Broker داریم:

```
Broker1
Broker2
Broker3
```

و replication:

```
Partition0
Leader → Broker1
Followers → Broker2, Broker3
```

حالا network partition رخ می‌دهد:

```
Group A → Broker1
Group B → Broker2 + Broker3
```

در KRaft:

- گروه B اکثریت دارد → Leader جدید انتخاب می‌کند
- در این حالت Broker1 اکثریت ندارد → نمی‌تواند Leader بماند

پس:

```
Leader → Broker2
```

در نتیجه Broker1 عملاً از cluster خارج می‌شود تا reconnect شود.

---

# 7. نقش Producer Idempotence

برای جلوگیری از writeهای متناقض:

```
enable.idempotence=true
```

ابزار Kafka از:

- producer id
- sequence number

استفاده می‌کند تا پیام‌های duplicate یا out-of-order را رد کند.

این هم به کاهش اثرات split brain کمک می‌کند.

---

# جمع‌بندی

ابزار Kafka با چند لایه از Split Brain جلوگیری می‌کند:

1. **Raft quorum (KRaft)** → جلوگیری از چند Controller
2. **اکثریت (majority voting)** → فقط اکثریت تصمیم می‌گیرد
3. **ISR-based leader election** → جلوگیری از leader ناسازگار
4. **Leader epochs** → جلوگیری از فعال شدن leader قدیمی
5. **Metadata log replication** → حفظ state واحد

نتیجه:

- فقط **یک Leader معتبر** وجود دارد
- ناسازگاری داده بسیار کم می‌شود
