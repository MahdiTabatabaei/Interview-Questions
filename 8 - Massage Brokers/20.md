در Kafka سه مدل تحویل پیام داریم:

1. at-most-once → ممکن است پیام گم شود، ولی دوباره پردازش نمی‌شود  
2. at-least-once → پیام گم نمی‌شود، اما ممکن است دوبار پردازش شود  
3. **exactly-once** → نه گم شود، نه دوبار پردازش شود

ابزار Kafka از نسخه 0.11 به بعد مکانیزم‌هایی برای **Exactly Once Semantics (EOS)** اضافه کرد.  
پیاده‌سازی‌اش بر ۳ ستون اصلی است:

---

## 1. مفهوم Idempotent Producer (تضمین بدون تکرار در سطح Topic)

درواقع Idempotent Producer باعث می‌شود اگر به‌خاطر Retryها یک پیام دوباره فرستاده شد، Kafka آن را **تکراری در Log ذخیره نکند**.

فعال‌سازی:

- `enable.idempotence = true`

کاری که Kafka می‌کند:

- به هر Producer یک `ProducerId` و به هر پیام یک `Sequence Number` می‌دهد  
- برای هر پارتیشن، Kafka آخرین Sequence را نگه می‌دارد  
- اگر پیام با Sequence تکراری دریافت شود → نادیده گرفته می‌شود

این مرحله جلوی **دوباره‌نویسی در Topic مقصد** را می‌گیرد، ولی برای سناریوی **read → process → write** به‌تنهایی کافی نیست.

---

## 2. Transactions (Atomic Read-Process-Write)

برای **exactly-once در pipeline کامل** (خواندن از یک Topic و نوشتن در Topic دیگر یا DB)، Kafka از **Producer Transaction** استفاده می‌کند.

مفهوم:

- چند پیام ارسالی به چند Topic / Partition  
- و + Commit Offsetهای مصرف‌شده  
→ همگی به صورت **اتمی (همه یا هیچ)** انجام می‌شوند.

در این حالت Producer حالت Transactional می‌گیرد:

- `transactional.id` را تنظیم می‌کنیم  
- `initTransactions()`  
- `beginTransaction()` / `commitTransaction()` / `abortTransaction()`

درواقع Kafka تضمین می‌کند:

- اگر Transaction کامل commit نشود → هیچ یک از پیام‌های آن transaction برای مصرف‌کننده‌های عادی قابل رؤیت نیستند.
- اگر Crash شود و دوباره بالا بیاید → می‌تواند Transactionهای نیمه‌کاره را تکمیل یا abort کند.

---

## 3. ارتباط Transaction با Offset (Consume-Transform-Produce)

برای exactly-once در الگوی رایج:

```text
consume from input-topic  →  process  →  produce to output-topic
```

باید دو چیز **در یک Transaction** انجام شود:

1. پیام‌های خروجی به Topicهای مقصد  
2. و Commit Offset ورودی

این کار از طریق API transaction در Producer انجام می‌شود:

- پس Producer در Kafka می‌تواند **Offsets را هم داخل Transaction بنویسد**  
- یعنی Offset در همان Transactionی commit می‌شود که پیام‌های خروجی نوشته می‌شوند

اگر Transaction commit نشود:

- نه Offset جلو می‌رود
- نه پیام خروجی برای سایر Consumer Groups visible می‌شود

بنابراین:

- اگر برنامه Crash کند و دوباره بالا بیاید، پیام ورودی دوباره خوانده می‌شود، اما چون قبلاً Transaction موفق نداشته، دوباره پردازش و **یک بار به صورت مؤثر** روی خروجی اعمال می‌شود.

---

## رفتار از دید مصرف‌کننده‌ها

ابزار Kafka دو نوع Consumer نسبت به Transaction دارد:

- **Read-committed** (پیش‌فرض در سناریوی EOS):  
- 
  فقط پیام‌های متعلق به Transactionهای commit شده را می‌بیند.

- **Read-uncommitted**:  
  همه چیز را می‌بیند (حتی پیام‌های abort شده)، بیشتر برای دیباگ.

برای Exactly-once باید:

```text
isolation.level = read_committed
```

باشد.

---

## جاسازی این مفهوم در یک Pipeline نمونه

سناریو:  
- از `input-topic` می‌خوانیم  
- پردازش می‌کنیم  
- نتیجه را در `output-topic` می‌نویسیم  
- وقتی Exactly-once می‌خواهیم (حتی با Crash، پیام ورودی یا صفر یا دقیقاً یک بار روی خروجی منعکس شود).

مراحل:

1. Consumer از `input-topic` پیام می‌خواند (read_committed).  
2. Producer (transactional) Transaction را شروع می‌کند: `beginTransaction()`  
3. پیام جدید به `output-topic` تولید می‌کند.  
4. Offset پیام مصرف‌شده را داخل همان Transaction علامت می‌زند (`sendOffsetsToTransaction`).  
5. `commitTransaction()` → پیام خروجی + Commit Offset به صورت اتمی.

اگر بین 2 تا 5 Crash شود:

- Transaction کامل نمی‌شود → پیام‌های خروجی آن Transaction برای دیگران visible نمی‌شوند  
- Offset جلو نمی‌رود → پیام ورودی بعداً دوباره خوانده می‌شود  
- به این ترتیب، “اثر خالص” پیام روی سیستم مقصد دقیقاً یک بار خواهد بود.

## نمونه کد تقریبی در C# (الگوی Consume → Process → Produce با EOS)

فعلاً کتابخانه رسمی Confluent.Kafka برای C# از Producerهای کاملاً Transactional به گستردگی جاوا پشتیبانی محدودتری دارد، ولی من ساختار منطقی را (شبه‌کد C#) نشان می‌دهم که مفهوم را بفهمی:

```csharp
using Confluent.Kafka;

var consumerConfig = new ConsumerConfig
{
    BootstrapServers = "localhost:9092",
    GroupId = "processor-group",
    EnableAutoCommit = false,
    IsolationLevel = IsolationLevel.ReadCommitted, // مهم برای EOS
    AutoOffsetReset = AutoOffsetReset.Earliest
};

var producerConfig = new ProducerConfig
{
    BootstrapServers = "localhost:9092",
    EnableIdempotence = true,         // برای عدم تکرار
    TransactionalId = "processor-tx", // شناسه یکتا برای Transactional Producer
    Acks = Acks.All
};

using var consumer = new ConsumerBuilder<string, string>(consumerConfig).Build();
using var producer = new ProducerBuilder<string, string>(producerConfig).Build();

// مقداردهی اولیه Transaction‌ها
producer.InitTransactions();

consumer.Subscribe("input-topic");

while (true)
{
    var cr = consumer.Consume();

    // شروع یک Transaction
    producer.BeginTransaction();

    try
    {
        var inputValue = cr.Message.Value;
        var outputValue = Process(inputValue); // منطق کسب‌وکار

        // ارسال پیام خروجی در همان Transaction
        producer.Produce("output-topic", new Message<string, string>
        {
            Key = cr.Message.Key,
            Value = outputValue
        });

        // ثبت Offset مصرف‌شده در Transaction
        producer.SendOffsetsToTransaction(
            new[] { new TopicPartitionOffset(cr.TopicPartition, cr.Offset + 1) },
            consumerConfig.GroupId
        );

        // Commit اتمی Transaction (پیام + Offset)
        producer.CommitTransaction();
    }
    catch (Exception ex)
    {
        // در صورت خطا، تغییرات این Batch حذف می‌شود
        producer.AbortTransaction();
        // می‌توان Log کرد یا Retryهای بعدی را مدیریت کرد
    }
}
```

اینجا:

- اگر همه‌چیز خوب باشد → CommitTransaction  
- اگر خطا رخ دهد یا برنامه وسط کار Crash کند → آن پیام ورودی دوباره خوانده می‌شود، و Transaction ناتمام قبلی روی خروجی تأثیر دائمی نمی‌گذارد.

---

## جمع‌بندی کوتاه

Exactly-once در Kafka با ترکیب این موارد پیاده می‌شود:

1. **Idempotent Producer**  
   جلوگیری از ثبت چندباره یک پیام به خاطر Retry

2. **Transactional Producer + Transaction Log**  
   نوشتن دسته‌ای پیام‌ها به صورت اتمی (همه یا هیچ)

3. **Atomic Commit Offset + Messages**  
   Commit کردن Offset مصرف‌شده + پیام‌های خروجی در یک Transaction مشترک

4. **Read-committed Consumers**  
   فقط پیام‌های متعلق به Transactionهای موفق را می‌بینند

نتیجه:  
حتی در صورت Crash یا Retry، اثر هر پیام ورودی روی سیستم خروجی **دقیقاً یک بار** مشاهده می‌شود (از دید منطقی/کاربردی).
