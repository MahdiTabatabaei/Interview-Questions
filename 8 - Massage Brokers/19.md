در Kafka برای **افزایش تحمل خطا (Fault Tolerance)** و جلوگیری از از دست رفتن داده‌ها از مکانیزم **Replication** استفاده می‌شود. دو مفهوم مهم در این بخش:

- **Replication Factor**
- **ISR (In‑Sync Replicas)**

---

# تعریف Replication Factor چیست؟

درواقع Replication Factor مشخص می‌کند **از هر پارتیشن چند نسخه (Replica) در کلاستر نگه‌داری شود**.

مثال:

```
Topic: orders
Partitions: 1
Replication Factor: 3
```

یعنی پارتیشن 0 سه کپی دارد:

```
Partition 0
   ├─ Broker 1 → Leader
   ├─ Broker 2 → Follower
   └─ Broker 3 → Follower
```

### نقش‌ها

- **Leader Replica**
  - تمام Producerها و Consumerها فقط با Leader ارتباط دارند.

- **Follower Replica**
  - از Leader کپی می‌گیرند و خودشان را Sync نگه می‌دارند.

---

# تعریف ISR (In‑Sync Replicas) چیست؟

درواقع ISR یعنی **لیست Replicaهایی که کاملاً با Leader همگام هستند**.

یعنی Replicaهایی که:

- اطلاعات آن lag زیادی ندارند
- داده‌های Leader را تقریباً کامل دارند
- می‌توانند در صورت خرابی Leader جایگزین شوند

مثال:

```
Replication Factor = 3

Replicas:
Broker1 (Leader)
Broker2 (Follower)
Broker3 (Follower)

ISR = {Broker1, Broker2}
```

در اینجا Broker3 عقب افتاده و از ISR خارج شده است.

---

# اگر Leader از کار بیفتد چه می‌شود؟

ابزار Kafka یک Replica از **ISR** را به عنوان Leader جدید انتخاب می‌کند.

مثال:

```
Leader: Broker1
ISR: {Broker1, Broker2}
```

اگر Broker1 Crash کند:

```
Leader جدید → Broker2
```

اما اگر Replica در ISR نباشد، معمولاً اجازه Leader شدن ندارد چون ممکن است داده کم داشته باشد.

---

# ارتباط ISR با از دست رفتن داده

ابزار Kafka برای امنیت داده‌ها از تنظیمات زیر استفاده می‌کند:

### Producer `acks`

```
acks = 0
acks = 1
acks = all
```

مهم‌ترین حالت:

```
acks = all
```

یعنی:

در این حالت Producer فقط زمانی موفق محسوب می‌شود که **تمام Replicaهای داخل ISR پیام را دریافت کنند**.

---

# مثال واقعی از فرآیند نوشتن پیام

فرض کنیم:

```
Replication Factor = 3
ISR = {Broker1, Broker2}
Leader = Broker1
```

وقتی Producer پیام ارسال می‌کند:

1. ارسال پیام از Producer → Leader
2. ابتدا Leader پیام را در Log می‌نویسد
3. سپس Followerها پیام را Fetch می‌کنند
4. وقتی همه ISR پیام را گرفتند → ACK به Producer

---

# اگر Replica عقب بیفتد چه می‌شود؟

اگر یک Follower خیلی عقب بماند:

```
replica.lag.time.max.ms
```

ابزار Kafka آن را از ISR خارج می‌کند.

مثال:

```
قبل:
ISR = {1,2,3}

بعد:
ISR = {1,2}
```

وقتی دوباره Sync شود، دوباره وارد ISR می‌شود.

---

# تنظیم مهم: min.insync.replicas

این تنظیم مشخص می‌کند **حداقل چند Replica باید در ISR باشند تا Kafka اجازه Write بدهد**.

مثال:

```
replication.factor = 3
min.insync.replicas = 2
acks = all
```

نتیجه:

- اگر فقط یک Replica باقی بماند → Kafka Write را رد می‌کند
- چون امنیت داده کافی نیست

---

# یک سناریوی ساده

```
Replication Factor = 3
ISR = {1,2,3}
Leader = 1
```

وقتی Producer پیام می‌فرستد:

```
Producer → Leader(1)
1 → 2
1 → 3
```

وقتی 2 و 3 Sync شدند:

```
ACK → Producer
```

---

# خلاصه

**Replication Factor**

- تعداد کپی‌های هر Partition
- برای Fault Tolerance

**ISR**

- فقط Replicaهایی که با Leader همگام هستند
- فقط اعضای ISR می‌توانند Leader شوند

**هدف**

- جلوگیری از از دست رفتن داده
- امکان Failover سریع
- افزایش پایداری کلاستر Kafka
