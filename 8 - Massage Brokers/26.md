ویژگی **Log Compaction** در Kafka یکی از مهم‌ترین قابلیت‌ها برای نگه‌داری **آخرین مقدار** هر Key است.  
ولی برخلاف Retention معمولی که بر اساس *زمان* یا *حجم* پیام‌ها را حذف می‌کند،  
مکانیزم Compaction بر اساس **Key** کار می‌کند.

توضیح کامل و ساده:

---

# تعریف Log Compaction چیست؟

درواقع Compaction یعنی:

سیستم **Kafka برای هر Key فقط آخرین پیام را در لاگ نگه می‌دارد  
و پیام‌های قدیمی‌تر همان Key را حذف می‌کند.**

یعنی اگر پیام‌های زیر آمده باشند:

```
key=A, value=10
key=B, value=5
key=A, value=20
key=A, value=30
```

بعد از Compaction، لاگ به این شکل می‌شود:

```
key=A, value=30
key=B, value=5
```

---

# کاربرد اصلی Compaction

### **نگه‌داشتن حالت (State) از یک سیستم**

اگر Topic شما نشان‌دهنده وضعیت موجودیت‌ها باشد:

- profile user  
- موجودی حساب  
- state ماشین  
- job status  
- cache state
- configuration stream  

درواقع Compaction کمک می‌کند همیشه **آخرین وضعیت هر موجودیت** باقی بماند.

این موضوع برای ساخت **Event-driven state store**, **CDC**, **Kafka Streams State Store** یا سیستم‌هایی مثل **Debezium** حیاتی است.

---

# تفاوت با Retention معمولی


## 1) حالت Retention معمولی → مبتنی بر *زمان* یا *حجم*

مثلاً:

```
retention.ms = 7 days
retention.bytes = 1GB
```

پیام‌ها بعد از یک هفته یا بعد از پر شدن دیسک حذف می‌شوند.

## 2) حالت Compaction → مبتنی بر *Key*

مهم نیست پیام کی آمده یا چقدر حجم دارد.  
هر Key همیشه **آخرین مقدار معتبر** خود را نگه می‌دارد.

---

# نکته مهم: پیام‌ها حذف نمی‌شوند تا حدی


درواقع Compaction کاملاً پیام‌های قدیمی را پاک نمی‌کند.  
ابزار Kafka همیشه یک بخش به نام **dirty log** و **cleaned log** دارد.

فرآیند:

1. ابزار Kafka بخش‌هایی از log (segmentها) را اسکن می‌کند.
2. پیام‌های قدیمی‌تر یک key را پیدا می‌کند.
3. پیام‌های اضافی حذف می‌شوند.
4. فقط آخرین پیام باقی می‌ماند.

اما:

- مقدار offsetها تغییر نمی‌کنند  
- ترتیب کلی log دست‌نخورده می‌ماند  
- و consumerهای قدیمی هنوز می‌توانند از offsetهای قبلی بخوانند (با nullها یا tombstoneها)

---

# تعریف Tombstone چیست؟

برای حذف یک Key در Topic compaction-enabled:

ابزار Kafka از پیام با **value=null** استفاده می‌کند:

```
key = A
value = null
```

این پیام یعنی:

```
A حذف شد
```

در Compaction بعدی:

- ابزار Kafka تمام پیام‌های مربوط به آن Key را حذف می‌کند
- خود tombstone هم بعد از مدتی پاک می‌شود

---

# مثال کاربردی Compaction

### مثال ۱: آخرین وضعیت User Profile

Topic:
```
users
```

پیام‌ها:

```
key=user123, value={name: Ali, age:20}
key=user123, value={name: Ali, age:21}
key=user555, value={name: Sara, age:30}
key=user123, value={name: Ali, age:22}
```

حداکثر compaction نتایج:

```
user123 → age:22
user555 → age:30
```

---

### مثال 2: Debezium / CDC

تغییرات جدول دیتابیس را به Kafka می‌فرستد.

برای هر row از جدول، key همان primary key است.

درواقع Compaction تضمین می‌کند همیشه **آخرین نسخه هر row** موجود باشد.

---

### مثال 3: Kafka Streams State Store


در Streams برای ذخیره state داخلی خودش از **compacted topic** استفاده می‌کند  
تا بعد از ری‌استارت بتواند state را دوباره rebuild کند.

---

# چطور یک Topic را Compacted کنیم؟

تنظیم ساده:

```
cleanup.policy=compact
```

یا ترکیب:

```
cleanup.policy=compact,delete
```

که یعنی:

- اگر حجم زیاد شد → delete
- برای keyهای تکراری → compact

---

# رفتار مهمی که باید بدانید


### 1. حالت Compaction تضمین نمی‌کند که log کوچک شود  

فقط تضمین می‌کند پیام‌های تکراری key حذف شوند.

### 2. حالت Compaction لحظه‌ای نیست  

در پس‌زمینه (background) اجرا می‌شود.

### 3. حالت Compaction Ordering را حذف نمی‌کند  

ترتیب بر اساس offset حفظ می‌شود.

### 4. مقدار Topics با Compaction مناسب برای **replay کامل تاریخچه** هستند  
چون همیشه آخرین مقدار هر key موجود است.

---

# جمع‌بندی واضح

```
Retention → delete based on time/size
Compaction → delete based on key (keep last value)
```

درواقع Log Compaction برای نگه داشتن **آخرین وضعیت هر key** در Kafka استفاده می‌شود و  
برای سیستم‌های stateful و event-sourcing بسیار حیاتی است.
