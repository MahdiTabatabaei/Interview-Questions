اگر یک **Broker** از کار بیفتد، رفتار Kafka و RabbitMQ متفاوت است چون معماری و مدل replication آن‌ها فرق می‌کند. در ادامه هر دو را جدا بررسی می‌کنیم.

---

# 1. وقتی Broker در Kafka از کار بیفتد

در Kafka داده‌ها به صورت **Replication بین Brokerها** نگهداری می‌شوند.

مثال:

```
Topic: orders
Partition: 0
Replication Factor: 3
```

```
Broker1 → Leader
Broker2 → Follower
Broker3 → Follower
```

## سناریو: Leader Broker از کار بیفتد

فرض کنیم:

```
Broker1 (Leader) → Crash
```

### مرحله 1: تشخیص خرابی

در این وضعیت Controller (در KRaft یا قبلاً Zookeeper) تشخیص می‌دهد که Broker1 از دسترس خارج شده است.

### مرحله 2: انتخاب Leader جدید

ابزار Kafka از میان **ISR (In-Sync Replicas)** یک Leader جدید انتخاب می‌کند.

مثال:

```
ISR = {Broker1, Broker2}
```

بعد از Crash:

```
Leader جدید → Broker2
```

### مرحله 3: ادامه کار Producer و Consumer

- ابتدا Producerها به Leader جدید وصل می‌شوند.
- سپس Consumerها از همان Partition ادامه می‌دهند.

و Downtime معمولاً **چند صد میلی‌ثانیه تا چند ثانیه** است.

---

## اگر Follower Broker از کار بیفتد

مثال:

```
Broker3 → Crash
```

در این حالت:

- کماکان Leader همچنان فعال است
- و Producer/Consumer بدون مشکل کار می‌کنند
- فقط تعداد Replica کم می‌شود

```
ISR = {Broker1, Broker2}
```

وقتی Broker3 برگردد:

- ابزار Kafka آن را **Resync** می‌کند.

---

## اگر Replication کافی نباشد

مثال:

```
replication.factor = 1
```

اگر همان Broker از کار بیفتد:

- ابتدا Partition کاملاً از دسترس خارج می‌شود
- سپس Producer و Consumer نمی‌توانند کار کنند
- و Downtime کامل

به همین دلیل در Production معمولاً:

```
replication.factor = 3
```

استفاده می‌شود.

---

# 2. وقتی Broker در RabbitMQ از کار بیفتد

در RabbitMQ رفتار بستگی به **نوع Queue** دارد.

ابزار RabbitMQ دو مدل مهم دارد:

- Classic Queue
- Quorum Queue (مدرن)

---

# حالت 1: Classic Queue بدون Mirroring

اگر Queue فقط روی یک Broker باشد:

```
Queue → Broker1
```

اگر Broker1 Crash کند:

- دیگر Queue در دسترس نیست
- و Producer و Consumer قطع می‌شوند
- پیام‌ها ممکن است از دست بروند

این حالت برای Production مناسب نیست.

---

# حالت 2: Mirrored Queue (قدیمی)


ابزار RabbitMQ قبلاً از **Mirrored Queue** استفاده می‌کرد:

```
Queue
 ├─ Broker1 (Leader)
 ├─ Broker2 (Mirror)
 └─ Broker3 (Mirror)
```

اگر Leader Crash کند:

- یکی از Mirrorها Leader می‌شود
- سیستم ادامه می‌دهد

اما این مدل مشکلاتی داشت:

- بار Sync سنگین دارد
- و مشکل در مقیاس‌پذیری

به همین دلیل deprecated شد.

---

# حالت 3: Quorum Queue (مدرن)


ابزار RabbitMQ جدید از **Raft consensus** استفاده می‌کند.

مثال:

```
Queue replicas = 3
```

```
Broker1
Broker2
Broker3
```

یکی Leader است، بقیه Follower.

## اگر Leader Crash کند

در این حالت Raft یک Leader جدید انتخاب می‌کند.

مثال:

```
Leader → Broker1 (Crash)

Leader جدید → Broker2
```

درنتیجه Downtime کوتاه (چند صد میلی‌ثانیه).

---

# تفاوت معماری Failover

### Kafka

- ایجاد replication در سطح **partition**
- برکذاری leader election سریع
- مصرف‌کننده‌ها از log ادامه می‌دهند
- قابلیت throughput بسیار بالا

### RabbitMQ

- ایجاد replication در سطح **queue**
- نیاز به quorum برای write
- وجود latency بیشتر در replication

---

# مقایسه خلاصه

Kafka:

- Leader partition crash → انتخاب leader جدید از ISR
- Follower crash → مشکلی برای سیستم ایجاد نمی‌کند
- replication factor مهم

RabbitMQ:

- Classic queue → خرابی broker = خرابی queue
- Mirrored queue → failover ممکن
- Quorum queue → leader election با Raft

---

✅ نتیجه:

- ابزار **Kafka** برای سیستم‌های **streaming و حجم بالا** بسیار مقاوم است.  
- ابزار **RabbitMQ** برای **message routing و queue-based workloads** مناسب است ولی replication آن متفاوت است.
