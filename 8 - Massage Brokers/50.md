اگر فعال باشد:

- در این وضعیت Subscriptionها ذخیره می‌شوند
- پیام‌ها هنگام offline بودن کلاینت نگهداری می‌شوند

وقتی دوباره وصل شود پیام‌ها تحویل داده می‌شوند.

---

درواقع **Persistent Session (یا Session Persistence)** در MQTT قابلیتی است که باعث می‌شود **Broker وضعیت سشن یک Client را حتی بعد از قطع شدن اتصال نگه دارد**.

به بیان ساده:

> اگر کلاینت موقتاً قطع شود، وقتی دوباره وصل شد، می‌تواند ادامه کار قبلی‌اش را از همان‌جا انجام دهد.

---

# 🔎 اول: Session در MQTT چیست؟

وقتی یک Client به Broker وصل می‌شود، یک **Session** ایجاد می‌شود که شامل این اطلاعات است:

- اطلاعات Subscriptionها (تاپیک‌هایی که subscribe کرده)
- پیام‌های QoS 1 و QoS 2 که هنوز کامل تحویل نشده‌اند
- پیام‌های صف‌شده برای Client (وقتی آفلاین بوده)
- وضعیت handshakeهای نیمه‌تمام QoS 2

---

# 🧠 مفهوم Persistent Session یعنی چه؟

اگر Session **Persistent باشد**:

✅ سیستم Broker اطلاعات بالا را ذخیره می‌کند  
✅ اطلاعات Subscriptionها پاک نمی‌شوند  
✅ پیام‌های QoS 1 و 2 که در زمان آفلاین بودن منتشر شده‌اند ذخیره می‌شوند  
✅ بعد از reconnect، پیام‌های از دست‌رفته تحویل داده می‌شوند  

اگر Session **Non‑Persistent (Clean Session)** باشد:

❌ بعد از قطع اتصال، همه چیز پاک می‌شود  
❌ اطلاعات Subscriptionها حذف می‌شوند  
❌ پیام‌های آفلاین از بین می‌روند  

---

# ⚙️ نحوه فعال‌سازی

## ✅ در MQTT 3.1.1
از فیلد:

```
cleanSession = false
```

## ✅ در MQTT 5
از فیلد:

```
cleanStart = false
sessionExpiryInterval > 0
```

اگر `sessionExpiryInterval = 0` باشد → سشن پایدار نیست.

---

# 📌 مثال عملی

فرض کن یک دستگاه مانیتورینگ داری.

### مرحله 1 — اتصال با Persistent Session

```
ClientID = device123
cleanSession = false
```

### مرحله 2 — subscribe

```
alerts/system
```

### مرحله 3 — قطع اینترنت

دستگاه آفلاین می‌شود.

### مرحله 4 — پیام جدید منتشر می‌شود

```
alerts/system → "High CPU usage"
QoS = 1
```

چون سشن Persistent است:

✅ درواقع Broker پیام را برای device123 ذخیره می‌کند.

### مرحله 5 — اتصال مجدد

وقتی device123 دوباره وصل شود:

✅ پیام ذخیره‌شده فوراً تحویل داده می‌شود.

---

# 🆚 مقایسه Persistent vs Clean Session

| ویژگی | Clean Session | Persistent Session |
|--------|---------------|-------------------|
| نگهداری Subscription | ❌ | ✅ |
| ذخیره پیام آفلاین | ❌ | ✅ (QoS 1 & 2) |
| مناسب برای | اتصال موقت و ساده | دستگاه‌های IoT یا کلاینت‌های ناپایدار |
| مصرف منابع Broker | کم | بیشتر |

---

# ⚠️ نکات مهم

### 1️⃣ فقط پیام‌های QoS 1 و QoS 2 ذخیره می‌شوند  

درحالت QoS 0 هرگز ذخیره نمی‌شود.

---

### 2️⃣ اطلاعات ClientID باید ثابت باشد  

اگر ClientID تغییر کند، Broker آن را یک کلاینت جدید در نظر می‌گیرد.

---

### 3️⃣ ممکن است Broker محدودیت داشته باشد  

بعضی Brokerها:

- محدودیت تعداد سشن
- محدودیت زمان انقضا
- محدودیت حجم پیام‌های ذخیره‌شده

دارند.

---

# 📦 کاربردهای مهم

✅ دستگاه‌های IoT با اینترنت ناپایدار  
✅ اپلیکیشن موبایل که گاهی آفلاین می‌شود  
✅ سیستم‌هایی که از دست رفتن پیام قابل قبول نیست  

---

# 🔗 تفاوت Persistent Session با Retained Message

| Persistent Session | Retained Message |
|--------------------|------------------|
| مخصوص یک Client خاص است | برای همه Subscriberهای جدید است |
| پیام‌های آفلاین ذخیره می‌شود | فقط آخرین پیام Topic ذخیره می‌شود |
| نیاز به ClientID ثابت دارد | مستقل از Client |

---

# ✅ جمع‌بندی ساده

درواقع **Persistent Session در MQTT یعنی Broker وضعیت یک Client را نگه می‌دارد تا اگر کلاینت قطع شد و دوباره وصل شد، پیام‌ها و Subscriptionهای قبلی از بین نروند.**
