در **Entity Framework Core** برای بارگذاری رابطه‌ها (Eager Loading) از دو متد اصلی استفاده می‌شود:

1. **Include** برای بارگذاری رابطهٔ سطح اول  
2. **ThenInclude** برای بارگذاری رابطه‌های تو در تو (Nested Relations)

در ادامه یک توضیح کاملاً شفاف همراه با مثال‌های کاربردی ارائه می‌کنم.

---

## 1. Include  
برای بارگذاری یک Navigation Property ساده (One-to-Many، Many-to-One یا One-to-One) استفاده می‌شود.

مثال: کاربرها به همراه سفارش‌ها (`User → Orders`)

```csharp
var users = context.Users
    .Include(u => u.Orders)
    .ToList();
```

---

## 2. ThenInclude  
وقتی رابطهٔ شما چند لایه‌ای باشد (Nested Navigation)، پس از Include از ThenInclude استفاده می‌کنید.

مثال:  
کاربر → سفارش‌ها → آیتم‌های سفارش  
`User → Orders → OrderItems`

```csharp
var users = context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.OrderItems)
    .ToList();
```

---

## مثال با چند Relation و چندین لایه

فرض کنید مدل‌های زیر را دارید:

- User  
- Orders  
- OrderItems  
- Product  

و می‌خواهید همهٔ این زنجیره را یک‌جا لود کنید:

```csharp
var users = context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.OrderItems)
            .ThenInclude(oi => oi.Product)
    .ToList();
```

---

## Include برای Collection و Reference تفاوتی ندارد  
EF Core خودش تشخیص می‌دهد که Navigation شما:

• Reference است (مثلاً `user.Profile`)  
• Collection است (مثلاً `user.Orders`)  

پس نحوهٔ نوشتن تغییر نمی‌کند:

### رابطهٔ یک به یک (One-to-One)

```csharp
var users = context.Users
    .Include(u => u.Profile)
    .ToList();
```

---

## بارگذاری چند رابطهٔ جدا از هم (Multiple Includes)

اگر بخواهیم چند Navigation مختلف از یک موجودیت را بارگذاری کنیم:

```csharp
var users = context.Users
    .Include(u => u.Orders)
    .Include(u => u.Address)
    .Include(u => u.Roles)
    .ToList();
```

---

## ترکیب Include و ThenInclude روی چند شاخه (Parallel Navigation)

اگر Navigation مجموعه باشد، می‌توان روی همان Include چند مسیر مختلف را بارگذاری کرد.

مثال:

```csharp
var users = context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.OrderItems)
    .Include(u => u.Orders)
        .ThenInclude(o => o.ShippingInfo)
    .ToList();
```

---

## نکته مهم: استفاده از Select برای بارگذاری‌های پیچیده  
در برخی موارد بارگذاری Select-based بهتر است، چون کوئری را سبک‌تر نگه می‌دارد:

```csharp
var users = context.Users
    .Select(u => new {
        u.Id,
        u.Name,
        Orders = u.Orders.Select(o => new {
            o.Id,
            o.Price,
            Items = o.OrderItems.Select(i => new {
                i.Id,
                Product = i.Product.Name
            })
        })
    })
    .ToList();
```

---

در EF Core وقتی از `Include` و مخصوصاً `ThenInclude` استفاده می‌کنید، اگر رابطه‌های عمیق و چندشاخه داشته باشید، EF Core **به‌طور پیش‌فرض** یک *join بزرگ* تولید می‌کند. این کار می‌تواند مشکلات زیر را ایجاد کند:

• ردیف‌های تکراری فراوان (Data Duplication)  
• سنگین شدن حافظه (High Memory Usage)  
• کند شدن عملیات Materialization  
• افزایش زمان انتقال داده از SQL Server به برنامه  

اینجاست که **AsSplitQuery** وارد می‌شود و می‌تواند بسیار مؤثر باشد.

---

# درواقع AsSplitQuery چه کاری می‌کند؟

به‌جای ساختن یک کوئری غول‌پیکر با چندین join، EF Core با `AsSplitQuery` **هر Include را تبدیل به یک کوئری جداگانه** می‌کند.

مثلاً این:

```csharp
context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.OrderItems)
    .Include(u => u.Profile)
    .ToList();
```

در حالت عادی یک JOIN بزرگ می‌سازد.

اما با:

```csharp
context.Users
    .Include(u => u.Orders)
        .ThenInclude(o => o.OrderItems)
    .Include(u => u.Profile)
    .AsSplitQuery()
    .ToList();
```

برای هر مسیر Include یک کوئری جداگانه اجرا می‌شود.

---

# چقدر بهینه می‌کند؟

## 1. کاهش شدت Join Explosion
در Include های تو در تو (مثل 3–4 لایه `ThenInclude`) کوئری JOIN می‌تواند صدها هزار ردیف تولید کند.  
`AsSplitQuery` این مشکل را از بین می‌برد و حجم دادهٔ انتقال‌یافته را **تا 50–90 درصد** کاهش می‌دهد.

## 2. کاهش حافظه مصرفی
بدون SplitQuery، EF باید جدول join شده را در حافظه پردازش کند.  
در SplitQuery داده‌ها را **دسته‌دسته** دریافت می‌کند → مصرف RAM کمتر.

به‌خصوص هنگام لود Relationهای بزرگ:

• Orders  
• OrderItems  
• Products  
• Reviews  
• Addresses  
…  

به‌طور محسوس سریع‌تر می‌شود.

## 3. جلوگیری از ردیف‌های تکراری (Duplication)
اگر یک User، 10 Order و هر Order، 10 Item داشته باشد:  
JOIN ترکیب‌شده 100 ردیف تولید می‌کند—even اگر User فقط یک بار لازم باشد.  
در Split Query این اتفاق نمی‌افتد.  

## 4. پایداری و قابل پیش‌بینی بودن Query Plan
کوئری‌های بزرگ‌تر → Query Plan پیچیده‌تر  
SplitQuery → Queryهای کوچک‌تر و ساده‌تر → CPU کمتر در SQL Server

در سیستم‌های بزرگ، این **فوق‌العاده حیاتی** است.

---

# آیا همیشه بهتر است؟
نه.

### مواردی که AsSplitQuery بهتر است:
• Include / ThenInclude در چند سطح  
• Relationهای مجموعه‌ای بزرگ (Collection Navigation)  
• دیتای زیاد (مثلاً 1 کاربر و 5000 سفارش)  
• وقتی جدول‌ها بزرگ هستند و JOIN سنگین می‌شود  
• جلوگیری از OOM یا کندی شدید

### مواردی که AsSingleQuery بهتر است:
• داده بسیار کم  
• فقط شامل 1 یا 2 JOIN ساده  
• نیاز به کم کردن تعداد round-trip به DB  
• محیط‌های latency بالا (مثلاً شبکهٔ کند)

---

# بهترین قاعدهٔ عملی
اگر ERD شما مثل درخت با شاخه‌های متعدد است:

User → Orders → OrderItems → Product → Reviews  
Profile → Address → Country

در این حالت:

```
AsSplitQuery ضروری است
```

برای سناریوهایی با چندین ThenInclude (3 سطح یا بیشتر) معمولاً بهبود عملکرد **بسیار محسوس** است.

در پروژه‌های واقعی معمولاً:

• تعداد ردیف کاهش چشمگیر دارد  
• سرعت 20–60 درصد بهتر می‌شود  
• مصرف RAM تا نصف کم می‌شود

---

# نتیجه
درواقع `AsSplitQuery` مخصوصاً در سناریوهای `ThenInclude` با لایه‌های عمیق **یکی از بهترین ابزارهای بهینه‌سازی EF Core** است و در بسیاری از سیستم‌های بزرگ، فعال کردن آن تفاوت قابل توجهی ایجاد می‌کند.
