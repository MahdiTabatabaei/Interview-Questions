درواقع **Shadow Property** در EF Core یعنی ستونی در دیتابیس که در **کلاس Entity در کد وجود ندارد**، اما EF Core آن را در مدل داخلی خودش نگه می‌دارد و مدیریت می‌کند.

یعنی property فقط در **مدل EF (Model metadata / ChangeTracker)** وجود دارد، نه در کلاس C#.

---

# مثال

فرض کنید کلاس:

```csharp
public class Post
{
    public int Id { get; set; }
    public string Title { get; set; }
}
```

اما در دیتابیس می‌خواهیم یک ستون `CreatedAt` هم داشته باشیم بدون اینکه در کلاس باشد.

در `OnModelCreating`:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Post>()
        .Property<DateTime>("CreatedAt");
}
```

در اینجا:

```
CreatedAt = Shadow Property
```

چون در کلاس `Post` وجود ندارد.

---

# دسترسی به Shadow Property

چون در کلاس نیست باید از `EF.Property` استفاده کنیم.

مثال Query:

```csharp
var posts = context.Posts
    .Where(p => EF.Property<DateTime>(p, "CreatedAt") > DateTime.Now.AddDays(-7))
    .ToList();
```

یا برای set کردن:

```csharp
context.Entry(post).Property("CreatedAt").CurrentValue = DateTime.Now;
```

---

# کاربردهای رایج

Shadow property معمولاً برای این موارد استفاده می‌شود:

- **Foreign Key های مخفی**
- **Audit fields**
  - CreatedAt
  - UpdatedAt
- **Soft delete flag**
- **Multi‑tenancy**

مثال:

```csharp
modelBuilder.Entity<Post>()
    .Property<bool>("IsDeleted");
```

# چرا می‌تواند باعث سردرگمی شود؟

### 1. در کلاس وجود ندارد
کسی که کد را می‌بیند متوجه نمی‌شود که چنین ستونی وجود دارد.

مثلاً:

```
Post class -> CreatedAt ندارد
Database -> CreatedAt دارد
```

این باعث می‌شود:

- مراحل debugging سخت شود
- توسعه‌دهنده‌ها گیج شوند

---

### 2. Query نوشتن سخت‌تر می‌شود

باید از:

```csharp
EF.Property<T>()
```

استفاده شود که:

- خوانایی کمتر دارد
- باعث refactor سخت‌تر است

---

### 3. خطاهای runtime

چون property در کلاس نیست، اگر اسم را اشتباه بنویسی:

```csharp
EF.Property<DateTime>(p, "CreateAt") // typo
```

خطا **در compile-time مشخص نمی‌شود** و در runtime می‌ترکد.

---

### 4. هزینه اضافی در ChangeTracker

درواقع Shadow property ها در **ChangeTracker داخلی EF** نگهداری می‌شوند نه در object واقعی.

پس EF باید:

- باید metadata نگه دارد
- همچنین value را جدا ذخیره کند

در تعداد entity زیاد ممکن است **کمی overhead ایجاد کند**.

(البته معمولاً خیلی شدید نیست ولی در سیستم‌های بزرگ قابل توجه است.)

---

# خلاصه

**Shadow Property**:

- درواقع propertyای است که در کلاس entity وجود ندارد
- اما در مدل EF و دیتابیس وجود دارد

مزایا:

- تمیز نگه داشتن domain model
- مخفی کردن ستون‌های infrastructure

معایب:

- خوانایی کمتر
- مراحل debug سخت‌تر
- احتمال خطای runtime
- افزودن overhead در ChangeTracker
