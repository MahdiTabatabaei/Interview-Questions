استفاده از `Channel` یک ساختار **asynchronous producer-consumer queue** در .NET است که برای انتقال داده بین **Taskها یا Threadهای مختلف** طراحی شده است.

### مشکلی که حل می‌کند

وقتی چند بخش برنامه همزمان کار می‌کنند:

- یک بخش **داده تولید می‌کند** (Producer)
- یک بخش **داده مصرف می‌کند** (Consumer)

اگر مدیریت صف داده‌ها درست انجام نشود مشکلاتی ایجاد می‌شود:

- مشکل [[1 - CSharp – Language Fundamentals/61| race condition]] 
- نیاز به lock زیاد
- مشکل performance
- هماهنگی سخت بین threadها

درواقع  `Channel` این کار را **ایمن، async-friendly و بسیار سریع** انجام می‌دهد.

---

### مثال ساده
```csharp

using System.Threading.Channels;

var channel = Channel.CreateUnbounded<int>();

// Producer
_ = Task.Run(async () =>
{
    for (int i = 1; i <= 5; i++)
    {
        await channel.Writer.WriteAsync(i);
    }

    channel.Writer.Complete();
});

// Consumer
await foreach (var item in channel.Reader.ReadAllAsync())
{
    Console.WriteLine($"Received: {item}");
}

```

----

در .NET **Channel** (در `System.Threading.Channels`) یک **ابزار سطح‌بالا برای ارسال پیام (Message Passing) بین تولیدکننده‌ها و مصرف‌کننده‌ها** است؛ مخصوصاً در سناریوهای:

- چندتردی (multi-threading)
- پردازش غیرهمزمان (async/await)
- تولید و مصرف با سرعت‌های متفاوت (backpressure)
- صف‌بندی ایمن (thread‑safe queuing)

به زبان ساده:

# مفهوم Channel = صف غیرهمزمان، سریع، بدون قفل (lock‑free)، با [[back‑pressure]] 


---

# مشکل اصلی که Channel حل می‌کند چیست؟


### 1. **هماهنگی بین Producer/Consumer**

قبل از ورود Channel، معمولاً از:

- ابزار `ConcurrentQueue`
- و `BlockingCollection`
- یا lockها

استفاده می‌شد.  
اما این‌ها مشکلاتی داشتند:

- در `ConcurrentQueue` **async-friendly نیست** ⇒ مجبورید Poll کنید
- و `BlockingCollection` **مسدود‌کننده (blocking)** است ⇒ با async سازگار نیست
- همچنین lock ⇒ کند، پیچیده، مستعد deadlock

درواقع Channel این مشکلات را حل می‌کند:

- **کاملاً async** (`await channel.Reader.ReadAsync()`)
- بدون lock ⇒ **فوق‌العاده سریع**
- همچنین [[back‑pressure]] ⇒ **اگر مصرف کند باشد، تولیدکننده متوقف می‌شود**

---

# ابزار Channel دقیقاً چیست؟

یک **جفت** است:

- `Channel.Writer` → داده را می‌نویسد
- `Channel.Reader` → داده را می‌خواند

مثل یک Pipe.

```csharp
var channel = Channel.CreateUnbounded<int>();

await channel.Writer.WriteAsync(1);
int value = await channel.Reader.ReadAsync();
```

---

# مثال واقعی ساده  
### Producer → Channel → Consumer

```csharp
var channel = Channel.CreateBounded<int>(5); // ظرفیت 5

var writer = Task.Run(async () =>
{
    for (int i = 0; i < 20; i++)
    {
        await channel.Writer.WriteAsync(i);
        Console.WriteLine($"Produced: {i}");
    }

    channel.Writer.Complete();
});

var reader = Task.Run(async () =>
{
    await foreach (var item in channel.Reader.ReadAllAsync())
    {
        Console.WriteLine($"Consumed: {item}");
    }
});

await Task.WhenAll(writer, reader);
```

### نکته‌ها:
- قابلیت `CreateBounded` باعث *back‑pressure* می‌شود ⇒ اگر مصرف‌کننده کند باشد، producer هم کند می‌شود.
- قابلیت `ReadAllAsync` یک **stream غیرهمزمان** است.
- بدون lock، بدون deadlock، سرعت بسیار بالا.

# ۱۰ مشکلی که Channel حل می‌کند

### 1. **از بین بردن نیاز به lock**
نه Producer و نه Consumer به lock نیاز ندارند.

### 2. **بدون busy-waiting**
مصرف‌کننده نمی‌پرسد: «چیزی هست؟»  
بلکه **منتظر async یک آیتم می‌شود**.

### 3. **پشتیبانی از back-pressure**
اگر channel پر باشد:

- تولید کننده Producer **به صورت async صبر می‌کند**
- درنتیجه CPU بیهوده مصرف نمی‌شود

### 4. **جدا کردن تولیدکننده و مصرف‌کننده**

قابلیت Loose coupling.

تولید کننده Producer نمی‌داند چه کسی مصرف می‌کند.

### 5. **جایگزین بهتر برای BlockingCollection**

ابزار BlockingCollection قدیمی و blocking است، ولی Channel async است.

### 6. **مناسب برای High throughput**

درواقع Channel [[lock‑free]] است ⇒ سرعت بسیار بالا.

### 7. **خیلی طبیعی در async/await**

Reader:

```csharp
await foreach (...)
```

Writer:

```csharp
await channel.Writer.WriteAsync()
```

### 8. **Stops gracefully**
با `Writer.Complete()`، Consumer به صورت کنترل‌شده متوقف می‌شود.

### 9. **Thread-safe طبیعی**
بدون هزینه اضافه.

### 10. **استفاده در سناریوهای Server-side**

بهترین گزینه برای:

- Background processing
- Event streaming
- Messaging بدون نیاز به سرویس خارجی
- Logging pipelines
- Real-time processing

# سناریوی مهم: پردازش پس‌زمینه در ASP.NET Core  

درواقع Channel در فضای سرور **بسیار محبوب** است.

### مثال: صف درخواست‌ها برای Background Worker

```csharp
public class BackgroundTaskQueue
{
    private readonly Channel<Func<CancellationToken, Task>> _queue;

    public BackgroundTaskQueue()
    {
        _queue = Channel.CreateUnbounded<Func<CancellationToken, Task>>();
    }

    public ValueTask QueueAsync(Func<CancellationToken, Task> task)
        => _queue.Writer.WriteAsync(task);

    public IAsyncEnumerable<Func<CancellationToken, Task>> DequeueAsync(CancellationToken token)
        => _queue.Reader.ReadAllAsync(token);
}
```

این ساختار را مایکروسافت خودش در نمونه‌ها پیشنهاد می‌دهد.

# کی از Channel استفاده کنیم؟

### انتخاب درست است اگر:

- مصرف کننده Consumer باید async باشد
- تولید کننده Producer و Consumer سرعت متفاوت دارند
- به Throughput بالا نیاز دارید
- نمی‌خواهید lock و concurrency را خودتان مدیریت کنید
- نیاز به back-pressure دارید

### انتخاب اشتباه است اگر:

- نیاز به ذخیره‌سازی دائمی (persistent queue) دارید
→ مثال: RabbitMQ, Kafka

# خلاصه نهایی 

ابزار **Channel در .NET یک صف غیرهمزمان، بدون قفل، با پشتیبانی built‑in از back-pressure است. برای ساخت سیستم‌های Producer/Consumer سریع و ایمن استفاده می‌شود و جایگزینی مدرن برای ConcurrentQueue و BlockingCollection است.**
