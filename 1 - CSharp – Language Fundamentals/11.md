S – Single Responsibility

O – Open Closed

# 1. Single Responsibility Principle (SRP)

هر کلاس باید **فقط یک مسئولیت (reason to change)** داشته باشد.

❌ طراحی اشتباه:
```csharp

class UserService
{
    public void SaveUser(User user)
    {
        // ذخیره در دیتابیس
    }

    public void SendEmail(User user)
    {
        // ارسال ایمیل
    }
}

```

این کلاس **دو مسئولیت** دارد:

- ذخیره کاربر
- ارسال ایمیل

✅ طراحی صحیح:

```csharp

class UserRepository
{
    public void Save(User user)
    {
        // ذخیره در دیتابیس
    }
}

class EmailService
{
    public void SendEmail(User user)
    {
        // ارسال ایمیل
    }
}

```

حالا هر کلاس **یک مسئولیت** دارد.

# 2. Open / Closed Principle (OCP)

کلاس باید:

- **برای توسعه باز باشد**
- **برای تغییر بسته باشد**

یعنی بدون تغییر کد قبلی بتوانیم قابلیت جدید اضافه کنیم.

❌ مثال بد:

```csharp

class Discount
{
    public double Calculate(string type, double price)
    {
        if(type == "Regular")
            return price * 0.1;

        if(type == "VIP")
            return price * 0.2;

        return 0;
    }
}

```

اگر نوع جدید اضافه شود باید کد را تغییر دهیم.

✅ مثال درست:

```csharp

interface IDiscount
{
    double Calculate(double price);
}

class RegularDiscount : IDiscount
{
    public double Calculate(double price)
    {
        return price * 0.1;
    }
}

class VipDiscount : IDiscount
{
    public double Calculate(double price)
    {
        return price * 0.2;
    }
}

```

حالا اگر نوع جدید اضافه شود فقط یک کلاس جدید می‌سازیم.

# 3. Liskov Substitution Principle (LSP)

کلاس فرزند باید بتواند **بدون مشکل جایگزین کلاس پدر شود**.
> هر جایی که از یک **کلاس پایه (Base Class)** استفاده می‌کنیم باید بتوانیم **کلاس فرزند (Derived Class)** را بدون خراب شدن رفتار برنامه جایگزین آن کنیم.

یعنی **کد مصرف‌کننده نباید بفهمد شیء واقعی از نوع فرزند است.**

❌ مثال بد:
```csharp

class Bird
{
    public virtual void Fly()
    {
    }
}

class Ostrich : Bird
{
    public override void Fly()
    {
        throw new Exception("Ostrich can't fly");
    }
}


```

فرض کن یک متد داریم که با **Bird** کار می‌کند:
```csharp

void MakeBirdFly(Bird bird)
{
    bird.Fly();
}

```
حالا استفاده:
```csharp

MakeBirdFly(new Bird());      // OK
MakeBirdFly(new Sparrow());   // OK
MakeBirdFly(new Ostrich());   // 💥 Exception

```
اینجا **Ostrich** نمی‌تواند درست جایگزین **Bird** شود.

مشکل اینجاست:

کدی که با **Bird** نوشته شده انتظار دارد **هر Bird بتواند پرواز کند**.

اما **Ostrich نمی‌تواند** و برنامه crash می‌کند.

پس **Ostrich جایگزین معتبری برای Bird نیست** → نقض LSP.

# طراحی درست‌تر

مشکل اصلی این است که ما **یک رفتار اشتباه را در کلاس پایه گذاشته‌ایم**.

همه پرنده‌ها پرواز نمی‌کنند.

پس باید رفتارها را جدا کنیم.

✅ طراحی بهتر:

```csharp

interface IFlyable
{
    void Fly();
}

class Sparrow : IFlyable
{
    public void Fly()
    {
    }
}

class Ostrich
{
}

```
![[11_LSP_01.png]]
این عکس انواع مختلف **رفتار زیرنوع‌ها (Subtypes)** نسبت به نوع پایه (Base Type) را نشان می‌دهد:

### ۱. **Covariant Return Type** (هم‌متغیری نوع بازگشتی)

```csharp
public class AnimalShelter {
    public Cat Get() {}
}
public class CatShelter : AnimalShelter {
    public Cat Get() {}
}
```
➡ **نوع بازگشتی در زیرنوع، هم‌متغیر (Covariant) است** – می‌تواند زیرنوع نوع بازگشتی پدر باشد.
### ۲. **Covariant Method Argument** (آیا درست است؟ خیر)

```csharp
public class AnimalShelter {
    public void PutAnimal(Animal animal) {}
}
public class CatShelter : AnimalShelter {
    public void PutAnimal(Cat cat) {}
}
```
➡ این یک **اشتباه** است.  
چرا؟ چون آرگومان ورودی را **خاص‌تر** کرده‌ایم (Animal → Cat) در حالی که باید عام‌تر یا همانند باشد. این نقض LSP است.
### ۳. **Contravariant Return Type** (آیا درست است؟ خیر)


```csharp
public class AnimalShelter {
    public void PutAnimal(Animal animal) {}
}
public class Shelter : AnimalShelter {
    public void PutAnimal(Object animal) {}
}
```
➡ نوع بازگشتی در اینجا معنا ندارد (چون void است) – احتمالاً تصویر در جای دیگر توضیح متفاوتی دارد.  
اما **در روش عمومی**: بازگشتی را نمی‌توان عام‌تر از نوع پدر کرد (نقض LSP).

### ۴. **Contravariant Method Argument** (درست)


```csharp
public class AnimalShelter {
    public void PutAnimal(Animal animal) {}
}
public class Shelter : AnimalShelter {
    public void PutAnimal(Object animal) {}
}
```
➡ **آرگومان ورودی، عام‌تر** شده (Animal → Object).  
این در LSP مجاز است و به آن **Contravariance** گفته می‌شود.

![[11_LSP_02.png]]
- **  
    کونتراواریانس/Contravariance** (ناهمتغیری) پارامترهای ورودی در زیرنوع ✅
    
- کوواریانس/**Covariance** (هم‌متغیری) نوع بازگشتی در زیرنوع ✅
    
- استثناها/**Exception**:  
    زیرنوع نباید استثناهای جدیدی پرتاب کند، مگر آنکه خود آن استثنا زیرنوعی از استثناهای متد پدر باشد.
    
- **Precondition** (پیش‌شرط):  
    نمی‌تواند در زیرنوع **قوی‌تر** شود.  
    (یعنی نمی‌توان محدودیت بیشتری به ورودی اضافه کرد)
    
- **Postcondition** (پس‌شرط):  
    نمی‌تواند در زیرنوع **ضعیف‌تر** شود.  
    (یعنی باید حداقل همان تضمین‌ها را بدهد یا بیشتر)
    
- **Invariant** (ناوردا/ثابت):  
    تمام قوانین و روابط ثابت کلاس پایه باید در زیرنوع حفظ شود.
###   
🟢 Covariance (هم‌متغیری) – برای نوع خروجی

```csharp
class Animal { }
class Cat : Animal { }
class AnimalShelter {
    public virtual Animal GetAnimal() { return new Animal(); }
}
class CatShelter : AnimalShelter {
    public override Cat GetAnimal() { return new Cat(); } // ✅ مجاز
}
```

✅ این درست است:  
هرجا AnimalShelter انتظار می‌رود، CatShelter می‌تواند جایگزین شود و **نوع خاص‌تری برگرداند**.

---
### 🟢 Contravariance (ناهمتغیری) – برای نوع ورودی

```csharp
class Animal { }
class Cat : Animal { }
class AnimalShelter {
    public virtual void Put(Animal a) { }
}
class AdvancedShelter : AnimalShelter {
    public override void Put(object o) { } // ✅ مجاز
}
```

✅ این درست است:  
اگر کدی قرار است `Animal` بدهد، می‌تواند به متدی که `object` می‌گیرد هم بدهد.  
شرط ورودی سخت‌گیرانه‌تر نشده است.

---
### ❌ مثال نقض LSP (پیش‌شرط قوی‌تر)

```csharp
class AnimalShelter {
    public virtual void Put(Animal a) { }
}
class CatShelter : AnimalShelter {
    public override void Put(Animal a) {
        if (!(a is Cat)) throw new Exception("فقط گربه"); // ❌ نقض
    }
}
```

✅ درست: باید هر Animalای را بپذیرد.

---
### ✅ مثال حفظ Invariant

فرض کنید کلاس پایه تضمین می‌کند `Count >= 0`.  
زیرنوع هم باید این قانون را حفظ کند.

## خلاصه طلایی LSP

> هر نمونه از زیرنوع باید بتواند به جای نمونه‌ای از نوع پایه قرار گیرد بدون اینکه رفتار برنامه تغییر غیرمنتظره‌ای کند.

| قانون   | معنی ساده                                |
| ------- | ---------------------------------------- |
| ورودی   | باید **عام‌تر** یا همان (Contravariance) |
| خروجی   | باید **خاص‌تر** یا همان (Covariance)     |
| پیش‌شرط | نمی‌تواند سخت‌گیرانه‌تر شود              |
| پس‌شرط  | نمی‌تواند ضعیف‌تر شود                    |
| استثنا  | فقط زیرنوع استثناهای پدر مجاز است        |
اگر این قوانین رعایت شوند، چندریختی (Polymorphism) به درستی کار می‌کند و برنامه ما در برابر تغییرات مقاوم خواهد بود.

# 4. Interface Segregation Principle (ISP)

یک کلاس نباید مجبور شود متدهایی را پیاده‌سازی کند که به آنها نیاز ندارد.

❌ مثال بد:

```csharp

interface IWorker
{
    void Work();
    void Eat();
}

```

اگر یک **Robot** داشته باشیم:

```csharp

class Robot : IWorker
{
    public void Work() { }

    public void Eat()
    {
        throw new NotImplementedException();
    }
}

```

✅ طراحی بهتر:

```csharp

interface IWorkable
{
    void Work();
}

interface IEatable
{
    void Eat();
}

```

# 5. Dependency Inversion Principle (DIP)

کلاس‌ها نباید به **Concrete Class** وابسته باشند بلکه باید به **Abstraction** وابسته باشند.

❌ مثال بد:
```csharp

class OrderService
{
    EmailService emailService = new EmailService();

    public void CreateOrder()
    {
        emailService.Send();
    }
}

```

✅ مثال درست:

```csharp

interface IMessageService
{
    void Send();
}

class EmailService : IMessageService
{
    public void Send()
    {
    }
}

class OrderService
{
    private IMessageService messageService;

    public OrderService(IMessageService messageService)
    {
        this.messageService = messageService;
    }
}

```

اینجا وابستگی به **Interface** است.

# جمع‌بندی 
- **SRP** → هر کلاس فقط یک مسئولیت داشته باشد
- **OCP** → کلاس برای توسعه باز و برای تغییر بسته باشد
- **LSP** → کلاس فرزند باید قابل جایگزینی با کلاس والد باشد
- **ISP** → Interfaceها باید کوچک و تخصصی باشند
- **DIP** → وابستگی باید به Abstraction باشد نه Concrete Class [[Concrete Class]]
