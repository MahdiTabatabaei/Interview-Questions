اصل **YAGNI** مخفف:

> **You Aren’t Gonna Need It**  
> یعنی: **«فعلاً بهش نیاز نداری»**

این اصل می‌گوید:

> چیزی را فقط وقتی پیاده‌سازی کن که واقعاً به آن نیاز فعلی وجود دارد، نه صرفاً چون شاید بعداً لازم شود.

---

## منظورش دقیقاً چیست؟

خیلی وقت‌ها برنامه‌نویس وسوسه می‌شود امکاناتی اضافه کند مثل:

- «شاید بعداً چندزبانه شد»
- «شاید بعداً چند نوع دیتابیس خواستیم»
- «شاید بعداً این ماژول عمومی شد»
- «بذار از الان کلی abstraction بسازم»

اصل YAGNI می‌گوید:

> تا وقتی نیاز واقعی و مشخصی نداری، این چیزها را نساز.

---

## چرا این اصل مهم است؟

چون پیاده‌سازی قابلیت‌های غیرضروری معمولاً باعث می‌شود:

- ❌ کد پیچیده‌تر شود
- ❌ زمان توسعه بیشتر شود
- ❌ نگهداری سخت‌تر شود
- ❌ تست‌نویسی بیشتر و بی‌دلیل شود
- ❌ احتمال باگ بالا برود
- ❌ تمرکز از نیاز اصلی محصول برداشته شود

---

## مثال ساده

فرض کن فقط یک روش ارسال پیامک داری، اما از اول این ساختار را می‌سازی:

```csharp
public interface IMessageSender
{
    void Send(string message);
}

public class SmsSender : IMessageSender
{
    public void Send(string message)
    {
        Console.WriteLine("Sending SMS: " + message);
    }
}
```

اگر واقعاً فقط SMS داری و هیچ نیازی به چند provider یا چند کانال نیست، شاید این abstraction فعلاً اضافی باشد.

### نسخه ساده‌تر:

```csharp
public class SmsSender
{
    public void Send(string message)
    {
        Console.WriteLine("Sending SMS: " + message);
    }
}
```

یعنی:
- الان نیاز واقعی را حل کن
- اگر بعداً نیاز به abstraction بود، آن زمان اضافه‌اش کن

---

## اصل YAGNI یعنی آینده‌نگر نباشیم؟

نه، معنی‌اش این نیست که طراحی بد انجام بدهیم.  
بلکه یعنی:

- **برای نیاز واقعی امروز طراحی کن**
- نه برای سناریوهای فرضی و احتمالی فردا

---

## تفاوت YAGNI با DRY

| اصل | مفهوم |
|------|-------|
| DRY | تکرار نکن |
| YAGNI | چیزی که هنوز لازم نیست نساز |

گاهی برنامه‌نویس برای فرار از تکرار، خیلی زود abstraction می‌سازد؛  
اینجا ممکن است **DRY را زیاده‌روی کند و YAGNI را نقض کند**.

---

## یک مثال واقعی از نقض YAGNI

فرض کن پروژه فعلاً فقط:
- یک نوع کاربر دارد
- یک روش پرداخت دارد
- یک زبان دارد

ولی تو از اول می‌سازی:
- سیستم نقش و permission خیلی پیچیده
- payment gateway abstraction برای ۵ درگاه
- localization کامل چندزبانه
- plugin architecture

در حالی که محصول هنوز MVP هم نشده.  
این دقیقاً جایی است که YAGNI هشدار می‌دهد.

---

## جمع‌بندی

اصل YAGNI می‌گوید:

> **چیزی را فقط وقتی بساز که نیازش ثابت شده باشد.**

نه وقتی:
- حدس می‌زنی شاید روزی لازم شود
- می‌خواهی کدت «خیلی حرفه‌ای» به نظر برسد
- می‌خواهی از اول برای همه آینده‌ها آماده باشی
