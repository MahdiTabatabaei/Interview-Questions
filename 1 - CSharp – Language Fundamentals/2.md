هر دو برای **قرارداد (contract)** در طراحی استفاده می‌شوند.

---

## Interface

فقط **تعریف متدها** را دارد.
## مثال : 
```csharp

interface IAnimal
{
    void Speak();
}

```
پیاده‌سازی:
```csharp

class Dog : IAnimal
{
    public void Speak()
    {
        Console.WriteLine("Bark");
    }
}

```
ویژگی‌ها:

- فقط تعریف
- چندین interface قابل پیاده‌سازی
- هیچ implementation ندارد (در نسخه‌های جدید کمی دارد)

---

## Abstract Class

می‌تواند **متد پیاده‌سازی شده و نشده** داشته باشد.

## مثال :
```csharp

abstract class Animal
{
    public abstract void Speak();

    public void Sleep()
    {
        Console.WriteLine("Sleeping");
    }
}

```

پرسش چه زمانی میتوان از abstract class استفاده کرد و چه زمانی از اینترفیس :

- وقتی از کلاس انتزاعی (abstract class) استفاده کن که:
  - می‌خواهی بخشی از رفتار مشترک را یک‌بار پیاده‌سازی کنی و به ارث برسد.
  - نیاز به state یا فیلدهای مشترک، protected helperها، یا lifecycle مشترک داری.
  - می‌خواهی قرارداد + پیاده‌سازی پیش‌فرض برخی متدها را با هم بدهی.
  - سلسله‌مراتب ارث‌بری معنادار است و از محدودیت «یک ارث‌بری» مشکلی نداری.

- وقتی از اینترفیس استفاده کن که:
  - فقط به «قرارداد» نیاز داری و پیاده‌سازی را به کلاس‌های مختلف می‌سپاری.
  - می‌خواهی چندین قرارداد را هم‌زمان روی یک کلاس اعمال کنی (multiple inheritance of type).
  - زمانی که coupling کم‌تری می‌خواهی و تست‌پذیری/انعطاف مهم‌تر است.
  - امکان اشتراک کد برایت حیاتی نیست یا می‌توانی با ترکیب (composition) حل کنی.

نکته‌های مهم با توجه به C# مدرن:

- Default interface methods (از C# 8 به بعد): اینترفیس می‌تواند پیاده‌سازی پیش‌فرض هم داشته باشد. اما:
  - برای اشتراک کد ساده و قرارداد سبک خوب است، ولی
  - برای منطق پیچیده، نگه‌داری state، یا الگوهای ارث‌بری سنتی، هنوز abstract class تمیزتر و قابل‌پیش‌بینی‌تر است.
  - پیاده‌سازی پیش‌فرض در اینترفیس‌ها می‌تواند خوانایی و دیباگ را سخت‌تر کند، به‌خصوص اگر چند اینترفیس با پیاده‌سازی پیش‌فرض تداخل داشته باشند.

- ترکیب (Composition) را فراموش نکن:
  - اگر چند کلاس باید منطق مشترک را دقیقاً یکسان به‌کار ببرند اما سلسله‌مراتب ارث‌بری مناسب نیست، یک سرویس/هِلپر بساز و آن را تزریق کن. این کار از قفل شدن در ارث‌بری جلوگیری می‌کند.

الگوی تصمیم‌گیری سریع
- فقط قرارداد لازم است؟ اینترفیس.
- قرارداد + کد مشترک ساده و بدون state؟ یا default method در اینترفیس یا abstract class سبک؛ اگر کد زیاد/پیچیده شد، abstract class بهتر.
- قرارداد + کد مشترک با state/محافظت‌شده‌ها/الگوی قالب (Template Method)؟ abstract class.
- نیاز به چند قرارداد هم‌زمان؟ اینترفیس‌ها (و اگر کد مشترک لازم شد، آن را در یک کلاس کمکی ترکیب کن).

نمونه کوتاه

1) وقتی قرارداد صرف می‌خواهی:
```csharp
public interface IExporter
{
    Task ExportAsync(Stream output);
}
```

2) وقتی قرارداد + اسکلت مشترک با state و الگوی قالب می‌خواهی:
```csharp
public abstract class ExporterBase : IExporter
{
    protected readonly ILogger Logger;
    protected ExporterBase(ILogger logger) => Logger = logger;

    public async Task ExportAsync(Stream output)
    {
        Logger.LogInformation("Start");
        await WriteHeaderAsync(output);
        await WriteBodyAsync(output);
        await WriteFooterAsync(output);
        Logger.LogInformation("Done");
    }

    protected abstract Task WriteHeaderAsync(Stream output);
    protected abstract Task WriteBodyAsync(Stream output);
    protected virtual Task WriteFooterAsync(Stream output) => Task.CompletedTask;
}
```

3) وقتی می‌خواهی قرارداد سبک اما کمی رفتار پیش‌فرض هم داشته باشی (C# 8+):
```csharp
public interface IRetryable
{
    Task ExecuteAsync(Func<Task> action, int retries = 3);

    // default implementation
    async Task IRetryable.ExecuteAsync(Func<Task> action, int retries)
    {
        for (int i = 0; i < retries; i++)
        {
            try { await action(); return; }
            catch when (i < retries - 1) { /* swallow and retry */ }
        }
    }
}
```
هشدار: این سبک برای منطق مهم/پیچیده توصیه نمی‌شود.

جمع‌بندی
- اگر «پیاده‌سازی یکسان» و «ساختار مشترک با state و hookها» واقعاً نیاز است، کلاس ابسترکت انتخاب طبیعی است.
- اگر فقط «امضای متدها» مشترک است و می‌خواهی آزادی عمل و چند قرارداد داشته باشی، اینترفیس مناسب‌تر است.
- برای اشتراک کد بدون ارث‌بری، ترکیب را در نظر بگیر.
