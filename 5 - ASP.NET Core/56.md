**چرا Singleton برای سرویس‌های Stateless مناسب است؟**

وقتی یک سرویس **stateless** است یعنی هیچ وضعیت (state) وابسته به درخواست یا کاربر را داخل خودش نگه نمی‌دارد. بنابراین یک نمونه از آن می‌تواند برای همه درخواست‌ها استفاده شود.

مزایا:

- **کاهش مصرف حافظه**: فقط یک instance ساخته می‌شود و بین همه استفاده‌کنندگان share می‌شود.
- **کاهش هزینه ساخت object**: اگر ساخت object سنگین باشد (مثل initialization یا اتصال به resourceها)، Singleton باعث می‌شود فقط یک بار ساخته شود.
- قابلیت **Thread-safe بودن ساده‌تر**: چون state ندارد، چند thread می‌توانند بدون تداخل از همان instance استفاده کنند.
- **کارایی بهتر در DI containers**: در فریم‌ورک‌هایی مثل ASP.NET Core سرویس‌های stateless معمولاً به صورت Singleton رجیستر می‌شوند چون lifecycle ساده‌تری دارند.

مثال از سرویس‌های مناسب برای Singleton:

- Logger
- Mapper
- Configuration reader
- Validation services
- Utility services

این‌ها معمولاً فقط **input می‌گیرند و output می‌دهند** بدون نگه داشتن state.

---

**چرا نباید همه چیز Singleton باشد؟**

اگر همه چیز Singleton شود مشکلات جدی ایجاد می‌شود:

### 1. مشکل State مشترک

اگر سرویس state داشته باشد، همه درخواست‌ها آن state را share می‌کنند.

مثال بد:

```
class ShoppingCartService {
    List<Item> items;
}
```

اگر این Singleton باشد، همه کاربران یک سبد خرید مشترک خواهند داشت.

---

### 2. مشکلات Thread Safety

سرویس‌های stateful در محیط multi-thread ممکن است race condition ایجاد کنند.

مثال:

```
counter++
```

چند thread ممکن است همزمان مقدار را تغییر دهند و نتیجه غلط شود.

---

### 3. مشکل Lifecycle وابستگی‌ها

در DI قانونی مهم وجود دارد:

در.اقع **Singleton نباید به Scoped وابسته باشد.**

مثال در ASP.NET Core:

```
Singleton -> Scoped (DbContext)
```

این باعث خطای runtime یا رفتار غیرقابل پیش‌بینی می‌شود.

---

### 4. سخت‌تر شدن تست

سرویس Singletonها معمولاً **shared global state** ایجاد می‌کنند که:

- تست‌ها به هم وابسته می‌شوند
- برای mock کردن سخت‌تر می‌شود

---

### 5. نگه داشتن resource برای مدت طولانی

اگر Singleton منابعی مثل connection یا memory cache نامناسب نگه دارد، ممکن است:

- memory leak
- resource exhaustion

ایجاد شود.

---

✅ **قاعده عملی خوب:**

- **Singleton** → سرویس‌های *stateless و thread-safe*
- **Scoped** → چیزهایی که به request وابسته‌اند (مثل `DbContext`)
- **Transient** → objectهای سبک و کوتاه‌عمر
