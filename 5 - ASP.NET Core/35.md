### Liveness

آیا برنامه **زنده است؟**

---

### Readiness

آیا برنامه **آماده سرویس‌دهی است؟**

در سیستم‌های مدرن مثل **Docker** و **Kubernetes** دو نوع مهم Health Check وجود دارد:

# 1) Liveness Probe  
# 2) Readiness Probe  

هرکدام هدف متفاوتی دارند؛ دانستن تفاوت آن‌ها برای جلوگیری از ریست‌های اشتباه و Down شدن سرویس بسیار مهم است.

---

# 1️⃣ Liveness چیست؟  
**برای اینکه بفهمیم اپلیکیشن زنده است یا نه.**

اگر Liveness شکست بخورد، Orchestrator (مثل Kubernetes) فکر می‌کند برنامه **قفل شده یا کرش کرده** و آن را **ری‌استارت می‌کند**.

کاربرد:

- تشخیص Deadlock  
- تشخیص Crash  
- تشخیص هنگ کردن برنامه  
- جلوگیری از سرویس‌هایی که بالا هستند ولی پاسخگو نیستند  

به عبارت ساده:

- اگر **Liveness fail شود → Pod ری‌استارت می‌شود**

---

# 2️⃣ Readiness چیست؟  
**برای اینکه بفهمیم اپلیکیشن آماده‌ی سرویس‌دهی است یا نه.**

اگر Readiness شکست بخورد:

- سرویس از Load Balancer جدا می‌شود  
- اما **ری‌استارت نمی‌شود**

کاربرد:

- برنامه هنوز warm-up نشده  
- دیتابیس وصل نشده  
- Cache Load نشده  
- dependency ها آماده نیستند  

به عبارت ساده:

- اگر **Readiness fail شود → ترافیک قطع می‌شود، ولی برنامه همچنان زنده می‌ماند**

---

# تفاوت خلاصه

| ویژگی | Liveness | Readiness |
|------|----------|-----------|
| هدف | آیا برنامه زنده است؟ | آیا برنامه آماده سرویس‌دهی است؟ |
| در صورت Fail | ری‌استارت می‌شود | از ترافیک کنار گذاشته می‌شود |
| کاربرد | کشف Hang/Crash | مدیریت Warm-up و وابستگی‌ها |
| رفتار در Kubernetes | `restart` | `stop receiving traffic` |

---

# تشبیه ساده

- Liveness = «آیا فرد زنده است؟»
- Readiness = «آیا فرد آماده پاسخگویی است؟»

ممکن است زنده باشد ولی هنوز آماده‌ی کار نباشد!

---

# استفاده در ASP.NET Core

معمولاً دو endpoint جدا تعریف می‌کنیم:

```csharp
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => false // فقط برای چک‌ کردن اینکه برنامه زنده است
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => true // همه health checks اجرا می‌شوند
});
```

توضیح:

- در Liveness معمولاً هیچ چکی انجام نمی‌دهیم (فقط اینکه برنامه Hang نکرده)
- در Readiness بررسی واقعی مثل DB، Redis، API انجام می‌دهیم

---
یک نمونه واقعی در **ASP.NET Core** که سه وابستگی مهم را بررسی می‌کند:

- SQL Server  
- Redis  
- External API  

و همچنین **Liveness** و **Readiness** را جدا می‌کند.

# 1️⃣ نصب پکیج‌های لازم

```bash
dotnet add package AspNetCore.HealthChecks.SqlServer
dotnet add package AspNetCore.HealthChecks.Redis
dotnet add package AspNetCore.HealthChecks.Uris
```

---

# 2️⃣ تنظیم Program.cs

```csharp
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Microsoft.Extensions.Diagnostics.HealthChecks;

var builder = WebApplication.CreateBuilder(args);

var configuration = builder.Configuration;

builder.Services.AddHealthChecks()

    // SQL Server
    .AddSqlServer(
        connectionString: configuration.GetConnectionString("DefaultConnection"),
        name: "sql",
        failureStatus: HealthStatus.Unhealthy,
        tags: new[] { "ready" })

    // Redis
    .AddRedis(
        configuration.GetConnectionString("Redis"),
        name: "redis",
        failureStatus: HealthStatus.Unhealthy,
        tags: new[] { "ready" })

    // External API
    .AddUrlGroup(
        new Uri("https://api.github.com"),
        name: "external-api",
        failureStatus: HealthStatus.Degraded,
        tags: new[] { "ready" });

var app = builder.Build();


// Liveness → فقط بررسی می‌کند برنامه بالا است
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});


// Readiness → وابستگی‌ها را بررسی می‌کند
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.Run();
```

# 5️⃣ استفاده در Kubernetes

مثال در deployment:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /health/ready
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 5
```

رفتار:

- اگر **live fail شود → Pod restart**
- اگر **ready fail شود → ترافیک قطع**

این بخش از **Kubernetes Deployment YAML** مشخص می‌کند که Kubernetes چگونه سلامت یک **Pod/Container** را بررسی کند.

دو نوع بررسی تعریف شده:

- `livenessProbe`
- `readinessProbe`

هر دو با درخواست HTTP به endpointهای برنامه شما (`/health/live` و `/health/ready`) وضعیت را بررسی می‌کنند.

---

# تعریف livenessProbe چیست؟

هدف: بررسی اینکه **اپلیکیشن هنوز زنده است یا نه**.

اگر این probe چند بار پشت سر هم fail شود، Kubernetes فرض می‌کند برنامه **hang کرده یا crash شده** و container را **restart می‌کند**.

مثال شما:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 80
  initialDelaySeconds: 10
  periodSeconds: 10
```

معنی پارامترها:

- `httpGet`  
  Kubernetes یک HTTP request می‌فرستد.

- `path: /health/live`  
  endpoint که بررسی می‌شود.

- `port: 80`  
  پورتی که برنامه روی آن اجرا شده.

- `initialDelaySeconds: 10`  
  بعد از بالا آمدن container، **10 ثانیه صبر می‌کند** و بعد اولین health check را انجام می‌دهد.

- `periodSeconds: 10`  
  هر **10 ثانیه یکبار** health check اجرا می‌شود.

اگر endpoint پاسخ **200** بدهد → healthy  
اگر خطا بدهد → unhealthy

در صورت fail شدن چند بار پشت سر هم → **container restart**

---

# تعریف readinessProbe چیست؟

هدف: بررسی اینکه **آیا برنامه آماده دریافت ترافیک هست یا نه**.

اگر این probe fail شود:

- خود Pod **ری‌استارت نمی‌شود**
- فقط از **Load Balancer خارج می‌شود**

مثال:

```yaml
readinessProbe:
  httpGet:
    path: /health/ready
    port: 80
  initialDelaySeconds: 5
  periodSeconds: 5
```

معنی:

- بعد از **5 ثانیه** اولین بررسی انجام می‌شود
- هر **5 ثانیه** تکرار می‌شود

اگر fail شود:

ابزار Kubernetes این Pod را از لیست endpointهای سرویس حذف می‌کند.

یعنی:

```
Service → دیگر درخواست به این Pod نمی‌فرستد
```

اما container هنوز در حال اجرا است.

---

# یک سناریوی واقعی

فرض کن اپلیکیشن ASP.NET Core داری که:

- SQL Server دارد
- Redis دارد
- External API دارد

وقتی container بالا می‌آید:

1️⃣ برنامه start می‌شود  
2️⃣ ارتباط connection به DB برقرار می‌شود  
3️⃣ و مقدار cache load می‌شود  

در این زمان:

- برنامه **زنده است** ✅  
- ولی هنوز **آماده سرویس نیست** ❌  

پس:

```
liveness = OK
readiness = Fail
```

نتیجه:

- سرویس container restart نمی‌شود
- ولی هنوز request دریافت نمی‌کند

وقتی همه dependencyها آماده شدند:

```
readiness = OK
```

ابزار Kubernetes شروع می‌کند به ارسال ترافیک.

---

# تفاوت رفتار در failure

اگر **liveness fail شود**

```
Kubernetes → restart container
```

اگر **readiness fail شود**

```
Kubernetes → stop routing traffic
```

---

# چرا هر دو لازم هستند؟

اگر فقط liveness داشته باشی:

مشکل:

- وقتی DB قطع شود container restart می‌شود
- درواقع restartهای بی‌دلیل رخ می‌دهد

اگر فقط readiness داشته باشی:

مشکل:

- اگر برنامه deadlock شود restart نمی‌شود

پس بهترین practice:

```
Liveness → detect crash/hang
Readiness → detect dependency issues
```

---

# جریان واقعی در Kubernetes

```
Client
   ↓
Service
   ↓
Ready Pods فقط
   ↓
Container
```

اگر readiness fail شود:

```
Pod از Service حذف می‌شود
```

---

✅ خلاصه:

- `livenessProbe` → آیا برنامه زنده است؟ → در صورت fail **restart**
- `readinessProbe` → آیا آماده سرویس است؟ → در صورت fail **قطع ترافیک**


---

✅ این معماری در Production رایج است چون:

- از restartهای بی‌دلیل جلوگیری می‌کند  
- وابستگی‌ها را مانیتور می‌کند  
- با Kubernetes / Docker / LoadBalancer سازگار است
