

**READ COMMITTED SNAPSHOT (RCSI)**

سطح Read Committed را به نسخه‌برداری (Versioning) تبدیل می‌کند.

فقط Queryهای Read از نسخه قدیمی استفاده می‌کنند.

**Snapshot Isolation (SI)**

برای کل تراکنش نسخه داده را حفظ می‌کند.

هر تراکنش “تصویر ثابتی” از داده‌ها دارد حتی طولانی باشد.

مثال

RCSI = عکس لحظه‌ای بگیری و بخوانی

SI = یک ویدئو دانلود شده داری و تا آخر دیدن، تغییر نمی‌کند

---

 این دو گزینه در SQL Server خیلی شبیه به هم به نظر می‌رسند (هر دو از **Versioning در TempDB** استفاده می‌کنند و **قفل خواندن (Shared Locks)** را حذف می‌کنند)، اما در واقع **رفتار تراکنشی و کاربردشان کاملاً متفاوت است**.  
بیایید با دقت و مثال تفاوتشان را ببینیم 👇

---

## 🔹 شباهت‌ها (نقطه‌ی مشترک کلی)

| ویژگی | توضیح |
|--------|--------|
| مبنا | هر دو از **row versioning** در `tempdb` استفاده می‌کنند. |
| هدف | جلوگیری از **Reader–Writer Blocking** (خواندن بدون قفل شدن توسط writers). |
| قفل‌ها | در هر دو، تراکنش‌های خواننده معمولاً **Shared Lock** نمی‌گیرند. |
| داده خوانده‌شده | داده‌ی **Commit‌شده** می‌خوانند (نه داده‌ی در حال تغییر). |

---

## 🔸 تفاوت اصلی در سطح تأثیر و رفتار تراکنش‌ها

| ویژگی | **READ COMMITTED SNAPSHOT (RCSI)** | **SNAPSHOT ISOLATION (SI)** |
|---------|----------------------------------|-----------------------------|
| **سطح ایزولیشن** | جایگزین **Read Committed** فعلی برای تمام کوئری‌ها است (اگر فعال شود). | سطح ایزولیشن **جداگانه‌ای** است که تراکنش باید صراحتاً انتخابش کند. |
| **فعال‌سازی** | با دستور: <br>`ALTER DATABASE MyDB SET READ_COMMITTED_SNAPSHOT ON;` | با دستور: <br>`ALTER DATABASE MyDB SET ALLOW_SNAPSHOT_ISOLATION ON;` |
| **نحوه انتخاب در تراکنش** | به‌صورت پیش‌فرض برای کل دیتابیس اعمال می‌شود (دیگر نیازی به SET نیست). | باید در ابتدای تراکنش بنویسید:<br>`SET TRANSACTION ISOLATION LEVEL SNAPSHOT;` |
| **دامنه زمان اسنپ‌شات (Snapshot Point)** | **برای هر Query** جداگانه اسنپ‌شات گرفته می‌شود. | **برای کل تراکنش** فقط یک بار در ابتدای تراکنش اسنپ‌شات گرفته می‌شود. |
| **رفتار در تغییرات همزمان (Writer Conflict)** | اگر دو تراکنش همزمان روی یک row کار کنند، فقط قفل معمولی رخ می‌دهد (مثل Read Committed). | اگر دو تراکنش یک row را تغییر دهند، دومین تراکنش در COMMIT با خطا (`Update conflict`) مواجه می‌شود. |
| **مناسب برای** | سیستم‌های خواندنی زیاد (Reporting، Read-heavy workloads). | سیستم‌هایی که نیاز به پایداری تصویری از داده در طول یک تراکنش دارند. |
| **کاهش قفل‌ها (Blocking)** | زیاد — خواندن‌ها دیگر با نویسنده‌ها بلاک نمی‌شوند. | زیاد — ولی در سطح تراکنش پایدارتر و قابل‌کنترل‌تر. |

---

## 🎯 خلاصه تفاوت کلیدی (در یک جمله)

> - **RCSI** ⇒ هر **کوئری جداگانه**، داده‌ی Commit‌شده‌ی لحظه‌ی اجرای خودش را می‌بیند.  
> - **Snapshot Isolation** ⇒ کل **تراکنش** یک نسخه ثابت از داده را از ابتدا تا پایان خود می‌بیند.

---

## 🔍 مثال تفاوت رفتاری

فرض کنیم جدول `Accounts` داریم با موجودی‌ها:

| AccountID | Balance |
|------------|----------|
| 1 | 100 |
| 2 | 200 |

### سناریو:
1.  تراکنش T1 شروع می‌شود.
2.  تراکنش T2 موجودی را آپدیت می‌کند و Commit می‌کند.
3.  تراکنش T1 دوباره همان سطرها را می‌خواند.

#### 🔹 در RCSI:
T1 در هر بار اجرای `SELECT`، **آخرین دیتاهای Commit‌شده تا همان لحظه اجرا** را می‌بیند.  
یعنی اجرای دوم `SELECT` مقدار جدید (Updated) را می‌خواند.

#### 🔹 در Snapshot Isolation:
T1 از زمانی که شروع شد، یک snapshot ثابت از داده دارد.  
حتی اگر T2 Commit کرده باشد، T1 همچنان همان مقادیر زمان شروع خود را می‌بیند.  
(یعنی مقدار قدیمی 100 و 200 را می‌بیند.)

---

## ⚙️ نحوه فعال‌سازی هرکدام
```sql
-- برای فعال‌سازی Snapshot Isolation
ALTER DATABASE MyDB SET ALLOW_SNAPSHOT_ISOLATION ON;

-- برای فعال‌سازی Read Committed Snapshot
ALTER DATABASE MyDB SET READ_COMMITTED_SNAPSHOT ON;
```

📌 نکته: این دو می‌توانند **همزمان فعال باشند**، اما انتخاب اینکه از کدام استفاده بشود بستگی به سطح ایزولیشن تراکنش دارد.

## ✅ جمع‌بندی سریع

| جنبه | RCSI | Snapshot Isolation |
|-------|------|-------------------|
| نوع | سطح read committed بهبود یافته | سطح جداگانه مستقل |
| Snapshot زمان‌بندی | هر Query | ابتدای Transaction |
| Conflict تشخیص | ندارد | دارد (در زمان Commit) |
| استفاده | خودکار برای همه‌ی تراکنش‌ها | فقط تراکنش‌هایی که صراحتاً تنظیم شوند |
| کاربرد معمول | برای خواندن سبک و سریع | برای سازگاری پایدار در تراکنش‌های طولانی |
