تفاوت اصلی بین **Row Lock** (قفل ردیف) و **Page Lock** (قفل صفحه) در **«دانه‎‌بندی» (Granularity)** یا همان «محدوده تحت پوشش» آن‌هاست. برای درک بهتر این موضوع در SQL Server، باید ابتدا بدانید که داده‌ها در دیتابیس چگونه ذخیره می‌شوند.

در SQL Server، کوچک‌ترین واحد ذخیره‌سازی داده، **Page** (صفحه) نام دارد که اندازه آن ثابت و برابر با **۸ کیلوبایت** است. هر صفحه می‌تواند شامل چندین ردیف (Row) باشد.

---

### ۱. Row Lock (قفل ردیف)
*   **محدوده:** فقط روی یک ردیف خاص از یک جدول.
*   **دقت:** بسیار بالا.
*   **همزمانی (Concurrency):** بسیار بالا. وقتی تراکنش A روی ردیف ۱ قفل می‌گیرد، تراکنش B می‌تواند بدون هیچ مشکلی ردیف ۲ (که در همان صفحه است) را تغییر دهد.
[[Concurrency]]
*   **سربار (Overhead):** بالاست. چون SQL Server باید برای هر ردیف، اطلاعات قفل را در حافظه مدیریت کند. اگر میلیون‌ها ردیف را قفل کنید، حافظه زیادی اشغال می‌شود (که همین باعث ایجاد **Lock Escalation** می‌شود که قبلاً بررسی کردیم).

### ۲. Page Lock (قفل صفحه)
*   **محدوده:** روی کل یک صفحه ۸ کیلوبایتی (شامل تمام ردیف‌های داخل آن صفحه).
*   **دقت:** پایین‌تر.
*   **همزمانی:** کمتر. وقتی تراکنش A روی یک صفحه قفل می‌گیرد، هیچ‌کس دیگری نمی‌تواند حتی ردیف‌های دیگری که در آن صفحه هستند را تغییر دهد، حتی اگر با ردیف مورد نظر تراکنش A کاری نداشته باشند.
*   **سربار:** بسیار کم. چون به جای ۱۰ یا ۲۰ ردیف، فقط **یک قفل** برای کل صفحه مدیریت می‌شود.

---

### مقایسه کلیدی در یک نگاه

| ویژگی | Row Lock | Page Lock |
| :--- | :--- | :--- |
| **دقت (Granularity)** | ریز (Fine-grained) | درشت (Coarse-grained) |
| **میزان همزمانی** | عالی | متوسط |
| **سربار مدیریت** | زیاد | کم |
| **احتمال بلوکه شدن** | کم | زیاد |

---

### مثال عملی برای درک بهتر

فرض کنید جدول `Employees` دارید که در هر صفحه (Page)، ۱۰ ردیف جای می‌گیرد.

1.  **سناریو با Row Lock:**
    *   کاربر A ردیف شماره ۱ را آپدیت می‌کند (فقط یک قفل روی ردیف ۱).
    *   کاربر B ردیف شماره ۵ را آپدیت می‌کند.
    *   **نتیجه:** هیچ بلوکه‌ای رخ نمی‌دهد. هر دو با سرعت کارشان را انجام می‌دهند.

2.  **سناریو با Page Lock:**
    *   کاربر A ردیف شماره ۱ را آپدیت می‌کند و SQL Server تصمیم می‌گیرد Page Lock بگیرد.
    *   کاربر B می‌خواهد ردیف شماره ۵ را آپدیت کند.
    *   **نتیجه:** کاربر B باید صبر کند (Block می‌شود)، چون کاربر A کلِ صفحه‌ای که ردیف ۵ هم در آن است را قفل کرده است!

---

### سیستم SQL Server چگونه تصمیم می‌گیرد؟

به‌صورت پیش‌فرض، SQL Server خودش تصمیم می‌گیرد که از چه نوع قفلی استفاده کند. او معمولاً با **Row Lock** شروع می‌کند، اما اگر:
*   تعداد ردیف‌های تحت تأثیر زیاد باشد.
*   حافظه تخصیص‌یافته به قفل‌ها رو به پایان باشد.
*   کوئری به گونه‌ای باشد که اسکن کردن کل جدول (Table Scan) به‌صرفه‌تر باشد.

آن‌وقت سیستم به‌طور خودکار قفل‌ها را به **Page Lock** یا نهایتاً **Table Lock** (همان Lock Escalation) ارتقا می‌دهد.

### نکته 

*  اگر می‌خواهید کنترل دستی داشته باشید، می‌توانید از **Lock Hints** استفاده کنید (مثلاً `WITH (ROWLOCK)`).
**اما هشدار:** استفاده از هینت‌ها در ۹۹٪ مواقع توصیه نمی‌شود، چون شما با این کار موتور بهینه‌ساز SQL Server را محدود می‌کنید و ممکن است جلوی تصمیم‌های هوشمندانه آن را بگیرید.

*   بهترین راه برای مدیریت این قفل‌ها، **طراحی ایندکس مناسب** است. وقتی ایندکس درست داشته باشید، کوئری مستقیماً به سراغ ردیف مورد نظر می‌رود، Row Lock گرفته می‌شود و در نتیجه احتمال Page Lock یا ارتقای قفل به حداقل می‌رسد.
