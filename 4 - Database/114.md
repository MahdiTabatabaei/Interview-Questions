درواقع **Index Seek** زمانی اتفاق می‌افتد که SQL Server بتواند **مستقیماً از طریق Index به رکوردهای موردنظر برسد** بدون اینکه کل جدول یا کل ایندکس را اسکن کند.

به زبان ساده:  
مثل **جستجو در فهرست یک کتاب** است؛ مستقیم به صفحه موردنظر می‌روی.

---

## چه زمانی Index Seek رخ می‌دهد؟

### 1️⃣ وقتی روی ستون شرط (`WHERE`) ایندکس وجود داشته باشد

مثال:

```sql
CREATE INDEX IX_Employees_ID
ON Employees(ID)
```

Query:

```sql
SELECT *
FROM Employees
WHERE ID = 10
```

در این حالت SQL Server مستقیم به مقدار **ID = 10** می‌رود → **Index Seek**

---

### 2️⃣ وقتی شرط جستجو Selective باشد

یعنی Query تعداد کمی رکورد برگرداند.

مثال:

```sql
WHERE CustomerID = 125
```

اگر فقط چند رکورد باشد → **Seek**

ولی اگر مثلاً:

```sql
WHERE Country = 'USA'
```

و نصف جدول USA باشد → ممکن است **Index Scan** شود.

---

### 3️⃣ وقتی شرط روی ابتدای ایندکس باشد

اگر ایندکس ترکیبی باشد:

```sql
CREATE INDEX IX_Test
ON Orders(CustomerID, OrderDate)
```

این Query **Seek** می‌شود:

```sql
WHERE CustomerID = 10
```

این هم **Seek** می‌شود:

```sql
WHERE CustomerID = 10
AND OrderDate = '2025-01-01'
```

اما این معمولاً **Seek نمی‌شود**:

```sql
WHERE OrderDate = '2025-01-01'
```

چون ستون اول ایندکس استفاده نشده.

---

### 4️⃣ وقتی روی ستون تابع (Function) استفاده نشود

این باعث می‌شود SQL Server نتواند Seek کند.

بد:

```sql
WHERE YEAR(OrderDate) = 2024
```

خوب:

```sql
WHERE OrderDate BETWEEN '2024-01-01' AND '2024-12-31'
```

---

### 5️⃣ وقتی نوع داده‌ها یکسان باشد

اگر conversion اتفاق بیفتد ممکن است Seek از بین برود.

مثال:

```sql
WHERE ID = '10'
```

در حالی که `ID` از نوع `INT` است.

---

# تفاوت مهم

**Index Seek**

- سریع
- مستقیم به رکورد می‌رود
- I/O کم

**Index Scan**

- کل ایندکس خوانده می‌شود
- کندتر
- I/O زیاد

---

✅ **یک نکته مهم برای مصاحبه SQL Server**

گاهی Execution Plan می‌نویسد:

```
Index Seek + Key Lookup
```

یعنی:
- ایندکس برای پیدا کردن رکورد استفاده شده
- اما برای گرفتن ستون‌های دیگر مجبور شده به **Clustered Index** برگردد
