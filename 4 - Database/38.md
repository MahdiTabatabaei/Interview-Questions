رویداد **Deadlock** زمانی رخ می‌دهد که **دو یا چند تراکنش منتظر منابعی هستند که توسط یکدیگر قفل شده‌اند** و هیچ‌کدام نمی‌توانند ادامه دهند.

**مثال:**

- **تراکنش T1:** قفل روی سطر X را دارد و برای قفل سطر Y منتظر است.
- **تراکنش T2:** قفل روی سطر Y را دارد و برای قفل سطر X منتظر است.

در این حالت، T1 منتظر T2 است و T2 منتظر T1. هر دو قفل شده‌اند و هرگز پیش نمی‌روند.

سیستم پایگاه داده (SQL Server) به طور خودکار Deadlock را تشخیص داده و معمولاً یکی از تراکنش‌ها را به عنوان “قربانی Deadlock” انتخاب کرده و آن را لغو (Rollback) می‌کند تا تراکنش دیگر بتواند ادامه دهد.

---


یک مثال ساده با دو جدول:

```sql
CREATE TABLE TableA (
    id INT PRIMARY KEY,
    value INT
);

CREATE TABLE TableB (
    id INT PRIMARY KEY,
    value INT
);

INSERT INTO TableA VALUES (1,10);
INSERT INTO TableB VALUES (1,20);
```

حالا دو **Session** جدا در SSMS باز می‌کنیم.

---

# Session 1
```sql
BEGIN TRAN

UPDATE TableA
SET value = value + 1
WHERE id = 1

WAITFOR DELAY '00:00:05'

UPDATE TableB
SET value = value + 1
WHERE id = 1

COMMIT
```

---

# Session 2
```sql
BEGIN TRAN

UPDATE TableB
SET value = value + 1
WHERE id = 1

WAITFOR DELAY '00:00:05'

UPDATE TableA
SET value = value + 1
WHERE id = 1

COMMIT
```

---

# چه اتفاقی می‌افتد؟

1. Session1 روی **TableA** قفل می‌گیرد.
2. Session2 روی **TableB** قفل می‌گیرد.

بعد از 5 ثانیه:

3. Session1 می‌خواهد **TableB** را آپدیت کند → ولی قفل است.
4. Session2 می‌خواهد **TableA** را آپدیت کند → ولی قفل است.

پس:

```
Session1 → منتظر TableB
Session2 → منتظر TableA
```

هیچ‌کدام آزاد نمی‌شوند → **Deadlock**

SQL Server یکی را انتخاب می‌کند و این خطا می‌دهد:

```
Transaction (Process ID ...) was deadlocked on resources with another process
and has been chosen as the deadlock victim.
```

---

# روش جلوگیری از این Deadlock

مهم‌ترین روش:

**همیشه جداول را در یک ترتیب یکسان Lock کنید.**

مثلاً هر دو تراکنش:

```
TableA → TableB
```

نه اینکه یکی برعکس باشد.
