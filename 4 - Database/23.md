درواقع **Fill Factor** مشخص می‌کند هنگام **ساخت یا Rebuild کردن ایندکس**، هر Page از B‑Tree چه مقدار پر شود.

مقدار آن معمولاً بین **1 تا 100** است.

- `100` → صفحه تقریباً کاملاً پر می‌شود  
- `80` → فقط 80٪ صفحه پر می‌شود و 20٪ خالی می‌ماند

این فضای خالی عمداً باقی می‌ماند تا **Insertهای آینده باعث Page Split نشوند**.

---

# نقش Fill Factor در ایندکس

در ساختار **B‑Tree** داده‌ها داخل **Pageهای 8KB** ذخیره می‌شوند.

وقتی صفحه کاملاً پر باشد و رکورد جدیدی وارد شود که باید در همان صفحه قرار بگیرد:

ابزار SQL Server مجبور می‌شود:

1. صفحه را **Split** کند  
2. نصف داده‌ها را به صفحه جدید منتقل کند  
3. ساختار درخت را آپدیت کند

این فرآیند باعث می‌شود:

- ایجاد Fragmentation زیاد شود  
- میزان I/O افزایش پیدا کند  
- سرعت Query کاهش پیدا کند

درواقع Fill Factor با **گذاشتن فضای خالی در صفحات** احتمال Page Split را کاهش می‌دهد.

---

# مثال ساده

فرض کنید یک Page ظرفیت **100 رکورد** دارد.

### Fill Factor = 100

```
Page
[100 رکورد]
```

اگر رکورد جدیدی وارد شود:

```
Page Split
```

صفحه تبدیل می‌شود به:

```
Page1: 50 رکورد
Page2: 50 رکورد
```

که باعث Fragmentation می‌شود.

---

### Fill Factor = 80

در زمان ساخت ایندکس:

```
Page
[80 رکورد + 20 فضای خالی]
```

وقتی رکوردهای جدید اضافه شوند:

```
80 → 81 → 82 → ... → 100
```

مدتی طول می‌کشد تا Page Split رخ دهد.

پس:

داشتن **Page Split کمتر → Fragmentation کمتر**

---

# تعریف Fragmentation چیست؟

درواقع Fragmentation یعنی **صفحات ایندکس به ترتیب فیزیکی مرتب نباشند**.

مثلاً:

```
Page1
Page7
Page3
Page20
```

به جای:

```
Page1
Page2
Page3
Page4
```

این باعث می‌شود:

- خواندن Range Queryها کندتر شود
- میزان I/O دیسک زیاد شود

---

# انتخاب مقدار مناسب Fill Factor

انتخاب مقدار بستگی به **نوع workload** دارد.

### 1️⃣ جدول mostly Read

اگر جدول:

- تغییر کم دارد
- بیشتر SELECT دارد

بهترین گزینه:

```
Fill Factor = 100
```

چون:

- فضای هدر نمی‌رود
- تعداد صفحات کمتر است

---

### 2️⃣ جدول با Insert زیاد

مثلاً:

- جدول Orders
- جدول Logs
- جدول Transactions

بهتر است:

```
Fill Factor = 90
یا
Fill Factor = 80
```

تا فضای خالی برای Insertها وجود داشته باشد.

---

### 3️⃣ جدول با Update روی کلید ایندکس

اگر مقدار ستون ایندکس تغییر کند و اندازه رکورد افزایش یابد:

```
Fill Factor پایین‌تر
```

مناسب‌تر است.

---

# نکته مهم درباره Clustered Index

اگر Clustered Index روی **کلید تصادفی** باشد (مثل `GUID NEWID()`):

عمل Insertها در وسط ایندکس اتفاق می‌افتد.

در این حالت:

```
Fill Factor پایین‌تر (مثلاً 70–80)
```

کمک می‌کند Fragmentation کمتر شود.

اما اگر کلید:

```
INT IDENTITY
```

باشد:

عمل Insert همیشه **آخر ایندکس** است.

در این حالت:

```
Fill Factor = 100
```

کاملاً مناسب است.

---

# یک مثال SQL

ساخت ایندکس با Fill Factor:

```sql
CREATE INDEX IX_Customers_Name
ON Customers(Name)
WITH (FILLFACTOR = 80);
```

یا هنگام Rebuild:

```sql
ALTER INDEX IX_Customers_Name
ON Customers
REBUILD WITH (FILLFACTOR = 80);
```

---

# جمع‌بندی

مقدار Fill Factor تعیین می‌کند:

**چه مقدار از هر Page هنگام ساخت ایندکس پر شود.**

هدف آن:

- کاهش Page Split
- کاهش Fragmentation
- بهبود Performance

قاعده عملی:

```
Read-heavy tables → Fill Factor نزدیک 100
Write-heavy tables → Fill Factor بین 70 تا 90
Sequential keys (INT Identity) → Fill Factor بالا
Random keys (GUID) → Fill Factor پایین‌تر
```
