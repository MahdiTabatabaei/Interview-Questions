✅ مفهوم **Key Lookup** (که در بعضی منابع به آن **Bookmark Lookup** هم گفته می‌شود) یکی از عملیات‌های خاص در SQL Server است که هنگام اجرای کوئری اتفاق می‌افتد، وقتی **دیتابیس مجبور شود از Index به جدول اصلی (Clustered Index) برگردد** تا ستون‌های بیشتری را که در ایندکس وجود ندارند، بخواند.

---

## 🔍 تعریف ساده

وقتی SQL Server از **Non-Clustered Index** برای فیلتر کردن رکوردها استفاده می‌کند، ولی لازم دارد **ستون‌هایی را بخواند که در آن ایندکس نیستند**، باید با کلید اصلی (Key) برگردد به داده اصلی.

به این مرحله می‌گویند **Key Lookup**.

یعنی:
> "من از ایندکس رکوردها را پیدا کردم، ولی برای گرفتن بقیه ستون‌ها مجبورم برگردم به جدول اصلی."

---

## 🔧 مثال ساده

فرض کن جدول زیر داریم:

```sql
CREATE TABLE Customers (
    CustomerID INT PRIMARY KEY CLUSTERED,
    Name NVARCHAR(100),
    City NVARCHAR(100),
    Phone NVARCHAR(50)
);
```

و یک ایندکس غیرکلاستر شده روی `City` داریم:

```sql
CREATE NONCLUSTERED INDEX IX_Customers_City ON Customers(City);
```

حال کوئری زیر را اجرا کنیم:

```sql
SELECT Name, City
FROM Customers
WHERE City = 'Tehran';
```

در اینجا:
- SQL Server می‌تواند از `IX_Customers_City` برای پیدا کردن سطرهای شهر *Tehran* استفاده کند.
- اما ستون `Name` در این ایندکس وجود ندارد.  
  پس باید برای هر سطر **برگردد به جدول اصلی** تا `Name` را بگیرد.

این مرحلهٔ رفت‌وبرگشت همان **Key Lookup** است.

---

## 🧠 در Execution Plan چگونه دیده می‌شود؟

وقتی Execution Plan را ببینی، معمولاً شامل دو مرحله است:

```
Index Seek (NonClustered)
→ Key Lookup (Clustered)
```

این یعنی:
1. رکوردهایی که `City = 'Tehran'` هستند از ایندکس گرفته می‌شوند.  
2. بعد برای گرفتن ستون‌های دیگر (`Name`) به Clustered Index مراجعه می‌شود.

---

## ⚠️ مشکل کجاست؟

در نگاه اول harmless است، ولی اگر تعداد رکوردها زیاد شود:

- برای هر رکورد باید **رفت و برگشت جداگانه** انجام دهد.  
- این یعنی ده‌ها/صدها **random I/O** روی دیسک.
- در نهایت باعث **کندی شدید (Performance Bottleneck)** می‌شود.

---

## 💡 راه‌حل‌ها برای حذف Key Lookup

1. **Covering Index ایجاد کن**

   یعنی ستون‌های مورد نیاز را در ایندکس اضافه کن (به عنوان *Included Columns*):

   ```sql
   CREATE NONCLUSTERED INDEX IX_Customers_City
       ON Customers(City)
       INCLUDE (Name);
   ```

   حالا `Name` هم در ایندکس موجود است → نیازی به Lookup نیست.

---

2. **فقط ستون‌های لازم را بخوان**

   اگر در SELECT همه‌چیز را `SELECT *` بگیری، احتمال Lookup زیاد می‌شود.
   
   بهتر است فقط ستون‌های لازم را بنویسی.

---

3. **بررسی Execution Plan**

   اگر دیدی در Plan عبارت **Key Lookup (Clustered)** هست، یعنی احتمالاً جای بهبود ایندکس وجود دارد.

---

## 📊 خلاصه‌ی مهم

| ویژگی | توضیح |
|--------|--------|
| تعریف | مراجعه از Index به Clustered Index برای گرفتن ستون‌های غایب |
| چه زمانی رخ می‌دهد | وقتی Query از Nonclustered Index استفاده کند ولی همه ستون‌های Query در آن ایندکس نباشند |
| علامت در Execution Plan | `Key Lookup (Clustered)` |
| اثر روی کارایی | خیلی گران است اگر تعداد رکورد زیاد باشد |
| راه‌حل | Covering Index با `INCLUDE` یا بازنویسی Query |
