درواقع B‑Tree (یا به طور دقیق‌تر B+ Tree) ساختار داده‌ای است که **اساس کار ایندکس‌ها در SQL Server** (و بسیاری دیگر از دیتابیس‌ها) است. نقش اصلی آن، **فراهم کردن دسترسی سریع و کارآمد به داده‌ها** در جداول بزرگ است، به طوری که نیازی به خواندن کل جدول (Full Table Scan) نباشد.

تصور کنید کتابخانه بزرگی دارید و دنبال یک کتاب خاص هستید. اگر کتاب‌ها فقط به صورت تصادفی روی قفسه‌ها چیده شده باشند، باید تمام کتاب‌ها را بگردید. اما اگر یک سیستم کاتالوگ (فهرست) منظم داشته باشید که به شما بگوید هر کتاب در کدام بخش، قفسه و ردیف قرار دارد، پیدا کردن کتاب بسیار سریع‌تر می‌شود. B‑Tree دقیقاً نقش همین کاتالوگ یا فهرست را برای دیتابیس بازی می‌کند.

# ساختار B+ Tree در SQL Server

ساختار B+ Tree یک ساختار درختی متعادل (Balanced Tree) است. این یعنی:

- **تمام برگ‌ها (Leaf Nodes) در یک سطح قرار دارند.** این باعث می‌شود که مسیر جستجو همیشه یکسان و قابل پیش‌بینی باشد.
- **هر گره (Node) می‌تواند تعداد زیادی فرزند داشته باشد.** این باعث می‌شود ارتفاع درخت کم باشد، که برای کاهش تعداد دیسک I/O بسیار حیاتی است.

در SQL Server، هر گره (Node) در B+ Tree معمولاً معادل **یک صفحه دیسک (Page)** است (8 کیلوبایت).

### اجزای اصلی B+ Tree:

1.  نقطه **Root Node (گره ریشه):** بالاترین گره درخت که نقطه شروع تمام جستجوهاست. معمولاً فقط یک گره ریشه وجود دارد.
2.  **Intermediate Nodes (گره‌های میانی / Internal Nodes):** این گره‌ها فقط شامل کلیدهای ایندکس و اشاره‌گرهایی (Pointers) به گره‌های پایین‌تر هستند. این گره‌ها به دیتابیس کمک می‌کنند تا سریع‌تر به سطح برگ‌ها برسد.
3.  **Leaf Nodes (گره‌های برگ):** پایین‌ترین سطح درخت. این گره‌ها **حاوی داده‌های واقعی** هستند (در Clustered Index) یا **اشاره‌گرهایی به ردیف‌های جدول** (در Non-Clustered Index). تمام برگ‌ها به هم متصل هستند (Linked List) که برای اسکن بازه‌ای (Range Scans) مفید است.

# نقش B‑Tree در SQL Server

1.  **مدیریت ایندکس‌ها:**
    *   **Clustered Index:** داده‌های جدول به صورت فیزیکی بر اساس کلید Clustered Index مرتب و در Leaf Nodes ذخیره می‌شوند. هر جدول فقط یک Clustered Index می‌تواند داشته باشد.
    *   **Non-Clustered Index:** Leaf Nodes این نوع ایندکس، **کلید ایندکس** و **ردیابی‌کننده (Row Locator)** به ردیف اصلی داده‌ها را نگه می‌دارند. این ردیف‌کننده در جدول Clustered، کلید Clustered Index است و در جداول Heap، آدرس فیزیکی ردیف (RID) است.

2.  **جستجوی سریع (Index Seek):**
    *   وقتی کوئری‌ای اجرا می‌شود، SQL Server جستجو را از Root Node شروع می‌کند.
    *   بر اساس مقادیر در گره‌های میانی، دیتابیس تصمیم می‌گیرد به کدام فرزند (کدام صفحه دیسک) برود.
    *   این فرآیند تا رسیدن به Leaf Node ادامه می‌یابد.
    *   به دلیل کم بودن ارتفاع درخت (به دلیل تعداد زیاد فرزند در هر گره)، تعداد دیسک I/O مورد نیاز برای پیدا کردن یک رکورد بسیار کم است.

3.  **اسکن بازه‌ای (Range Scan):**
    *   وقتی در کوئری از عملگرهایی مثل `>`, `<`, `>=`, `<=`, `BETWEEN`, `LIKE 'prefix%'` استفاده می‌شود، دیتابیس می‌تواند ابتدا یک رکورد را پیدا کند و سپس با استفاده از لیست پیوندی برگ‌ها، به صورت ترتیبی رکوردها را بخواند. این کار بسیار سریع‌تر از خواندن کل جدول است.

4.  **پشتیبانی از عملیات `ORDER BY` و `GROUP BY`:**
    *   اگر ایندکسی وجود داشته باشد که ترتیب ستون‌هایش با `ORDER BY` یا `GROUP BY` کوئری مطابقت داشته باشد، دیتابیس می‌تواند از همان ایندکس برای مرتب‌سازی استفاده کند و نیازی به مرتب‌سازی جداگانه داده‌ها نباشد.

5.  **مدیریت داده‌های در حال تغییر (Insert, Update, Delete):**
    *   هنگام درج، به‌روزرسانی یا حذف داده، B+ Tree ساختار خود را حفظ می‌کند.
    *   **Page Splits:** اگر یک گره (Page) پر شود، دیتابیس آن را به دو نیم تقسیم می‌کند و برخی داده‌ها را به گره جدید منتقل می‌کند. این فرآیند می‌تواند پرهزینه باشد، به خصوص اگر کلید Clustered Index بهینه نباشد.
    *   **Key Lookups:** در Non-Clustered Indexها، پس از پیدا کردن رکورد در Leaf Node، اگر ستون‌های درخواستی در ایندکس نباشند، دیتابیس باید از طریق Row Locator به Clustered Index (یا Heap) مراجعه کند تا داده‌های کامل را بخواند.

# B‑Tree در عمل (تصویر ذهنی)

*   **Root:** فقط یک کلید و اشاره‌گر به یک یا چند Node میانی.
*   **Intermediate Nodes:** شامل چندین کلید (که مقادیر بین دو اشاره‌گر را مشخص می‌کنند) و اشاره‌گر به Nodeهای پایین‌تر.
*   **Leaf Nodes:** شامل تمام کلیدها و داده‌ها (Clustered Index) یا کلیدها و Row Locatorها (Non-Clustered Index). برگ‌ها به هم متصل هستند.

**مثال ساده:**

فرض کنید ایندکس روی ستون `ID` داریم:

```
Root:
  [100] -> Pointer to Node A
  [500] -> Pointer to Node B

Node A (Intermediate):
  [50] -> Pointer to Leaf 1
  [150] -> Pointer to Leaf 2

Node B (Intermediate):
  [550] -> Pointer to Leaf 3
  [950] -> Pointer to Leaf 4

Leaf Nodes:
  Leaf 1: [10], [20], [30], [40] --> Data for IDs 10-40
  Leaf 2: [110], [120], [130], [140] --> Data for IDs 110-140
  ... و الی آخر
```

برای پیدا کردن ID=125:
1.  از Root شروع کن. 125 بین 100 و 500 است. برو به Node A.
2.  در Node A، 125 بین 50 و 150 است. برو به Leaf 2.
3.  در Leaf 2، ID=125 را پیدا کن و داده مربوطه را بخوان.

این فرآیند معمولاً فقط 3-4 مرحله (Page Read) طول می‌کشد، حتی برای جداولی با میلیون‌ها رکورد.

# نکات مهم

- **صفحات دیسک:** هر گره معمولاً یک صفحه 8 کیلوبایتی است.
- **تعداد فرزندان:** تعداد کلیدها و اشاره‌گرها در هر گره بستگی به اندازه کلید ایندکس دارد. کلیدهای کوچک‌تر باعث می‌شوند گره‌ها فرزندان بیشتری داشته باشند و ارتفاع درخت کمتر شود.
- **تعادل:** درخت همیشه متعادل باقی می‌ماند.

درک B+ Tree به شما کمک می‌کند تا بفهمید چرا انتخاب درست کلید ایندکس (به خصوص Clustered Index) و نوشتن کوئری‌های بهینه چقدر اهمیت دارد.
