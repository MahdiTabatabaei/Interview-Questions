تفاوت اصلی این است که **PostgreSQL برای کنترل همزمانی عمدتاً از MVCC استفاده می‌کند**، اما **SQL Server به طور سنتی از Locking استفاده می‌کند** (هرچند نسخه‌های جدید SQL Server هم Snapshot/MVCC‑like دارند).

بیاییم ساده و دقیق مقایسه کنیم.

---

# 1️⃣ مدل اصلی کنترل همزمانی

## PostgreSQL → MVCC (Multi-Version Concurrency Control)

در PostgreSQL وقتی یک ردیف تغییر می‌کند:

- ردیف قبلی را **حذف نمی‌کند**
- یک **نسخه جدید** از آن ردیف می‌سازد

در نتیجه:

- در Reader ها نسخه قدیمی را می‌بینند
- و Writer ها نسخه جدید را می‌نویسند

پس:

عمل **Reader و Writer همدیگر را بلاک نمی‌کنند.**

مثال:

```
T1: SELECT
T2: UPDATE
```

در PostgreSQL:

- SELECT نسخه قدیمی را می‌بیند
- UPDATE نسخه جدید می‌سازد
- Blocking کم است

---

## SQL Server → Lock-based Concurrency

ابزار SQL Server معمولاً برای کنترل همزمانی از **Locks** استفاده می‌کند.

مثال:

```
T1: UPDATE row
T2: SELECT same row
```

در حالت پیش‌فرض (Read Committed):

- UPDATE → Exclusive Lock
- SELECT → Shared Lock

پس:

```
SELECT باید صبر کند
```

یعنی **Blocking رخ می‌دهد**.

---

# 2️⃣ رفتار Read و Write

### PostgreSQL

```
Read → snapshot
Write → new version
```

درواقع Reader ها:

- هیچ Lock جدی نمی‌گیرند
- نسخه مناسب را می‌بینند

---

### SQL Server (Default)

```
Read → Shared Lock
Write → Exclusive Lock
```

در نتیجه:

- Read ممکن است Write را بلاک کند
- Write ممکن است Read را بلاک کند

---

# 3️⃣ Storage رفتار

### PostgreSQL

چون نسخه‌های مختلف نگه می‌دارد:

- جدول ممکن است **bloat** شود

برای همین:

```
VACUUM
```

لازم است.

فرایند [[VACUUM]] نسخه‌های قدیمی را پاک می‌کند.


---

### SQL Server

چون نسخه نگه نمی‌دارد (در حالت عادی):

- فضای اضافی ایجاد نمی‌شود
- فرایند VACUUM نیاز ندارد

اما Locking بیشتر می‌شود.

---

# 4️⃣ Snapshot در SQL Server

ابزار SQL Server هم می‌تواند شبیه MVCC رفتار کند اگر فعال شود:

### RCSI

```
READ_COMMITTED_SNAPSHOT
```

یا:

### Snapshot Isolation

در این حالت:

- مقدار row versions در **tempdb** ذخیره می‌شوند.

پس SQL Server هم می‌تواند:

```
Read بدون Blocking
```

داشته باشد.

اما **پیش‌فرض نیست**.

---

# 5️⃣ Performance در workload های مختلف

### PostgreSQL (MVCC)

خیلی خوب برای:

- read-heavy systems
- web applications
- microservices
- analytics

چون:

```
reads block writes = no
writes block reads = rarely
```

---

### SQL Server (Locking)

در workload های:

- transaction-heavy
- OLTP کلاسیک

خوب کار می‌کند، ولی ممکن است:

```
blocking
deadlock
```

بیشتر رخ دهد.

---

# 6️⃣ Deadlock

هر دو دارند، ولی:

- در **SQL Server** بیشتر دیده می‌شود (به خاطر Lock زیاد)
- در **PostgreSQL** کمتر

---

# خلاصه کوتاه

| ویژگی | PostgreSQL | SQL Server |
|------|-------------|------------|
| مدل اصلی | MVCC | Lock-based |
| Read blocking | تقریباً ندارد | ممکن است |
| Write blocking | کمتر | بیشتر |
| Version storage | داخل table | tempdb (اگر snapshot) |
| Cleanup | VACUUM | نیاز ندارد |

---

✅ **خلاصه خیلی کوتاه**

درواقع PostgreSQL از **MVCC** استفاده می‌کند که چند نسخه از ردیف‌ها نگه می‌دارد تا **Read و Write همدیگر را بلاک نکنند**، اما SQL Server به طور پیش‌فرض از **Locking** استفاده می‌کند که می‌تواند باعث **Blocking** شود، مگر اینکه **Snapshot Isolation یا RCSI** فعال شود.
