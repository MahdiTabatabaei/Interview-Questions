مفهوم **Included Columns** در ایندکس‌ها (مخصوصاً در SQL Server) این است که شما می‌توانید **ستون‌هایی را به یک ایندکس اضافه کنید که جزو کلید ایندکس نباشند، اما در Leaf Nodeها ذخیره شوند.**

این قابلیت به شما اجازه می‌دهد که **Covering Indexهای بسیار مؤثرتر و کارآمدتری** بسازید.

---

# تعری فCovering Index چیست؟

یک **Covering Index** ایندکسی است که **تمام ستون‌های مورد نیاز یک کوئری** (یعنی ستون‌های موجود در `SELECT` و `WHERE`) را پوشش می‌دهد.

وقتی ایندکس Covering باشد، دیتابیس می‌تواند **تمام اطلاعات مورد نیاز را مستقیماً از خود ایندکس بخواند** و نیازی به مراجعه به جدول اصلی (Clustered Index یا Heap) نداشته باشد. این باعث **افزایش چشمگیر سرعت** می‌شود.

---

# مشکل در روش سنتی ساخت Covering Index

فرض کنید کوئری زیر را داریم:

```sql
SELECT FirstName, Email
FROM Employees
WHERE City = 'Tehran';
```

برای ساخت یک Covering Index سنتی، باید کلید ایندکس را روی ستون `City` و سپس ستون‌های مورد نیاز (`FirstName`, `Email`) قرار دهیم:

```sql
-- روش سنتی (غیر بهینه)
CREATE INDEX IX_Employees_City_Covering
ON Employees (City, FirstName, Email);
```

مشکل این روش این است که:

1.  **ترکیب ستون‌ها در کلید ایندکس:** ستون‌های `FirstName` و `Email` که فقط برای خواندن استفاده می‌شوند، بخشی از کلید اصلی ایندکس می‌شوند. این باعث می‌شود:
    *   ایندکس **بزرگ‌تر** شود.
    *   عملیات `INSERT`/`UPDATE`/`DELETE` **کندتر** شود.
    *   در نتیجه **Fragmantation** بیشتری ایجاد شود.

---

# راه حل: Included Columns

با استفاده از `INCLUDE`، شما می‌توانید ستون‌های مورد نیاز را به **Leaf Level** ایندکس اضافه کنید، بدون اینکه بخشی از کلید اصلی ایندکس شوند.

مثال بالا با استفاده از Included Columns:

```sql
-- روش بهینه با Included Columns
CREATE INDEX IX_Employees_City_Covering_Included
ON Employees (City) -- ستون City کلید ایندکس است
INCLUDE (FirstName, Email); -- ستون‌های FirstName و Email در Leaf Level ذخیره می‌شوند
```

### مزایای این روش

1.  **کلید ایندکس کوچک و کارآمد:** کلید ایندکس فقط `City` است که باعث می‌شود ایندکس کوچک‌تر، سریع‌تر در جستجوها و کم‌تأثیرتر روی عملیات `INSERT`/`UPDATE`/`DELETE` باشد.
2.  **پوشش کامل کوئری:** تمام ستون‌های مورد نیاز (`City`, `FirstName`, `Email`) در Leaf Level ایندکس موجود هستند. بنابراین، دیتابیس می‌تواند این کوئری را به طور کامل از ایندکس بخواند (Covering Index).

---

# اجزای ایندکس با Included Columns

وقتی ایندکس بالا ساخته می‌شود، ساختار آن شبیه این است:

```
Root Node (فقط شامل City)
  ↓
Intermediate Nodes (فقط شامل City)
  ↓
Leaf Nodes:
  - City Value
  - FirstName Value  (از ستون INCLUDE)
  - Email Value      (از ستون INCLUDE)
```

---

# محدودیت‌ها

-   **فقط در SQL Server:** این قابلیت (با این سینتکس) مخصوص SQL Server است. سایر دیتابیس‌ها ممکن است مکانیزم‌های مشابهی داشته باشند.
-   **نوع داده:** ستون‌های `INCLUDE` باید انواع داده‌ای مشخصی داشته باشند (مثلاً نمی‌توانند انواع LOB مثل `VARCHAR(MAX)` یا `TEXT` باشند).
-   **اندازه:** در مجموع، اندازه ردیف در Leaf Level نباید از محدودیت‌های Page (8KB) فراتر رود.
-   **کاربرد:** برای ستون‌هایی که در `WHERE` یا `JOIN` استفاده نمی‌شوند، ولی در `SELECT` مورد نیاز هستند، بیشترین کاربرد را دارد.

# جمع‌بندی

درواقع **Included Columns** ابزاری قدرتمند برای بهینه‌سازی عملکرد کوئری‌هاست، زیرا:

1.  به شما اجازه می‌دهد **Covering Indexهای مؤثرتری** بسازید.
2.  با **کوچک نگه داشتن کلید اصلی ایندکس**، باعث افزایش سرعت `SELECT` و کاهش تأثیر منفی روی `INSERT`/`UPDATE`/`DELETE` می‌شود.
3.  یک راه عالی برای **افزایش سرعت خواندن داده‌ها** بدون ایجاد ایندکس‌های خیلی بزرگ و حجیم است.
