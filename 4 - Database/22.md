استفاده از **INT** یا **GUID** به‌عنوان Primary Key تأثیر مستقیم روی **Indexing، اندازه ایندکس‌ها، Fragmentation و Performance** دارد. چون Primary Key معمولاً همان **Clustered Index** هم هست و در ساختار **B‑Tree** تمام ایندکس‌ها استفاده می‌شود.

در ادامه تفاوت‌ها را دقیق بررسی می‌کنیم.

---

# 1️⃣ اندازه (Storage Size)

### INT
- اندازه: **4 bytes**

### GUID
- اندازه: **16 bytes**

یعنی GUID تقریباً **۴ برابر بزرگ‌تر** است.

### اثر روی ایندکس

چون کلید Clustered در همه **Non‑Clustered Indexها** ذخیره می‌شود:

اگر GUID استفاده کنیم:

- تمام ایندکس‌ها بزرگ‌تر می‌شوند
- مصرف دیسک بیشتر
- حافظه بیشتر
- I/O بیشتر

بنابراین از نظر **Storage و Cache efficiency**، INT بسیار بهتر است.

---

# 2️⃣ Fragmentation و Page Split

### INT (Identity)

اگر از:

```sql
INT IDENTITY
```

استفاده شود:

مقادیر همیشه **صعودی (Sequential)** هستند.

مثال:

```
1
2
3
4
5
```

نتیجه:

- Insert همیشه **انتهای ایندکس** انجام می‌شود
- Page Split کم
- Fragmentation کم
- Performance بهتر

---

### GUID (NEWID)

GUID معمولی:

```sql
NEWID()
```

کاملاً **تصادفی** تولید می‌شود.

مثال:

```
F8A1...
02BC...
9D3F...
```

نتیجه:

- رکورد باید **وسط صفحات ایندکس** وارد شود
- Page Split زیاد
- Fragmentation شدید
- Insert کند

این یکی از بدترین سناریوها برای Clustered Index است.

---

# 3️⃣ Performance جستجو (Lookup)

در B‑Tree:

کلید بزرگ‌تر → تعداد کلید کمتر در هر Page → درخت عمیق‌تر.

چون GUID بزرگ‌تر است:

- Pages کمتر داده نگه می‌دارند
- ارتفاع B‑Tree بیشتر می‌شود
- I/O بیشتر می‌شود

در نتیجه:

```
INT lookup سریع‌تر است
```

---

# 4️⃣ Performance Join

در JOINها:

```sql
orders.customer_id = customers.id
```

اگر کلید:

INT باشد:

- مقایسه سریع‌تر
- مصرف حافظه کمتر

اگر GUID باشد:

- مقایسه سنگین‌تر
- hash/join structures بزرگ‌تر

در سیستم‌های بزرگ تفاوت قابل توجه می‌شود.

---

# 5️⃣ Distributed Systems

جایی که GUID برتری دارد:

**سیستم‌های توزیع‌شده**

مثال:

- Microservices
- Replication
- Multi-database inserts
- Offline clients

چون GUID:

- globally unique است
- نیاز به هماهنگی مرکزی ندارد

در حالی که INT:

- معمولاً نیاز به sequence مرکزی دارد.

---

# 6️⃣ امنیت (Security / Enumeration)

INT قابل حدس است:

```
/api/users/1
/api/users/2
/api/users/3
```

GUID قابل حدس نیست:

```
/api/users/8F14E45F-CEEA...
```

بنابراین برای APIهای عمومی GUID گاهی امن‌تر است.

---

# 7️⃣ GUID بهتر شده (Sequential GUID)

SQL Server گزینه بهتری هم دارد:

```
NEWSEQUENTIALID()
```

ویژگی:

- GUID است
- اما تقریباً **ترتیبی تولید می‌شود**

نتیجه:

- Fragmentation کمتر
- Insert سریع‌تر از NEWID()

ولی هنوز:

- از INT بزرگ‌تر است.

---

# 8️⃣ خلاصه مقایسه

### INT

مزایا:

- کوچک (4 bytes)
- ایندکس کوچک‌تر
- Page Split کمتر
- Fragmentation کمتر
- B‑Tree کوتاه‌تر
- Join سریع‌تر
- Insert سریع‌تر

معایب:

- در سیستم‌های توزیع‌شده مشکل ایجاد می‌کند
- قابل حدس است

---

### GUID

مزایا:

- Unique در سطح جهانی
- مناسب سیستم‌های distributed
- قابل حدس نیست

معایب:

- 16 bytes
- ایندکس بزرگ
- Fragmentation زیاد (با NEWID)
- Page Split زیاد
- Insert کندتر
- Join سنگین‌تر

---

# نتیجه عملی در طراحی دیتابیس

در اکثر سیستم‌ها بهترین الگو این است:

```
Clustered PK → INT IDENTITY
```

و اگر GUID نیاز داریم:

```
GUID → Non-clustered column
```

یا:

```
Clustered → INT
Unique → GUID
```
