انتخاب **کلید Clustered Index** یکی از *مهم‌ترین تصمیم‌های طراحی دیتابیس* است، چون **ترتیب فیزیکی دیتای جدول** بر اساس آن ستون تعیین می‌شود. انتخاب درست باعث سرعت بالای Queryها، و انتخاب اشتباه باعث کندی شدید عملیات می‌شود.

در ادامه معیارهای صحیح و مشکلات انتخاب اشتباه را مفصل توضیح می‌دهم.

------------------------------------

# معیارهای انتخاب کلید Clustered Index

### 1) **Unique بودن یا نزدیک به یونیک بودن**
کلید باید مقادیر تکراری خیلی کمی داشته باشد.

چرا؟

چون اگر مقدار تکراری زیاد باشد:

- گروه‌های بزرگی از رکوردها پشت سر هم قرار می‌گیرند  
- فیلتر و جستجو سخت‌تر می‌شود  
- Page Split افزایش می‌یابد  

بهترین گزینه: کلیدهای تقریباً یونیک مثل:

- `ID`
- `OrderID`
- `GUID (به شرط NEWSEQUENTIALID())`

------------------------------------

### 2) **Static بودن (ثابت بودن مقدار)**  
کلید Clustered نباید تغییر کند.

چرا؟

اگر مقدار کلید عوض شود، دیتابیس مجبور است **رکورد را به مکان جدید منتقل کند** چون ترتیب فیزیکی بر هم می‌خورد.

این کار:

- بسیار گران است  
- باعث Fragmentation بالا می‌شود  

پس ستون‌هایی مثل:

- `email`
- `username`
- `status`

هرگز مناسب نیستند.

------------------------------------

### 3) **Narrow بودن (کم‌حجم بودن ستون)**  
چون کلید Clustered در:

- تمام Index Non‑Clusteredها
- اشاره‌گرهای داخلی B‑Tree 
[[B‑Tree]]

ذخیره می‌شود.

اگر کلید بزرگ باشد:

- تمام ایندکس‌ها بزرگ می‌شوند  
- مصرف دیسک افزایش می‌یابد  
- حافظه بیشتری مصرف می‌شود  
- I/O زیاد می‌شود  

مثلاً:

بد:
- NVARCHAR(100)
- GUID عادی (16 بایت)

خوب:
- BIGINT
- INT

------------------------------------

### 4) **Ever-increasing بودن (صعودی بودن)**  
یکی از مهم‌ترین معیارها.

اگر کلید مرتب افزایش یابد:

- رکوردهای جدید همیشه به آخر Page اضافه می‌شوند  
- Page Split کم می‌شود  
- Fragmentation بسیار پایین می‌آید  
- Insert بسیار سریع‌تر می‌شود  

بهترین انتخاب‌ها:

- Identity INT / BIGINT  
- NEWSEQUENTIALID() برای GUID  

انتخاب‌های بد:

- GUID معمولی (`NEWID()`) → اتفاقی تولید می‌شود  
- شماره تلفن  
- کد ملی (چند محلی و نه کاملاً صعودی)

------------------------------------

### 5) **ستونی که در Queryها زیاد استفاده می‌شود (به‌خصوص Range Queries)**
تمرکز اصلی Clustered Index:

- جستجوهای Range (`BETWEEN`)
- مرتب‌سازی (`ORDER BY`)
- گروه‌بندی (`GROUP BY`)

پس اگر اکثر Queryها مبتنی بر بازه زمانی هستند:

بهترین کلید Clustered:

```
CreatedAt (اگر Ever-increasing باشد)
```

اگر اکثر Queryها روی CustomerID انجام می‌شود:

```
CustomerID
```

------------------------------------

# اگر کلید Clustered Index اشتباه انتخاب شود چه مشکلاتی ایجاد می‌شود؟

### مشکل 1) **Page Split زیاد**
وقتی کلید بی‌نظم باشد:

- رکورد باید وسط Page گذاشته شود
- Page شکسته می‌شود و جابه‌جایی اتفاق می‌افتد

نتیجه:

- کندی شدید Insert  
- افزایش هزینه CPU و I/O  
- افزایش حجم دیتابیس  

Page Split = دشمن اصلی Performance

------------------------------------

### مشکل 2) **Index Fragmentation بالا**
یکی از بزرگترین دلایل کند شدن:

- Scanها کند می‌شوند
- Cached Pages ناکارآمد می‌شود
- هزینه Reads افزایش می‌یابد

GUIDهای تصادفی بدترین حالت را ایجاد می‌کنند.

------------------------------------

### مشکل 3) **بزرگ‌شدن تمام Non-Clustered Indexها**
چون کلید Clustered داخل همه Indexها نگهداری می‌شود.

اگر کلید بزرگ باشد:

- همه ایندکس‌ها بزرگ‌تر می‌شوند  
- حافظه مصرفی بیشتر  
- I/O بیشتر  
- کوئری‌ها کندتر  

به همین دلیل هرگز NVARCHAR(100) را کلید Clustered نکنید.

------------------------------------

### مشکل 4) **کند شدن JOINها**
اگر ستون کلید:

- تکراری زیاد داشته باشد  
- یا طول زیادی داشته باشد  

JOINها سنگین می‌شوند.

------------------------------------

### مشکل 5) **کند شدن Updates**
اگر کلید تغییر کند = جابه‌جایی فیزیکی رکورد = بسیار سنگین

------------------------------------

# خلاصه توصیه‌ها برای کلید Clustered Index

بهترین انتخاب ستون باید:

- یونیک یا نزدیک به یونیک باشد  
- Ever-Increasing باشد  
- کوچک باشد (INT یا BIGINT)  
- ثابت باشد  
- در Queryها زیاد استفاده شود، مخصوصاً Range Queries  

بدترین انتخاب‌ها:

- GUID تصادفی  
- ستون‌های متنی (NVARCHAR)  
- ستون‌های پر تغییر  
- ستون‌های Low Selectivity مثل: `status`, `gender`
