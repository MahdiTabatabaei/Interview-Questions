در SignalR در نسخهٔ ASP.NET Core **به‌صورت خودکار** تلاش می‌کند اتصال را برقرار نگه دارد. اما سازوکار reconnect **یکسان نیست** و دقیقاً به این شکل کار می‌کند:

# ۱. مدل Reconnect در SignalR Core چگونه است؟

در SignalR سه وضعیت اصلی دارد:

1. **Connected**
2. **Reconnecting**
3. **Disconnected**

وقتی اینترنت قطع شود، شبکه unstable شود، سرور ری‌استارت شود، یا load balancer اتصال را ببندد، فرآیند زیر رخ می‌دهد:

---

# ۲. سازوکار Reconnect مرحله‌به‌مرحله

## مرحله ۱: تشخیص قطع‌شدن

وقتی یکی از موارد زیر رخ دهد:

- اتصال WebSocket بسته شود
- درخواست SSE/Long Polling پاسخی نگیرد
- عمل ping/pong به‌موقع نرسد

در این وضعیت SignalR تشخیص می‌دهد اتصال از بین رفته.

---

## مرحله ۲: ورود به حالت Reconnecting

کلاینت وارد وضعیت **Reconnecting** می‌شود و event زیر اجرا می‌شود:

JavaScript:
```javascript
connection.onreconnecting(error => {
    console.log("Reconnecting...", error);
});
```

در این حالت:
- هیچ پیام جدیدی دریافت یا ارسال نمی‌شود  
- اتصال *قابل استفاده نیست*  
- و UI می‌تواند پیام “در حال اتصال…” نمایش دهد  

---

## مرحله ۳: تلاش برای اتصال مجدد (Backoff Algorithm)

ابزار SignalR به‌صورت خودکار با الگوریتم زیر تلاش می‌کند:

1. بعد از **0 ثانیه** (فوری) → تلاش اول  
2. اگر موفق نشد → **2 ثانیه**  
3. اگر موفق نشد → **10 ثانیه**  
4. اگر موفق نشد → **30 ثانیه**  
5. سپس هر **30 ثانیه یک‌بار**

این همان **Exponential Backoff** است که در کلاینت‌ها استاندارد است.

تعداد تلاش‌ها **نامحدود** است مگر خودت قطعش کنی.

---

## مرحله ۴: بازیابی اتصال موفق (Reconnected)

اگر کلاینت دوباره به هاب وصل شود:

```javascript
connection.onreconnected(connectionId => {
    console.log("Reconnected with ID:", connectionId);
});
```

اما نکته مهم:

## نکته: ConnectionId جدید می‌شود

هیچ‌وقت پس از reconnect، ConnectionId قبلی بازنمی‌گردد.

این یعنی:
- باید گروه‌ها را مجدداً join کنی  
- هر داده‌ای بر اساس ConnectionId باید دوباره ساخته شود  

---

## مرحله ۵: شکست کامل اتصال

اگر کلاینت به هر دلیلی نتواند reconnect کند (مثلاً هاب خاموش شده):

JavaScript:
```javascript
connection.onclose(error => {
    console.log("Connection closed.", error);
});
```

و وضعیت به‌طور کامل **Disconnected** می‌شود.

این حالت مثلاً وقتی رخ می‌دهد که:
-  رویداغد connection.stop() را اجرا کرده باشی  
- و یا token دیگر معتبر نباشد  
- مسیر هاب اشتباه شده باشد  

---

# ۳. سمت کلاینت دقیقاً چه اتفاقی می‌افتد؟

### JavaScript
به‌صورت پیش‌فرض **auto reconnect فعال نیست**  
و باید خودت آن را روشن کنی:

```javascript
const connection = new signalR.HubConnectionBuilder()
    .withUrl("/chat")
    .withAutomaticReconnect()
    .build();
```

اگر پارامتر ندهی، از همان backoff استاندارد بالا استفاده می‌شود.

---

### C# Client
در C# نیز باید reconnect را فعال کنی:

```csharp
var connection = new HubConnectionBuilder()
    .WithUrl("https://localhost/chat")
    .WithAutomaticReconnect()
    .Build();
```

---

### نسخه‌های قدیمی SignalR (ASP.NET Framework)

در نسخه‌های قدیمی:
- تنظیم reconnect خودکار **اجباری و داخلی** بود  
- اما reconnect کامل نبود، بلکه یک اتصال جدید ساخته می‌شد  

---

# ۴. نکته مهم: چرا Sometimes قطع می‌شود؟

اتصال ممکن است به دلایل زیر قطع شود:

- اتفاق Drop شدن WebSocket توسط پروکسی / فایروال  
- رخداد Load balancer timeout  
- سرور ری‌استارت  
- ممکن است Token منقضی شده  
- و یا Cache invalidation در cloud  
- قطع کوتاه اینترنت کاربر  

ابزار SignalR برای همهٔ این‌ها reconnect می‌کند، **مگر token دیگر معتبر نباشد**.

---

# ۵. جمع‌بندی

ابزار SignalR reconnect را این‌طور انجام می‌دهد:

1. **قطع اتصال را تشخیص می‌دهد**
2. **وارد حالت reconnecting می‌شود**
3. با الگوریتم Backoff تلاش می‌کند:
   - فوری
   - 2 ثانیه
   - 10 ثانیه
   - 30 ثانیه
4. اگر موفق شد:
   - رویداد `onreconnected` اجرا می‌شود
   - و ConnectionId جدید صادر می‌شود
5. اگر شکست خورد:
   - رویداد `onclose` اجرا می‌شود
