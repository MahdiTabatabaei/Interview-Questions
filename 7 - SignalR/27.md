در SignalR Core برای برقراری ارتباط بین کلاینت و سرور از چند **Transport** مختلف استفاده می‌شود. Transport در واقع **روش انتقال داده روی شبکه** است. SignalR طوری طراحی شده که اگر بهترین روش در دسترس نباشد، به روش‌های دیگر **fallback** کند.

سه Transport اصلی وجود دارد.

---

# 1) WebSockets
بهترین و کارآمدترین Transport در SignalR است.

ویژگی‌ها:
- ارتباط **دوطرفه (Full‑Duplex)**  
- اتصال **پایدار (Persistent Connection)**  
- **کمترین latency**
- مصرف **کمتر CPU و شبکه**
- مناسب برای real‑time واقعی (چت، بازی، بازار مالی)

نحوه کار:
- یک اتصال TCP باز می‌ماند
- کلاینت و سرور هر زمان بخواهند پیام ارسال می‌کنند
- نیازی به درخواست HTTP جدید نیست

شرایط استفاده:
- مرورگر باید WebSocket را پشتیبانی کند
- سرور باید WebSocket را فعال کرده باشد
- بعضی Proxy یا Firewall ممکن است آن را مسدود کنند

به همین دلیل همیشه اولین انتخاب SignalR است.

---

# 2) Server‑Sent Events (SSE)
اگر WebSocket در دسترس نباشد، SignalR از SSE استفاده می‌کند.

ویژگی‌ها:
- ارتباط **یک‌طرفه از سرور به کلاینت**
- بر پایه **HTTP Streaming**
- اتصال HTTP باز می‌ماند
- سرور می‌تواند داده را push کند

اما:
- کلاینت نمی‌تواند روی همان اتصال پیام بفرستد
- برای ارسال پیام از کلاینت، درخواست HTTP جداگانه ارسال می‌شود

پشتیبانی مرورگر:
- اکثر مرورگرها
- **Internet Explorer پشتیبانی نمی‌کند**

موارد استفاده:
- Notification
- Feed
- بروزرسانی داده

---

# 3) Long Polling
آخرین گزینه و fallback نهایی است.

ویژگی‌ها:
- بر پایه **HTTP Request/Response**
- اتصال دائمی وجود ندارد
- کلاینت یک درخواست ارسال می‌کند
- سرور درخواست را نگه می‌دارد تا پیام داشته باشد
- بعد از ارسال پیام اتصال بسته می‌شود
- کلاینت فوراً درخواست جدید می‌فرستد

چرخه به این صورت است:

```
Client ----request----> Server
Client <---response---- Server
Client ----request----> Server
Client <---response---- Server
```

معایب:
- latency بیشتر
- مصرف منابع بیشتر
- تعداد request بالا

مزیت:
- تقریباً روی **همه شبکه‌ها و مرورگرها کار می‌کند**

---

# نحوه انتخاب Transport

SignalR به صورت **خودکار** Transport مناسب را انتخاب می‌کند.

الگوریتم انتخاب:

1. تلاش برای **WebSockets**
2. اگر ممکن نبود → **Server‑Sent Events**
3. اگر آن هم ممکن نبود → **Long Polling**

این فرآیند را **Transport Fallback** می‌نامند.

---

# فرآیند انتخاب در اتصال

وقتی کلاینت می‌خواهد وصل شود:

1. ابتدا یک درخواست **negotiate** به سرور ارسال می‌شود
2. سرور اعلام می‌کند چه Transportهایی پشتیبانی می‌شوند
3. کلاینت بهترین گزینه را انتخاب می‌کند
4. اتصال برقرار می‌شود

نمونه درخواست:

```
/chatHub/negotiate
```

پاسخ سرور شامل لیست transportها است.

---

# امکان انتخاب دستی Transport

اگر لازم باشد می‌توان Transport خاصی را اجبار کرد.

مثال در JavaScript:

```javascript
const connection = new signalR.HubConnectionBuilder()
  .withUrl("/chatHub", {
      transport: signalR.HttpTransportType.WebSockets
  })
  .build();
```

یا:

```javascript
signalR.HttpTransportType.LongPolling
```

# مقایسه سریع

| Transport | نوع اتصال | سرعت | دوطرفه |
|-----------|-----------|------|--------|
| WebSockets | persistent | بسیار سریع | بله |
| SSE | HTTP streaming | متوسط | فقط سرور |
| Long Polling | request/response | کندتر | بله (غیرمستقیم) |

---

✅ جمع‌بندی:

ابزار SignalR Core سه Transport دارد:

- WebSockets (بهترین)
- Server‑Sent Events
- Long Polling (fallback)

کلاینت ابتدا تلاش می‌کند WebSocket استفاده کند و اگر شرایط شبکه یا مرورگر اجازه ندهد، به گزینه‌های بعدی برمی‌گردد تا اتصال real‑time همچنان برقرار بماند.
