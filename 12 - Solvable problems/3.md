برای کنترل تعداد بسیار زیاد درخواست‌ها به یک سرویس خارجی (مثل سیستم بانکی) در C#، معمولاً باید چند الگوی مهم را همزمان استفاده کنیم تا:

- سیستم بانکی overload نشود
- اپلیکیشن خودمان crash نکند
- میزان [[Latency]] کنترل شود
- عملکرد retry و timeout مدیریت شود
- مقدار [[Throughput]] بالا باقی بماند

مهم‌ترین راهکارها:

---

# معماری پیشنهادی

به جای اینکه هر درخواست کاربر مستقیماً به بانک وصل شود:

```text
Users -> API -> Queue -> Worker Service -> Bank API
```

یعنی:

- درخواست‌ها داخل Queue قرار می‌گیرند
- و Workerها با تعداد کنترل‌شده درخواست‌ها را به بانک ارسال می‌کنند
- و Rate Limit اعمال می‌شود
- مکانیزم Retry و Circuit Breaker داریم

# راهکارهای اصلی

## 1. Rate Limiting

کنترل تعداد درخواست در ثانیه.

مثلاً:
- حداکثر 100 درخواست در ثانیه به بانک

در .NET می‌توان از:

```csharp
System.Threading.RateLimiting
```

استفاده کرد.

نمونه:

```csharp
using System.Threading.RateLimiting;

var limiter = new TokenBucketRateLimiter(
    new TokenBucketRateLimiterOptions
    {
        TokenLimit = 100,
        TokensPerPeriod = 100,
        ReplenishmentPeriod = TimeSpan.FromSeconds(1),
        QueueProcessingOrder = QueueProcessingOrder.OldestFirst,
        QueueLimit = 1000,
        AutoReplenishment = true
    });
```

استفاده:

```csharp
var lease = await limiter.AcquireAsync(1);

if (lease.IsAcquired)
{
    // Call bank API
}
else
{
    // Reject or retry later
}
```

# 2. Queue-Based Processing

بهترین روش برای حجم بالا.

به جای ارسال مستقیم:

- درخواست داخل RabbitMQ / Kafka / Azure Service Bus قرار می‌گیرد
- و Workerها پردازش می‌کنند

مزایا:
- جلوگیری از فشار لحظه‌ای
- قابلیت scale
- و Retry آسان
- جلوگیری از crash

نمونه ساده با Channel در C#:

```csharp
using System.Threading.Channels;

var channel = Channel.CreateBounded<string>(10000);

await channel.Writer.WriteAsync("transaction-request");
```

Worker:

```csharp
while (await channel.Reader.WaitToReadAsync())
{
    var item = await channel.Reader.ReadAsync();

    await ProcessBankRequest(item);
}
```

# 3. محدود کردن تعداد Request همزمان

نباید هزاران request همزمان به بانک ارسال شود.

استفاده از SemaphoreSlim:

```csharp
private static SemaphoreSlim semaphore = new SemaphoreSlim(50);

public async Task CallBankApi()
{
    await semaphore.WaitAsync();

    try
    {
        await SendRequest();
    }
    finally
    {
        semaphore.Release();
    }
}
```

یعنی:
- حداکثر 50 درخواست همزمان

# 4. Retry Policy با Polly

سرویس بانکی ممکن است:
- خطای timeout دهد
- 500 برگرداند
- موقتاً unavailable باشد

استفاده از Polly:

```csharp
services.AddHttpClient("BankApi")
    .AddTransientHttpErrorPolicy(policy =>
        policy.WaitAndRetryAsync(3, retry =>
            TimeSpan.FromSeconds(Math.Pow(2, retry))));
```

Retry:
- بار اول: 2 ثانیه
- بار دوم: 4 ثانیه
- بار سوم: 8 ثانیه

---

# 5. Circuit Breaker

اگر بانک down شد:
- نباید همچنان هزاران request ارسال کنیم

درواقع Circuit Breaker موقتاً ارتباط را قطع می‌کند.

نمونه:

```csharp
.AddCircuitBreakerAsync(
    5,
    TimeSpan.FromSeconds(30));
```

یعنی:
- اگر 5 خطا پشت سر هم رخ دهد
- تا 30 ثانیه درخواست جدید ارسال نشود

# راهکارهای صحیح در Kubernetes

## 1. Distributed Rate Limiting با Redis

رایج‌ترین روش Production.

همه Podها از یک storage مشترک استفاده می‌کنند.

معمولاً:
- ابزار Redis
- یا API Gateway

استفاده می‌شود.

---

# معماری

```text
Pod1 ─┐
Pod2 ─┼──> Redis Counter
Pod3 ─┘
```

همه Podها قبل از ارسال request:

- تعداد درخواست‌های فعلی را از Redis چک می‌کنند
- اگر limit پر شده باشد request را:
  - reject
  - queue
  - delay

می‌کنند.

---

# نمونه ساده در C#

## نصب

```bash
dotnet add package StackExchange.Redis
```

---

## پیاده‌سازی

```csharp
using StackExchange.Redis;

var redis = await ConnectionMultiplexer.ConnectAsync("redis:6379");
var db = redis.GetDatabase();

public async Task<bool> CanSendRequest()
{
    var key = $"bank-api-limit:{DateTime.UtcNow:yyyyMMddHHmmss}";

    var count = await db.StringIncrementAsync(key);

    if (count == 1)
    {
        await db.KeyExpireAsync(key, TimeSpan.FromSeconds(1));
    }

    return count <= 100;
}
```

---

# نحوه کار

همه Podها:

- یک key مشترک دارند
- ابزار Redis atomic increment انجام می‌دهد
- مجموع requestها کنترل می‌شود

# 3. Queue بهترین گزینه برای بانک

برای سیستم بانکی معمولاً حتی Rate Limiting هم کافی نیست.

بهترین معماری:

```text
Users
  ↓
API Pods
  ↓
Kafka / RabbitMQ
  ↓
Worker Pods (Limited)
  ↓
Bank API
```

---

# چرا Queue مهم است؟

فرض کنید:
- 20 هزار کاربر همزمان request می‌دهند

اگر مستقیم call کنید:
- بانک fail می‌شود

اما Queue:

- درخواست‌ها را buffer می‌کند
- و Workerها با نرخ ثابت مصرف می‌کنند

مثلاً:

```text
بانک فقط 50 request/sec
```

پس Workerها دقیقاً با همین سرعت consume می‌کنند.

# 4. Leader Election

- یک coordinator pod

اما این روش:
- پیچیده‌تر
- و single point of failure

است.

معمولاً Redis بهتر است.

# 5. Token Bucket Distributed

حرفه‌ای‌ترین الگوریتم.

- burst را مدیریت می‌کند
- load smoothing دارد
